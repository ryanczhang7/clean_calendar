# Audit: H22 — the phase that could not declare what its tests needed

**Date:** 2026-09-14
**Scope:** finding **H22** from the consolidated field report (new in WORLD-011),
read against the harness at `5633dbe`. The report offers three options and ranks
them; this round takes **option 1** (let RED write the manifest and check the
diff) and also does option 2 (name it at PLANNED) and option 3 (document the
excursion), because the report says the documentation is required whichever
option is chosen and because option 1 cannot cover every ecosystem.
**Left out:** nothing in the finding. What option 1 cannot reach — ecosystems
with no in-file dev/production split — falls to option 3 by design, and that is
stated rather than papered over.

## Decided

- **Dependency manifests are their own category.** `manifest`, split out of
  `config`, covering `Cargo.toml`, `package.json`, `pyproject.toml` and the four
  lockfiles that change when one is installed. RED, GREEN, GATES and SCAFFOLD may
  write it; PLANNED, REVIEW and DONE may not. `config` keeps everything else, so
  splitting the category did not hand RED a `tsconfig`, a `vite.config`, or a
  Dockerfile — those are production surface and stay frozen. Four tests pin that
  specifically, because "RED can write config now" is the plausible misreading.
- **Only files with an in-file dev/production split qualify.** `go.mod`,
  `requirements.txt` and `*.csproj` stay `config`. They have nowhere to put a
  test dependency that a checker could distinguish, so granting RED write access
  would be granting it production dependencies with no way to tell.
- **The permission is only safe because the commit is read.** The lock sees a
  path, never a diff, so it cannot tell a test dependency from a production one.
  `check-boundaries.sh` does it instead: for every commit whose *committed* story
  frontmatter says `phase: RED`, it deletes the dev-dependency block from both
  sides of the manifest and requires the remainder to be identical.
- **It has to be per-commit, and that is the whole design.** By the time a PR
  exists the story says REVIEW, and the merged branch diff cannot attribute a
  line to a phase. Only the story file committed alongside each change can. A
  check that read the tip, or the branch diff, would never see a RED commit at
  all — it would pass every time and mean nothing.
- **Whole-file comparison, not diff-hunk parsing.** Strip the block from each
  side and compare what is left. A hunk reader has to understand context lines
  and section boundaries; this only has to find one block, and it catches a
  version bump as readily as an addition — which matters, because bumping an
  existing production dependency changes what production code resolves to, from
  the phase that may not write production code.
- **Punctuation is normalised away before comparing.** Adding a dev block where
  none existed leaves a trailing comma or a blank line on one side only. A check
  that calls that a production change is a check people learn to route around,
  which is the failure this repository is least able to afford.
- **`[project.optional-dependencies]` is treated as production.** Extras can be
  production extras, and the safe error is a refusal RED can escalate rather than
  a permission nobody checks. PEP 735 `[dependency-groups]` is the supported
  place for Python test dependencies.
- **Lockfiles are permitted unchecked**, because they have no split to read. That
  is sound only because the manifest they follow from *is* checked: a dependency
  nobody declared cannot be used.
- **The excursion is written down, which the report says is required regardless.**
  `tdd-cycle`, `rules.md` and the `test-developer` prompt all say what RED does
  when the manifest cannot carry what it needs: stop, tell the orchestrator,
  change phase deliberately, record why. The report's own diagnosis is that a
  refusal with no sanctioned next step is the condition under which agents invent
  one, and before this round the harness said nothing at all.

## Evidence

- **The asymmetry the finding names is real and was reproduced.** Before this
  round, on a fixture in RED: `echo x >> Cargo.toml` refused, `echo x >>
  package.json` refused, `pyproject.toml` refused, lockfiles refused — while
  GREEN could write any of them, and any production dependency in them. Five
  assertions, all red before the category existed.
- **Every new assertion was earned by a reverted mutation**, through
  `scripts/mutate.sh`, each restored byte-for-byte:

  | Mutation | Watched red |
  |---|---|
  | TOML dev-section pattern stops matching | `a dev-dependency added in RED is fine` — a legitimate test dependency now reads as a production change |
  | the before/after comparison replaced with `if false` | all four refusal cases |
  | the `phase = RED` filter removed | `GREEN may add a production dependency` — the negative control |

  The third is the one worth keeping: it proves the check is scoped to RED rather
  than merely present, and without it a "cleanup" that dropped the phase filter
  would have quietly frozen GREEN's dependencies too.
- **RED was genuine on both halves.** `phase-guard`: 5 of 9 new cases red before
  the category (the four that must stay frozen already passed, which is the point
  of including them). `boundaries`: 6 of 8 red before the check existed; the two
  that passed are negative controls — GREEN's permission and the lockfile
  exemption — and could not fail until the check existed, so the mutations above
  are what earn them.
- **The suite is green and larger.** `bash scripts/ci-local.sh` — 13 suites, 546
  assertions, 0 failures. `boundaries` 34, `phase-guard` 114, `lib` 135.

## What would have to be true for this to be wrong

- That the dev-block extractors are right for real manifests. They are tested
  against fixtures in three formats. A `Cargo.toml` using
  `[target.'cfg(unix)'.dev-dependencies]` is handled by the `(^|\.)dev-dependencies$`
  pattern; a `package.json` with `devDependencies` written on one line is handled
  by the brace counter; neither shape is in the suite.
- That normalising trailing commas does not hide a real change. A manifest where
  the only production change is a trailing comma is not a dependency change, so
  the risk is theoretical — but it is a deliberate loosening and it is recorded
  here rather than only in a comment.
- That per-commit attribution survives history rewriting. A squashed or rebased
  branch presents different commits than were made; a squash-merge of a story
  branch would collapse RED and GREEN into one commit whose story says REVIEW,
  and this check would inspect nothing. The harness merges PRs rather than
  squashing, so it holds today, and it is fragile to that setting changing.
- That RED writing a lockfile is acceptable unchecked. It follows from the
  manifest check, and a lockfile edited *alone* cannot introduce a usable
  dependency — but nothing verifies the lockfile agrees with the manifest.

## What was not checked

- **No real project exercised this.** Every test is a fixture with a synthetic
  `Cargo.toml` and `package.json`. The finding came from a Rust story that worked
  around the gap with thirty lines of hand-rolled temp-directory code; that story
  is the real subject and it lives downstream.
- **Poetry and uv layouts were not tested.** The TOML extractor recognises
  `tool.poetry.group.{dev,test}*.dependencies` and `tool.uv.dev-dependencies` by
  pattern, from reading the formats, not from a fixture.
- **The excursion path has never been walked.** No story here has needed a test
  dependency in an ecosystem without a dev block, so the `go.mod` instruction is
  documentation that has not been used once.
- **No measurement of the check's cost.** It runs `git show` twice per manifest
  per RED commit. On a long branch with many RED commits this is linear and
  untimed.
- **H23's classifier is not used by this check.** `check-boundaries.sh` calls
  `classify` directly, since it already sources `lib.sh`. The new
  `scripts/classify.sh` is for test code in other languages; there is now one
  mechanism with two entry points, which is fine until they drift.

## Stories filed

None. Findings from a field report are applied here directly and recorded in this
audit; the harness ships its `docs/backlog/` to consumers, so a story about the
harness would be inherited by every project that installs it.
