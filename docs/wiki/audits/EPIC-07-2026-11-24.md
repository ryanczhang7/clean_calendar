   Each exact mutant goes red under the narrowest suite holding its
   assertion. Stryker over `handler.ts` agrees: 226 mutants, 206 killed,
   20 survived. Every survivor is one the first audit classified as
   equivalent or acceptable, and none is a CAL-085 or CAL-086 target. CAL-087's
   second mutant, `258:6` ConditionalExpression `true`, is the sub-condition
   `choiceFor(originalMinutes) === "at"`, not the whole condition, and it is
   killed both by the CAL-087 filter and by the whole unit project. Rests on
   E-DV, E-STRYKER and E-258.
2. **The per-story gaps are closed, except for three assertions that no
   mutant can reach independently.** Sixteen assertions passed on arrival
   without a DV reaching them. Thirteen are now earned, one mutation each
   (E-EARN). The three left over are named in E-EARN and in "Tests whose names
   claim more than they pin". None warrants a story, because the behaviour
   each one claims is pinned by a neighbouring assertion in the same case.
   Every DV row in the four handoffs was re-run in item 1, so each handoff's
   mutation table is reproduced in full, not by one sample.
3. **The cheap "not checked" items are cleared.**
   - The five `CalendarPage.tsx` timeouts are real detections that show up
     as a hang. Each mutant makes the `?event=` effect navigate forever, which
     is a real production defect: an endless replace-navigation loop. Under
     test, the act-flushed effect loop blocks the worker, so no test finishes
     and vitest's own `--testTimeout` never fires. The suite cannot go green
     under any of them, so they stay counted as detected. One of them
     (`536:9` `raw !== null`) also fails three assertions before it hangs.
     Rests on E-HANG.
   - All 13 hand-enumerated mutants of the `sw.ts` push and
     notificationclick listeners (`:54-64`) are killed by `src/sw.test.ts`.
     Rests on E-SW.
   - `258:6` is killed under the whole unit project. Rests on E-258.
4. **The general save path's guard is a real gap, filed as CAL-089.**
   `EventSheet.tsx:444:22` (`saving.current = true` after `commit`) and
   `:435:22` (`saving.current = false` before the write) both survive the
   whole unit project, all 3421 tests. Under `:444`, every Save after a
   refused save is silently ignored, and closing to escape asks "Discard
   changes?". This is CAL-088's defect on the path every event write takes.
   Under `:435`, a second press while a create is in flight creates a second
   event. The Save button is never disabled, so the guard is the only
   defence. The code is CAL-012's, not EPIC-07's. It is filed here because
   both audits of this epic met it and CAL-088's Out of scope routed it to
   the PO. Rests on E-GUARD.
5. **PO-2 warrants a fix story, not a test story, and the decision is the
   PO's. Not filed.** Reproduced, no longer just reasoned: with the `sent_at`
   PATCH answering 500 and every read answering, one reminder was pushed
   **six times**, once a minute from 09:00 to 09:05, and the run logged
   **nothing**. With 204 it was pushed once (E-PO2). A test-only story cannot
   pin anything here, because the correct behaviour is undecided: is a
   repeat acceptable, should the run retry, should it log? The minimum is
   uncontroversial. A non-2xx PATCH should be logged the way a non-2xx DELETE
   already is (`handler.ts:273-276`), because for an unattended cron the log
   is the only record. Whether to also stop the repeats is a product
   decision. A draft criterion for the PO is in E-PO2.
6. **Not filed: the vacuous "no scope question" needles.** In the
   `ReminderHost` harness, `onClose` clears the sheet's request
   (`EventSheet.test.tsx:2164-2167`), so
   `queryByRole("alertdialog", { name: "Change which events?" })` after
   `waitFor(onClose)` cannot fail (`:2678`, `:2929`, `:2964`). The behaviour
   they claim is still pinned, because any path that asks the scope question
   does not close, and each case waits for `onClose` first. It is reported as
   theatre, not filed. The PO may file a one-line reorder (assert before the
   close) if they want the needle to mean something. Rests on E-EARN, row
   087-AC3-dialog.

### E-PO2: item 4, a sent_at PATCH that answers non-2xx

The claim: with every read answering and the PATCH answering 500, one
reminder is pushed once per run for as long as it is inside the window, and
nothing is logged. A scratch Deno script (scratchpad `po2.ts`, run with
