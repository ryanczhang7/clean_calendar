## Decided

1. **The security core holds.** The owner gate, `isOwnerEmail`, RLS on all
   seven tables, `is_owner()`'s case and trim handling of the *claim*, its
   `security definer`, and the anon `execute` revoke are each pinned: every
   mutant of them was killed by an assertion that means it. Nothing below
   asks for these to be retested.
2. **`is_owner()` has one latent defect, and it needs a fix rather than
   only a test.** With `app_config.owner_email` blank (`''` or spaces), the
   shipped predicate returns **true** for a whitespace-only e-mail claim.
   CAL-003's client rule refuses exactly that case
   (`isOwnerEmail("   ", "   ") === false`, `session.test.ts:83`). The
   `coalesce(email, '') <> ''` guard checks the claim *before* trimming,
   and removing it changes no test (M4). Exploiting it needs a misconfigured
   owner *and* a token with a blank e-mail claim, so it is low severity, but
   it is the security predicate and it disagrees with its own spec. Filed as
   **CAL-032** (fix). Rests on Evidence E-SQL-3.
3. **The biggest gap is the data layer's patch mappers.** 13 of the 15
   columns in `fromEventPatch` / `fromEventOverridePatch` can be written to
   the wrong column and the whole unit suite stays green. Measured: an
   `endsAt` patch that writes `starts_at` passes 220/220. A daily recurrence
   is silently turned into `null` (non-recurring) by a mutant no test sees.
   Filed as **CAL-035**. Rests on E-TS-rows.
4. **AC-6's "whatever value the client sent" is tested only for a past
   value.** A trigger that honours a client-sent *future* `updated_at`
   survives, and so does one that drops the `greatest(...)` monotonic guard.
   Filed as **CAL-033**. Rests on M7 and M20.
5. **Every CHECK constraint in the schema is untested**, along with the
   `app_config` single-row check and the `reminders` FK cascade. CAL-004
   left them unpinned on purpose, but `toEvent` relies on the `origin`
   CHECK, and the calendar relies on `ends_at > starts_at`. Filed as
   **CAL-034**. Rests on M11 to M15 and M18.
6. **The UI gaps are interaction details, not access control:** how the
   account menu dismisses, the owner redirect's `replace`, the StrictMode
   once-only redirect, `tabIndex={-1}` on three headings, and Dialog's
   `preventDefault` on Escape. Filed together as **CAL-036**. Rests on
   E-TS-AppShell, E-TS-SignInPage, E-TS-Dialog and E-TS-NotFound.
7. **Token values are unpinned**, so a dark theme with light-theme text
   passes. `tokens.md` already states contrast ratios with a mechanical
   formula, so this is cheap to pin. Filed as **CAL-037**. Rests on
   E-tokens.
8. **The `SignInPage` offline tests are flaky under load, and that
   corrupts mutation scores.** Two different tests failed in 12 of 340
   unrelated full-suite runs (3.5%), and three of those failures were
   the *only* failure, so Stryker scored a kill that no assertion earned.
   CAL-005 says this was "filed as a follow-up", but no story file
   exists. Filed as **CAL-038**. This is not a survivor cluster. It is
   filed because it makes the mutation gate's kill count untrustworthy.
   Rests on E-flake.
9. **Run Stryker per module with a narrowed `mutate` and an explicit
   command, never unscoped.** A full-suite command is safer against false
   survivors, but until CAL-038 lands it creates false kills. Check every
   kill whose only failing test is a `SignInPage` offline test. The scoped
   configuration below took 1 to 6 minutes per module on this host.

## Evidence

Everything below was measured on one Windows 11 host (12 logical CPUs) with
Node 24.19.0, Vitest 5.0.4, Stryker 10.0.0 (`@stryker-mutator/core`, built-in
command runner), Deno 2.9.7, Supabase CLI 2.120.0 (local stack, Docker

Stryker runs and the SQL batch ran **at the same time** for most of the

could be wrong.

### How Stryker was run

There is no `--commandRunner.command` CLI flag in Stryker 10 (`stryker run
--help`), so each module got its own config file in the session scratchpad
(outside the tree, not committed), run from the repository root as
`pnpm exec stryker run <scratch>/<name>.mjs`. Every config had this shape,
and only `command`, `mutate` and the JSON file name varied:

```js
export default {
  testRunner: "command",
  commandRunner: { command: "pnpm exec vitest run --project unit <FILES>" },
  coverageAnalysis: "off",
  timeoutMS: 60000,
  concurrency: 4,
  mutate: ["<ONE FILE>"],
  reporters: ["clear-text", "json"],
  jsonReporter: { fileName: "reports/mutation/<name>.json" },
  clearTextReporter: { allowColor: false, logTests: false },
  tempDirName: ".stryker-tmp",
  plugins: [],
};
```

`coverageAnalysis: "off"` means every kill is a real run of the command. No
mutant is classed static. `<FILES>` was one of two things:

- **Narrowed** (data layer and `session.ts`): the test files that import the
  module. For `result.ts`: `src/data/kinds.test.ts src/data/events.test.ts
  src/data/eventOverrides.test.ts`. For `rows.ts`: `src/data/rows.test.ts`
  plus those three. For `kinds.ts`, `events.ts` and `eventOverrides.ts`: their
  own test file. For `session.ts`: `src/auth/session.test.ts
  src/auth/RequireOwner.test.tsx src/auth/SignInPage.test.tsx`.
- **Full** (empty `<FILES>`, i.e. `pnpm exec vitest run --project unit`, all
  220 tests): every component, `shared/version.ts`, and a second run of all
  five data modules, to rule out survivors that only the narrowed command
  would produce.

**The runner was checked before any score was trusted.** Stryker reported
`result.ts:27:7` `status === 0` → `status !== 0` as Killed. The same mutation

**E-SQL-3: the blank-owner defect.** Five rolled-back transactions against the
running stack (node + `postgres`, as `postgres`, `update app_config set
owner_email = …`, `set_config('request.jwt.claims', …)`, `set local role
authenticated`, `select public.is_owner()`, then rollback):

    {"owner_email":"","claim_email":"","is_owner":false}
    {"owner_email":"","claim_email":"   ","is_owner":true}
    {"owner_email":"   ","claim_email":"   ","is_owner":true}
    {"owner_email":"   ","claim_email":"","is_owner":false}
    {"owner_email":"owner@example.com","claim_email":"   ","is_owner":false}
    after rollback: {"owner_email":"owner@example.com"}

Mechanism, read from the shipped body: the guard tests the claim *before*
trimming (`'   ' <> ''` is true). The equality then compares
`lower(trim('   '))` = `''` with `lower(trim(''))` = `''`. CAL-004's handoff
says the guard is load-bearing because "with no `email` claim it must be
`false`". Against the shipped body it is not: GREEN wrapped the equality in
`coalesce(…, false)`, and that already gives `false` for a missing claim,
which is why M4 survives. What would make this unrepresentative: GoTrue
would have to issue a token whose `email` claim is whitespace, and that was
not checked. Exploiting the defect needs that token and an operator who
blanks `owner_email` (no CHECK prevents it).

## What would have to be true for this to be wrong

- A survivor is a gap only if a *test* is the right place to catch it.
  CAL-034's CHECK constraints could instead be judged out of scope
  (CAL-004 left them unpinned on purpose). That is the PO's call.
- "equivalent" for `select=`, the empty select, rests on one PostgREST
  build: the local stack the Supabase CLI 2.120.0 started.
- The React "setState after unmount is ignored" equivalences assume React 19
  (the installed version). They do not hold on React 17.
- `.order(col, {})` is equivalent only while postgrest-js defaults
  `ascending` to `true` (2.117.3).
- E-SQL-3's severity assumes GoTrue never issues a whitespace e-mail claim.
- The per-module counts assume the flaky offline tests caused no false kills
  beyond the four found by "only failure" parsing. A flaky failure *alongside*
  a real one does not change a verdict.
