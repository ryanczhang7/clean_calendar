## Decided

1. **The confirm screen's save path is the worst-protected code in the epic.
   Filed as CAL-049.** Five behaviours the owner meets on every capture can
   break without one of the 2,386 unit tests failing (E-RECHECK R1 to R5):
   - an all-day event's end date is replaced by its start date at Save
     (`ConfirmPage.tsx:109`), so a 12-14 Oct proposal is stored as 12 Oct only;
   - a partly filled end is overwritten with start + 1 h instead of being left
     to validation (`:112`);
   - the form's `preventDefault` can be removed (`:271`). In a real browser the
     Save button would then submit the form and reload the page;
   - after a failed save, `end()` can be removed (`:297`), and Save stays blocked
     for good;
   - the "couldn't save" alert can show on open (`:214`).
   Rests on E-STRYKER `ConfirmPage.tsx` and E-RECHECK.
2. **The capture function's job-row POST is not pinned to `application/json`.
   Filed as CAL-050, together with three unhandled-input cases.** With the
   job-row write's `content-type` header deleted, all 160 Deno tests pass (H63).
   Deno's `fetch` then labels a string body `text/plain;charset=UTF-8`. **I did
   not measure what PostgREST does with that.** If it refuses the body, every
   capture writes no row and answers 502. Also unpinned: a JSON `null` body
   (H16) and a Gemini 200 whose body is not JSON (G19) both throw out of the
   handler instead of returning a 4xx/5xx with CORS headers, a `PUT` is handled
   as a capture (H1), and `missing` is not de-duplicated when the model's
   `kindName` is null (H31). Rests on E-DENO.
3. **Nothing pins the content of the Gemini `responseSchema`. Filed as CAL-051.**
   With `nullable: true` deleted from every nullable field (G16), with the 0..1
   bounds deleted (G13), or with `allDay` dropped from `required` (G20), the suite
   is green. G16 is the serious one. The model would be told it cannot answer
   null, which pushes it to invent a title, time or place. That is exactly what
   the product brief forbids, and `geminiReplySchema` would still accept the
   invented strings. The existing test `assertEquals(req.generationConfig.responseSchema,
   geminiResponseSchema)` (`gemini_test.ts:79`) compares the export with itself
   and pins only the wiring. Rests on E-DENO.
4. **The owner check fails open when `is_owner()` answers 2xx with a body that
   is not JSON. Filed as CAL-052.** Changing the `catch` after `res.json()` to
   `return null` (O7) or to treating it as `true` (O7b) admits the caller, and all
   160 tests pass. Every other fail-closed branch (network error, non-2xx, false,
   null, `"true"`) is pinned. Low likelihood, because PostgREST answers JSON, but
   it is the one unpinned branch of an authorization check. Rests on E-DENO.
5. **The capture screen's request lifecycle is unpinned in five places. Filed
   as CAL-053.** Each of these survives the whole unit suite (E-RECHECK R6 to R10):
   - a reply arriving after the owner has left `/capture` still navigates to
     `/capture/confirm` (`CapturePage.tsx:89`);
   - with `-=` for `+=` on the run counter, a cancelled request's late reply is
     accepted once a new one starts (`:179`, Stryker `:135`);
   - after a failed shrink, "Asking the assistant…" stays up (`:148`);
   - after Remove, the same file cannot be picked again (`:200`);
   - a change event with no file attaches `undefined` (`:254`).
   Stryker also shows a Cancel during the shrink still sending the request
   (`:137`, `:146`).
6. **The downscaler's canvas path (`browserDeps`) has no test at all. Filed as
   CAL-054.** 17 Stryker mutants survive there, among them `drawImage` deleted
   (a blank image sent to Gemini) and `toBlob`'s null check inverted. jsdom has
   neither `createImageBitmap` nor a canvas, so only the `integration` project
   (Playwright) can reach it. The story makes `integration` required for itself.
7. **`KindPicker.tsx`'s keyboard behaviour is mostly unpinned. Filed as CAL-055
   under EPIC-03.** That behaviour is CAL-012's, and EPIC-03's audit did not mutate
   this file. It is in scope here only because CAL-021 touched the file to add
   `describedBy`. 21 gap survivors, among them:
   - any key on the trigger opens the list, Tab included, and its
     `preventDefault` then keeps focus there (`:78`);
   - ArrowDown can step past the last option (`:88`);
   - Enter on an empty list throws (`:98`);
   - Tab no longer closes the list (`:107`);
   - focus does not return to the trigger after a choice (`:59`);
   - the visual `data-active` marker is never asserted (`:160`);
   - the Escape guards can be removed **together** (`:103-104`, E-RECHECK K1).
   Every CAL-021 line in the file (`aria-describedby`) is killed.
8. **The function's input validation, status mapping, row contents, CORS
   answer, Gemini call and the stories' central claims all hold.** Killed:
   - the owner bypass (H3c: 21 red);
   - every refusal status (H48 to H51), the base64 scan's boundaries (H8 to H12,
     H55, H59), and the size limits (H5 to H7, H61);
   - the job-row contents and hash (H23 to H25, H35 to H37, H69);
   - the live-kinds query (H20, H21);
   - all eight CORS mutants (C1 to C8);
   - the Gemini URL, key header, part order and reply path (G2 to G4, G7, G8,
     G17, G18).
   CAL-018's RED table of negative controls was measured on a scratch
   implementation. Its rows for kind normalisation, `deleted_at`, de-duplication,
   `kind` pushed twice, latency rounding, `parts[1]` and the key header are now
   confirmed against the shipped code (H20, H26 to H29, H23, G8, G3).
9. **`shared/captureSchema.ts`, `src/pwa/*`, `src/sw.ts`, `confirmSummary.ts`
   and `captureJobs.ts` need nothing.** 5/5, 144/146, 149/151 and 8/9 killed.
   Every survivor is equivalent.
10. **CAL-043 (EPIC-03, PLANNED) is partly overtaken.** Its AC-1 to AC-3 target
    `eventForm.ts:66`, `:136` and `:144`, and this run killed every Stryker mutant
    on those lines: CAL-021's "from an empty start" cases now cover them. Only
    `:137` and `:193` (its AC-4 and AC-5) still survive. Re-check CAL-043's scope
    before starting it. Not re-filed here.
11. **Every assertion that passed on arrival in the seven stories has now been
    seen to fail.** CAL-018, CAL-019, CAL-021 and CAL-022 earned theirs with pasted
    probes. CAL-047 had none, and CAL-048's were earned in its GATES (78 red; row
    site only, 8 red). CAL-020's two absence halves are earned here (E-EARN).

## Evidence

Everything was measured on one host: Windows 11, 12 logical CPUs, Node 24.19.0,
Vitest 5.0.4, Stryker 10.0.0 (command runner), Deno 2.9.7, time zone
America/Chicago. Nothing was measured on CI, against a local Supabase stack
(Docker was not running) or against the hosted function. Stryker's JSON reports
(`reports/mutation/e05-*.json`) and sandbox (`.stryker-tmp/`) are gitignored and
will not survive a clean checkout.

**Load.** Each Stryker run used `concurrency: 6`. The E-RECHECK runs were
sequential and never overlapped Stryker. Some E-DENO runs overlapped the first
two Stryker runs. Under load a mutant can be killed by a flake or a timeout, but
it never survives because of one, so every survivor below stands. One Stryker
mutant timed out (`downscale.ts`) and is counted as detected without being
re-run.

## What would have to be true for this to be wrong

- H63's ranking assumes PostgREST refuses, or misreads, a `text/plain` body on
  `POST /rest/v1/capture_jobs`. If it accepts it, H63 is a pin with no live
  defect behind it, and CAL-050 is cheap insurance rather than a fix.
- G16's ranking assumes Gemini honours `responseSchema`'s `nullable` closely
  enough that removing it changes what the model returns. CAL-048's REVIEW saw
  real replies from 3.8 Flash, but nobody has measured them with and without it.
- O1 to O3 are classed acceptable on the assumption that the Supabase gateway's
  `verify_jwt` refuses any request without a valid `Bearer` token before the
  function runs.
- H17, H47 and the `captureJobs.ts` select are equivalent only if PostgREST's
  error bodies are JSON objects and `select=` returns every column (EPIC-01's
  measurement).
- The ConfirmPage `busyRef` survivors are acceptable because React 19 flushes
  state between discrete events. Under a concurrent-mode change that deferred
  them, a double tap on Save could create two events.
- R2's consequence (a page reload on Save) is how browsers treat a form whose
  submit is not prevented. jsdom does not implement navigation, so it was
  reasoned, not observed.
