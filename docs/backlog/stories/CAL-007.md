## Context

EPIC-02, brief §3 step 2: on a fresh device, before the calendar, a short
walkthrough shows the default kinds and lets the owner rename, recolour,
delete or add them (the owner's explicit choice over landing on the calendar).
Screen: `components.md`, "Kinds walkthrough and kind editor"; copy:
`voice.md`, "Kinds walkthrough" and "Dialogs"; layout: `layout.md`. The kind
list and the kind editor built here are reused unchanged by the kinds page in
CAL-008. Kind writes go through `src/sync/kindActions.ts`, online through the
repository until CAL-015 routes them through the outbox.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given an owner on a device where the walkthrough has not been
  completed (no `cc.onboarded` flag in `localStorage`), when any calendar
  route is visited, then `/welcome` renders: heading "Your event kinds", the
  line from `voice.md`, and one list row per live kind in `sort_order` showing
  a swatch in the active theme's colour, the kind's initial, its name and an
  "Edit" button named "Edit {name}".
- **AC-2** - Given the editor for a kind, when the name is changed and saved,
  then the row shows the new name and the repository received it; when the
  new name equals another live kind's ignoring case, then "You already have a
  kind called {name}." is shown on the field (`aria-invalid="true"`) and
  nothing is saved.
- **AC-3** - Given the editor, when a palette swatch is chosen for the light
  theme, then the dark swatch moves to that palette row's dark colour unless
  the dark colour was already edited by hand; the preview shows a line per
  theme "Text contrast {r}:1 · Against background {s}:1" computed by
  `domain/colour`.
- **AC-4** - Given a custom hex whose better text colour is below 4.5:1 in
  either theme, when it is entered, then Save is disabled, the message "Text
  would be hard to read. Try a darker shade." (or "…lighter shade.") is shown,
  and "Fix it" moves the colour to the nearest lightness that passes and
  re-enables Save. *Control:* `#808080` (best 4.35:1) must be refused; a
  colour below 3:1 against the surface but ≥ 4.5:1 for text must only warn.
- **AC-5** - Given "Delete {name}" in the editor, when it is confirmed in the
  dialog ("Delete the kind {name}?" … Cancel / Delete), then the kind is
  soft-deleted, its row disappears, and the toast "Deleted the kind {name}.
  Its events now show as Kind removed." is shown; Cancel changes nothing.
- **AC-6** - Given "Add kind", when the editor opens, then the name is empty and
  the first palette pair not used by a live kind is preselected; saving
  appends the kind with the next `sort_order`.
- **AC-7** - Given the walkthrough, when "Done, show my calendar" is pressed,
  then `cc.onboarded` is set and `/` renders; with zero live kinds the button
  has `aria-disabled="true"`; on the next visit to `/` on this device the
  walkthrough is not shown.

### Block 1 - `src/domain/colour.ts` gains

```ts
export const SURFACE_LIGHT = "#FFFFFF";   // tokens.css --color-surface, light
export const SURFACE_DARK = "#121417";    // tokens.css --color-surface, dark
export const TEXT_FLOOR = 4.5;            // accessibility.md, Contrast
export const SURFACE_FLOOR = 3;           // kinds-palette.md, "≥ 3:1 against its theme's surface"
/** The nearest lightness that passes TEXT_FLOOR, or null when `hex` already passes. */
export function nearestPassing(hex: string): { hex: string; direction: "darker" | "lighter" } | null;
/** A lightened `hex` for the dark theme: the first lightness step at relative luminance >= 0.42. */
export function darkCounterpart(hex: string): string;
```

- Both work in HSL. Convert `#RRGGBB` → HSL with the standard formula; the
  lightness is handled as an **integer percentage** (`round(L × 100)`), so a
  "step" is one percentage point; convert back by rounding each channel to
  the nearest integer and upper-casing the hex. Hue and saturation are kept.
- `nearestPassing`: if `chipText(hex).ratio >= TEXT_FLOOR` return `null`.
  Otherwise walk lightness downward (`darker`) and upward (`lighter`), one
  point at a time, each to the first colour whose `chipText(...).ratio >=
  TEXT_FLOOR`; return the direction that took fewer steps, a tie going to
  `darker`. Lightness clamps at 0 and 100; a direction that reaches the clamp
  without passing is out of the race. Expected (PO, by the formula; RED
  verifies and amends the hex if its rounding differs by one):
  `#808080` → `{ hex: "#858585", direction: "lighter" }` (2 steps up versus
  4 down); `#BD8200` → `null`; `#FFFFFF` → `null`.
- `darkCounterpart`: if `relativeLuminance(hex) >= 0.42` return `hex`
  unchanged; otherwise raise lightness one point at a time and return the
  first colour at or above 0.42. The eleven palette lights are never passed
  here (their pair is known); it serves custom colours only.
- Existing exports are untouched; `chipText`'s rounding and tie rule stand.

### Block 3 - `src/sync/kindActions.ts`

```ts
import type { KindsRepo } from "../data/kinds";
import type { Kind, KindPatch, NewKind } from "../data/rows";
import type { Result } from "../data/result";
import type { KindsStore } from "./kindsStore";
export type KindActions = {
  addKind(input: NewKind): Promise<Result<Kind>>;
  updateKind(kind: Kind, patch: KindPatch): Promise<Result<Kind>>;
  deleteKind(kind: Kind): Promise<Result<Kind>>;
};
export function createKindActions(
  repo: Pick<KindsRepo, "insert" | "update" | "remove">,
  store: Pick<KindsStore, "refresh">,
): KindActions;
/** The app's actions, over `kindsRepo(supabase)` and `kindsStore`. */
export const kindActions: KindActions;
```
- `addKind` → `repo.insert(input)`; `updateKind` → `repo.update(kind.id,
  patch, kind.updatedAt)` (the conditional-update token is the kind's own
  `updatedAt`, byte for byte); `deleteKind` → `repo.remove(kind.id,
  kind.updatedAt)`.
- On `status: "ok"` the action awaits `store.refresh()` **before**
  resolving, so a caller that awaits it sees the new snapshot. On any other
  status nothing is refreshed and the result is returned as is. Nothing
  throws; nothing retries (CAL-015 routes these through the outbox later).

### Block 4 - `src/kinds/KindList.tsx`

```ts
export function KindList(props: { kinds: Kind[]; onEdit: (kind: Kind) => void }): JSX.Element;
```
Markup: `<ul aria-label="Kinds">`, one `<li>` per kind in the order given
(the caller passes `useKinds().kinds`, already in `sort_order`). Inside each
`<li>`, in DOM order:
1. the swatch: `<span aria-hidden="true" class=…swatch style="--swatch-light: {colorLight}; --swatch-dark: {colorDark}">{initial}</span>` — the

   component never asks which theme is on; the swatch's text colour is
   `chipText(colour).text` per theme, set the same way

   code point of the trimmed name, upper-cased (`Array.from(name.trim())[0]`).
2. the name, as visible text in a `<span>`.
3. `<button type="button" aria-label="Edit {name}">Edit</button>` →
   `onEdit(kind)`.
No drag handles or move buttons (PO decision 7, `components.md`). An empty
list renders the `<ul>` with no `<li>`.

### Block 5 - `src/kinds/KindEditor.tsx`

```ts
export function KindEditor(props: {
  open: boolean;
  kind: Kind | null;          // null = "Add kind"
  kinds: Kind[];              // the live kinds, for uniqueness and the palette pick
  onClose: () => void;
  actions?: KindActions;      // default: the app's kindActions
}): JSX.Element;
```
Built on `ui/Dialog` (title `Edit {name}` or `Add kind`); the bottom-sheet
shape on phone is CSS only (`layout.md`).

**Fields, in DOM order:**
- Name: `<label>Name</label>` + `<input type="text" maxLength={32}>`,
  initial value the kind's name or `""`.
- Light colour: `<fieldset role="radiogroup" aria-label="Light theme colour">`
  holding twelve `role="radio"` buttons: one per `DEFAULT_KINDS` entry in
  order, `aria-label` = that entry's name (e.g. `Movies`), `aria-checked`
  when the current light hex equals the entry's `colorLight` (case-
  insensitive), and a twelfth labelled `Custom…`, checked when no palette
  light matches. While `Custom…` is checked, two more controls follow inside
  the fieldset: `<label>Hex</label>` + `<input type="text">` holding the hex,
  and `<input type="color" aria-label="Pick a colour">`.
- Dark colour: the same, `aria-label="Dark theme colour"`, over `colorDark`.
- Preview: one `<p data-preview="light">` and one `<p data-preview="dark">`,
  text exactly `Text contrast {r}:1 · Against background {s}:1` where
  `r = chipText(hex).ratio.toFixed(2)` and `s = contrast(hex, SURFACE_x).toFixed(2)`
  (the surface of that theme). Below each, when `chipText(hex).ratio <
  TEXT_FLOOR`: `<p>` with `Text would be hard to read. Try a {darker|lighter}
  shade.` (direction from `nearestPassing(hex)`), and a
  `<button type="button" aria-label="Fix the {light|dark} colour">Fix it</button>`
  that sets that theme's hex to `nearestPassing(hex).hex`. When text passes
  but `contrast(hex, surface) < SURFACE_FLOOR`: `<p>` `Low contrast against
  the background.` — a warning, Save stays enabled.
- Alert strip: `<div role="alert">` present only after a failed save or
  delete: `Couldn't save. Try again.` (every non-`ok` result, conflict
  included; v1 has no merge UI).
- Actions (Dialog `actions`): `Cancel` (→ `onClose`), `Save`
  (`type="submit"`), and when editing an existing kind
  `<button type="button" data-variant="danger" aria-label="Delete {name}">Delete {name}</button>`
  — `data-variant="danger"` is what `Dialog` skips for initial focus.

**Behaviour:**
- Picking a light palette radio sets the light hex to the entry's
  `colorLight` and, unless the dark side has been edited by hand in this
  editor session (`darkTouched`), sets the dark hex to the same entry's
  `colorDark`. A custom light hex (valid) proposes `darkCounterpart(hex)`
  the same way. Editing anything in the dark group sets `darkTouched`;
  picking a dark radio never changes the light side.
- Hex inputs validate `^#[0-9A-Fa-f]{6}$` on change: invalid → `aria-
  invalid="true"`, message `Enter a colour like #BD8200.` linked by
  `aria-describedby`, Save disabled. The stored value is upper-cased on save.
- Save is `disabled` (the attribute; a form cannot submit it) while: the
  trimmed name is empty, either hex is invalid, or either theme's
  `chipText(hex).ratio < TEXT_FLOOR`. It is **not** disabled for a duplicate
  name: AC-2 is checked on submit.
- Submit: if another **live** kind (not the one being edited) has
  `name.trim().toLowerCase()` equal to the typed one, show `You already have
  a kind called {thatKind.name}.` on the Name field (`aria-invalid="true"`,
  `aria-describedby`), focus it, call nothing. Otherwise: add →
  `actions.addKind({ name: trimmed, colorLight, colorDark, sortOrder: (max
  live sortOrder, or 0) + 1, isDefault: false })`; edit →
  `actions.updateKind(kind, patch)` with only the fields that changed (an
  unchanged kind submits `{}` and still calls `updateKind`). While the
  promise is pending Save carries `aria-busy="true"`. `ok` → `onClose()`;
  anything else → the alert strip, editor stays open.
- Delete: the danger button opens a second `Dialog`, title `Delete the kind
  {name}?`, body `Its events keep their details and show as Kind removed.
  You can't undo this.` (PO decision 2: no event count in v1), actions
  `Cancel` and `Delete` (`data-variant="danger"`). Confirm →
  `actions.deleteKind(kind)`: `ok` → close both dialogs, `onClose()`, and
  `useToast().showToast({ text: "Deleted the kind {name}. Its events now show as Kind removed." })`;
  anything else → close the confirmation, show the alert strip. Cancel
  closes the confirmation and changes nothing.
- "Add kind" preselection: the first `DEFAULT_KINDS` entry whose
  `colorLight` (case-insensitive) is not the `colorLight` of any kind in
  `kinds`; if every entry is used, the first entry. Name empty.
