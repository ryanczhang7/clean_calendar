## Context

EPIC-05. Source: `docs/wiki/audits/epic-05-2026-11-11.md` (Decided 3;
Evidence E-DENO-2, G29 and G41).

CAL-051 pinned the *content* of `geminiResponseSchema`
(`supabase/functions/capture/gemini.ts:24-56`): the proposal's property types
and `nullable`, the confidence properties' type and 0..1 bounds, the
proposal's `required` list, and the nullable mirror of the zod schema. The
re-audit confirms all of that holds (G13, G16, G20, G27, G28, G33 to G35, G40
are killed). Two type tags the model is held to are still unpinned, and each
of these mutants leaves all 282 Deno tests green:

- **G41**: `gemini.ts:47`, the `confidence` object's `type: "OBJECT"` →
  `"ARRAY"`. The model would be told confidence is an array.
  `geminiReplySchema` (`shared/captureSchema.ts`) requires an object, so a
  model that obeyed would get every capture answered 502 `unreadable`. If
  Gemini instead refused the contradictory schema (an `ARRAY` with
  `properties`), every capture would be answered 502 `upstream 400`. Which of
  the two happens was not measured.
- **G29**: `gemini.ts:52`, the `missing` array's `items: { type: "STRING",
  enum: FIELDS }` → `type: "NUMBER"`. A NUMBER with a string enum. The same
  two outcomes: numbers that zod refuses, or a schema Gemini refuses.

Neither is a defect today. The schema as shipped is right. What is missing
is the test that fails when someone edits it wrong. The existing test at
`gemini_test.ts:112` asserts `missing.type` is `array` and the enum's
members, and does not read `items.type`. Nothing reads `confidence.type`.

Test-only: the shipped schema is believed right, so each new assertion passes
on arrival and is earned by its mutant.

Required gate that would fail if this broke: `deno-test`.
