## Context

EPIC-01. Found by CAL-038's AC-1 measurement (CAL-038 `## Notes`, "AC-1 and
AC-4 measured"; `## Amendments`). `src/auth/SignInPage.test.tsx` was run 200
times, each run alongside three looping full `vitest run --project unit`
suites (four concurrent vitest processes, 12 cores). Under that load,
"arriving signed in as the owner (AC-3) › renders the remembered path instead
of the card" failed 1 of 200 on `main` 01d3787 and 4 of 200 with CAL-038's
change. CAL-038 touches neither the test nor the code it exercises. The
failure:

    TestingLibraryElementError: Unable to find role="heading" and name "Event kinds"
    <body><div /></body>
     ❯ waitForWrapper .../@testing-library/dom/dist/wait-for.js:163:27

The run took 1008-1042 ms, which is `findByRole`'s default 1 s timeout, and
the body was still empty: nothing had rendered yet, not even the card. It is
the first test in its describe and the first owner path in the file. On
`/signin` with a session, the router has to resolve the session, run
`RequireOwner`'s kinds seed through MSW, and load `/kinds`. **Cause not
established.** Do not assume it is the CAL-038 race: different symptom,
different code.

Required gates that would fail: `unit` and `coverage`.

## Acceptance criteria

- **AC-1** — Given the load CAL-038 used (four concurrent `pnpm exec vitest
  run --project unit` processes), when `src/auth/SignInPage.test.tsx` runs 200
  times, then "renders the remembered path instead of the card" passes every
  time. The baseline failure count out of 200 is measured and recorded first.
- **AC-2** — The test still detects the defect it exists for: with the
  remembered path ignored (`takeReturnTo()` returning `/`), it fails on every
  run.

### Cause measured (PLANNED, 2026-11-06, lead-po orchestrator, Fable 5.1)

measurement; classifies as `test`) mirrored this file's harness exactly -
the same `vi.mock` of supabase, `installServer()`, `beforeEach`, first case

`cc.returnTo = /kinds`, waiting up to 15 s so late runs were measured, not
cut off. Each run is a fresh `vitest run` process (as the real failure is).

concurrent vitest processes, 12 cores), the CAL-038 method. Milliseconds from
the test's start:

    unloaded, warm:    <h1> in the DOM ~62, heading found ~119-129, one getByRole ~4

Reading: the app reaches the right page in 400 of 400; it is late in two
ways - the rare tail before anything paints (run 1's 4 of 200 over 1 s,
matching CAL-038's empty `<body>` and its 1-4 in 200), and the larger, more
common lag between the `<h1>` existing and `findByRole` observing it, since
under load a role query is expensive and polling timers starve. The probe's
"found" time includes Testing Library's post-resolution drain (a 0 ms
timeout, delayed under load), which is why 53-72 of 200 over 1 s here is far
more than the real case's 1-4 in 200: the probe overstates the query lag,
not the render. **Cause, as far as this evidence goes: load-induced
slowness, never a wrong render.** Raw logs (not in the tree): the session
scratchpad's `cal046-probe.jsonl` and `cal046-probe2.jsonl`.

  evidence; the user answered "Yes, raise the timeout". The change is the
  narrowest that covers the measured case: one `findByRole`, 4,000 ms, the
  one case CAL-038 saw fail (Contract Block 2). Not a criterion change.
