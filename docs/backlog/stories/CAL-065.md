## Context

EPIC-04, from `docs/wiki/audits/epic-04-2026-11-06.md` (Decided 6;
Evidence E-STRYKER `src/sync/drain.ts`, E-HAND D11 and RQ1).

Two pass-level rules of the drain survive the whole unit project:

- **The announcement belongs to one pass** (`drain.ts:320`). `run({
  announce: true })` sets a flag that the shared pass's `finally` resets.
  Drop the reset (D11), or set it to `true` (Stryker `:320:22`), and after
  the first announced pass, which is every reconnection and every sign-in
  (`startSync`), **every later pass** announces too. Each edit made online
  would then toast "Back online. 1 change synced." Under D11 the whole unit
  project passes 2999 of 3000, and the one failure is a `noSecrets.test.ts`
  timeout (E-FLAKE). Each announce case in the suite uses a fresh drain, so
  none runs an unannounced pass after an announced one.
- **A reminder's undo survives a conflict** (`:236`). CAL-044 AC-1
  re-queues a `restore` whose re-fetched row is deleted, for events and
  reminders. Only the events half is tested. With the condition reduced to
  `table === "events"` (RQ1), and under Stryker's three mutants of `table
  === "reminders"`, the whole unit project passes 3000 of 3000. A reminder
  the owner brought back with Undo is then dropped without a notice when the
  other device has re-stamped it.

Test-only: the shipped drain is believed correct, so each new assertion
passes on arrival and is earned by the mutant its criterion names.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given a drain that has run one announced pass which sent an
  op, when another op is queued and `run()` is called **without**
  `announce`, then that pass sends it and emits no `drained` notice. A test
  fails when the reset `announce = false` at `drain.ts:320` is removed
  (audit D11) and when it sets `true` (`:320:22`).
- **AC-2** - Given a queued reminders `restore` op whose conditional restore
  matches zero rows and whose re-fetched reminder is **deleted** (re-stamped
  by the other device), when the drain runs, then the restore is queued
  again over the fresh row, the cached reminder is live, no notice is
  emitted, and the same pass sends the re-queued restore. A test fails when
  `:236` is `table === "events"` (audit RQ1), and when its `table ===
  "reminders"` is `false`, `!==` or compares with `""`.
