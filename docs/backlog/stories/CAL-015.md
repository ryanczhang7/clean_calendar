## Context

EPIC-04, brief §4.4 and success criterion 3: "nothing is lost after an
offline edit". `architecture.md`, "Where state lives": every create, update
and delete is written to the cache optimistically **and** appended to an
outbox, which drains in order while online. The conflict rule is fixed there:
last writer wins per row, decided by the server through the conditional update
of CAL-005; a lost local edit is reported with a toast and a Redo, deletes win
over edits. This story moves `eventActions` (CAL-012/013) and `kindActions`
(CAL-007) onto the outbox behind their existing signatures and fills the
sync status indicator (`components.md`, "Sync status indicator"; copy
`voice.md`).

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given the network is down, when an event is created, edited or
  deleted, then the cache reflects it at once, the outbox holds one op per
  action in order (`{op, table, id, patch, baseUpdatedAt, clientTs}`), and the
  chip's name ends ", saving" with a dashed outline.
- **AC-2** - Given ops in the outbox, when the network returns, then they are
  sent in order, each removed after the server accepts it, the cache row takes
  the server's `updated_at`, and the toast "Back online. {n} changes synced."
  is shown.
- **AC-3** - Given an op whose conditional update matches zero rows (server
  copy newer), when it drains, then the client re-fetches the row, replaces its
  cache copy, drops the op, and shows an alert toast "Edited elsewhere; your
  change to {field} was not applied." with "Redo" (several fields: "your
  changes to title and location were not applied."); Redo reapplies the
  dropped patch over the fresh row as a new op.
- **AC-4** - Given a delete op and an edit op for the same row from different
  devices, when both reach the server in either order, then the row ends
  deleted (the edit after a delete is dropped without a toast).
- **AC-5** - Given an op refused with a 4xx other than a conflict, when it
  drains, then it stays in the outbox marked failed, later ops still drain,
  the chip shows the danger ring with a "!" and its name ends ", not synced",
  and the toast "{title} couldn't sync." offers "Retry"; Discard removes the op
  and restores the server copy.
- **AC-6** - Given a 5xx or a network error, when an op drains, then it stays
  queued, unmarked, and is retried when the network next returns.
- **AC-7** - Given each state, when the sync status renders, then it is a
  `role="status"` element labelled "Synced", "Syncing {n} changes" ("Syncing
  1 change"), "Offline — changes will sync later" or "{n} changes couldn't
  sync" (`voice.md`), with a distinct glyph per state.

### Block 2 - `src/sync/outbox.ts` (the optimistic write)

```ts
export type Repos = { events: EventsRepo; kinds: KindsRepo };   // the Picks each block needs are named there
export function newId(): string;                                  // crypto.randomUUID()
export function nowTs(): string;                                  // new Date().toISOString()
/** Writes the cache row and queues the op in one Dexie transaction, returns the cache row as it now is. */
export function enqueueInsert(db: CalendarDb, table: "events", input: NewEvent): Promise<Event>;
export function enqueueInsert(db: CalendarDb, table: "kinds", input: NewKind): Promise<Kind>;
export function enqueueUpdate(db: CalendarDb, table: "events", id: string, patch: EventPatch): Promise<Event | null>;
export function enqueueUpdate(db: CalendarDb, table: "kinds", id: string, patch: KindPatch): Promise<Kind | null>;
export function enqueueDelete(db: CalendarDb, table: "events" | "kinds", id: string): Promise<Event | Kind | null>;
export function enqueueRestore(db: CalendarDb, table: "events" | "kinds", id: string): Promise<Event | Kind | null>;
export function retryOp(db: CalendarDb, seq: number): Promise<void>;      // failed → queued, error cleared
export function discardOp(db: CalendarDb, seq: number, repos: Repos): Promise<void>;  // Block 4 says what it restores
export function queuedCount(db: CalendarDb): Promise<number>;
export function failedCount(db: CalendarDb): Promise<number>;
```

- **insert**: `id = newId()`, cache row = input + `{ id, createdAt: ts,
  updatedAt: ts, deletedAt: null }` with `ts = nowTs()`; op `{ op: "insert",
  id, patch: input, baseUpdatedAt: null, clientTs: ts, status: "queued" }`.
- **update**: the patch is applied to the cache row's fields; **`updatedAt`
  is not touched** - it stays the last stamp the server gave, which is what
  the drain sends as the conditional token (Block 3). Op `baseUpdatedAt` =
  that stamp. A missing cache row → `null`, nothing queued.
- **delete**: cache row `deletedAt = ts` (it leaves every view at once;
  CAL-013's `hide` is no longer needed on this path); op `patch: null`.
- **restore**: cache row `deletedAt = null`; op `"restore"`.
- Each queues **one op per action, in `seq` order** (AC-1); nothing
  coalesces.

### Block 3 - `src/sync/drain.ts`

```ts
export type DrainNotice =
  | { kind: "drained"; count: number }                                   // AC-2 toast, announce passes only
  | { kind: "conflict"; table; id: string; title: string; fields: string[]; patch: unknown; freshUpdatedAt: string }  // AC-3
  | { kind: "failed"; seq: number; table; id: string; title: string; error: { code; message; http? } }              // AC-5
  | { kind: "changed" };                                                 // the outbox changed (counts to re-read)
export type Drain = {
  /** One pass over the queued ops in seq order; concurrent calls share a pass. */
  run(opts?: { announce?: boolean }): Promise<{ sent: number; stoppedAt: "end" | "offline" | "server" }>;
  subscribe(listener: (n: DrainNotice) => void): () => void;
};
export function createDrain(db: CalendarDb, repos: Repos, online?: () => boolean): Drain;   // default () => navigator.onLine
```

Per op, in `seq` order, skipping `status: "failed"` ops:
- **Token.** For update, delete and restore the conditional token is the
  cache row's **current** `updatedAt` (the latest server stamp known, since
  optimistic writes never change it; a previous op in this pass has already
  written the server's new one), falling back to `op.baseUpdatedAt` when the
  cache row is gone. For insert: `repo.insert(patch, op.id)`.
- **ok** → the cache row takes the server row's `updatedAt`, `createdAt` and
  `deletedAt` only (`db.<table>.update(id, …)`), so later queued patches on
  the row stay visible; the op is deleted; `sent++`.
- **conflict** (zero rows) → `repo.get(id)`:
  - server row `deletedAt !== null` → cache row replaced by it, op dropped,
    **no notice** (AC-4: an edit after a delete);
  - server row live and the op is a **delete** → cache row replaced by it,
    then `enqueueDelete` again (deletes win, AC-4) - no notice;
  - server row live, any other op → cache row replaced by it, op dropped,
    notice `conflict` with `fields = fieldNames(table, patch)` and the fresh
    stamp (AC-3). Later queued ops for the same row stay queued and drain
    against the fresh stamp (their patches reappear when they land; a known
    limit, `## Notes`).
  - `get` itself not ok → treated as the failure below.
- **error with `http` in 400-499** → `status: "failed"`, `error` stored,
  notice `failed`, the pass **continues** (AC-5 "later ops still drain").
- **error otherwise (5xx, no `http`), or offline** → the op stays `queued`
  untouched and the pass **stops** (`stoppedAt: "server" | "offline"`), so
  order is kept (AC-6). Nothing throws.
- When `online()` is false at the start, the pass returns at once.
- After a pass with `announce: true` and `sent > 0`: notice `drained`
  (AC-2's toast). A pass started by an enqueue while online announces
  nothing.

```ts
/** Plain field names, voice.md: title, kind, start time, end time, all day, location, notes, repeat; kinds: name, colour, order. */
export function fieldNames(table: "events" | "kinds", patch: unknown): string[];
/** "Edited elsewhere; your change to title was not applied." / "…your changes to title and location were not applied." / "a, b and c". */
export function conflictCopy(fields: string[]): string;
```
"all day" and the kind field names are added to `voice.md`'s list by this
story (PO decision 8, a docs write). `patch` keys never in a UI patch
(`origin`, `captureJobId`) map to their own key.

> **RED amendments, 2026-10-21** (each pinned by `drain.test.ts`):
> - **The pass loop.** A pass repeatedly takes the queued op with the lowest
>   `seq` greater than the last one it handled, until there is none. So an op
>   enqueued while a pass is in flight is sent by that pass - otherwise the
>   `void drain.run()` after an enqueue joins the in-flight pass (concurrent
>   calls share it) and the new op waits for the next `online` event - and a
>   conflicted delete that the pass re-queues is sent in the same pass, over
>   the fresh stamp (the AC-4 case expects `remove` twice: `[id, T1]`, then
>   `[id, S9]`).
> - `sent` counts ops the server accepted; a conflicted op is not sent. A pass
>   that finds `online()` false returns `{ sent: 0, stoppedAt: "offline" }`;
>   an empty outbox `{ sent: 0, stoppedAt: "end" }`.
> - A `get` that answers `offline` leaves the op queued and untouched and
>   stops the pass with `stoppedAt: "offline"`. (A `get` answering `conflict`
>   or an error is not pinned.)
> - Notices: `table` is `"events" | "kinds"`. The conflict notice's `title`
>   is the **fresh server row's** title (a kind: its name); the failed
>   notice's `title` is the **cache row's** title at the time (the optimistic
>   one - "{title} couldn't sync." names what the user typed). A pass that
>   changed the outbox emits at least one `{ kind: "changed" }`.
> - `fieldNames` returns names in **voice.md's order**, whatever the patch's
>   key order: events title, kind, start time, end time, all day, location,
>   notes, repeat; kinds name, colour, order. `colorLight` and `colorDark` are
>   one field, "colour", named once. Any other key (`origin`, `captureJobId`,
>   `isDefault`) follows, as itself, in patch key order.

### Block 4 - retry, discard and the actions

- `retryOp(seq)`: `status: "queued"`, `error` removed, then one `run()`
  when online.
- `discardOp(seq, repos)`: the op is deleted; for an **insert** the cache
  row is deleted too; otherwise `repos.<table>.get(id)` and the server row
  replaces the cache row (AC-5 "restores the server copy"); a `get` that is
  not ok leaves the cache row as it is.

```ts
// src/sync/eventActions.ts
export function createOutboxEventActions(db: CalendarDb, drain: Pick<Drain, "run">, online?: () => boolean): EventActions;
export const eventActions: EventActions;   // now createOutboxEventActions(db, appDrain)
// src/sync/kindActions.ts
export function createOutboxKindActions(db: CalendarDb, drain: Pick<Drain, "run">, online?: () => boolean): KindActions;
export const kindActions: KindActions;
```
`createEvent(input)` → `enqueueInsert`, resolves `{ status: "ok", row }`;
`updateEvent(id, patch, expectedUpdatedAt)` → `enqueueUpdate` (the
caller's `expectedUpdatedAt` is **ignored**: the cache's stamp is the token,
Block 3; `null` row → `{ status: "conflict" }`); `removeEvent(event)` →
`enqueueDelete`; `restoreEvent(deleted)` → `enqueueRestore`. Kinds likewise
(`deleteKind` → delete; no restore). After each enqueue, when `online()`,
`void drain.run()` (not awaited, not announced). The in-memory factories are
untouched.

### PO decisions at PLANNED → RED (2026-10-21, lead-po)

1. **Outbox actions beside the online ones.** The singletons `eventActions`
   and `kindActions` become outbox actions behind the same types; the
   in-memory factories `createEventActions` / `createKindActions` stay as
   shipped, so `CalendarPage.test.tsx`, `KindsPage.test.tsx`,
   `WalkthroughPage.test.tsx` and the CAL-007/012/013 action suites change
   nothing. CAL-014's pattern.
2. **The client names new rows.** An optimistic insert needs an id before
   the server answers, so `enqueueInsert` generates a uuid
   (`crypto.randomUUID()`) and the repository's `insert` forwards it; the
   schema's `default gen_random_uuid()` accepts a supplied id.
3. **The cache row's `updatedAt` is the server's, always.** Optimistic
   updates never touch it, so it is the right conditional token whenever an
   op is sent, and a second op on the same row needs no rewriting after the
   first lands. The `expectedUpdatedAt` callers pass to `updateEvent` is
   ignored by the outbox actions: a page that undoes a move passes the token
   of a row the server may already have re-stamped, and honouring it would
   turn every online undo into a false "Edited elsewhere".
4. **4xx is told from 5xx by the HTTP status**, which `Result` dropped
   until now; `Failure.error` gains an optional `http`. A fake that omits it
   is treated as retryable (queued), never as failed.
5. **Deletes win, both ways.** Our edit against their delete: the re-fetched
   row is deleted → the op is dropped silently and the row leaves the views.
   Our delete against their newer edit: the delete is queued again over the
   fresh row. `architecture.md`'s rule, made mechanical.
6. **Drain before hydrate, and hydrate skips rows with pending ops.**
   Otherwise `startSync`'s pull overwrites an optimistic patch with the
   server's older copy, and the edit reappears only when its op lands.
7. **The toasts are shown by `SyncStatus`**, which sits inside
   `ToastProvider` in the shell and subscribes to the drain's notices; the
   drain itself knows nothing of React. "Back online. {n} changes synced." is
   announced only by a pass the `online` event or `startSync` started, never
   by the immediate send after an enqueue while online.
8. **Copy added to `voice.md`** (a docs write): "all day" joins the field
   list (AC-3's `{field}` has no name for `allDay` there), and the kind
   fields "name", "colour", "order". Serial comma style follows the existing
   "title and location" example: "a, b and c".
9. **Discard lives in the status indicator's dialog**, not in the sheet.
   AC-5 pins what Discard does, not where it is; `components.md` puts
   Retry / Discard in the indicator's popover and also in the sheet. The
   sheet's error line is a follow-up (filed when this closes), so this story
   does not touch `EventSheet.tsx`.
10. **A 5xx stops the pass; a 4xx does not.** AC-6 says a 5xx op "stays
    queued" and AC-2 says ops are sent in order, so a 5xx must hold the ops
    behind it; AC-5 says later ops still drain past a failed one.
11. **Kinds get no chip marker.** AC-1's marker is the event chip's; kind
    ops still count in the status indicator and take the same conflict and
    failure paths.
12. **Known limit, not fixed here.** After a conflict drops one op, later
    queued ops for the same row keep their patches in the outbox but the
    cache row shows the server copy until they land. One user on two devices
    rarely queues two edits of one row across a conflict; recorded, not
    built around.
13. **Epic done-when checked.** Airplane-mode edits accepted and on the
    server within seconds of reconnecting, and a conflicting edit resolving
    to the server's copy with a notice: this story. The other device seeing
    it without a reload: CAL-016. Install: CAL-017. No gap.
14. **Required gate: `unit`** (`covers | unit | src/**`, required). The
