## Context

EPIC-04, brief §4.4 and success criterion 3: "nothing is lost after an
offline edit". `architecture.md`, "Where state lives": every create, update
and delete is written to the cache optimistically **and** appended to an
outbox, which drains in order while online. The conflict rule is fixed there:
last writer wins per row, decided by the server through the conditional update
of CAL-005; a lost local edit is reported with a toast and a Redo, deletes win
over edits. This story moves `eventActions` (CAL-012/013) and `kindActions`
(CAL-007) onto the outbox behind their existing signatures and fills the
sync status indicator (`components.md`, "Sync status indicator"; copy
`voice.md`).

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given the network is down, when an event is created, edited or
  deleted, then the cache reflects it at once, the outbox holds one op per
  action in order (`{op, table, id, patch, baseUpdatedAt, clientTs}`), and the
  chip's name ends ", saving" with a dashed outline.
- **AC-2** - Given ops in the outbox, when the network returns, then they are
  sent in order, each removed after the server accepts it, the cache row takes
  the server's `updated_at`, and the toast "Back online. {n} changes synced."
  is shown.
- **AC-3** - Given an op whose conditional update matches zero rows (server
  copy newer), when it drains, then the client re-fetches the row, replaces its
  cache copy, drops the op, and shows an alert toast "Edited elsewhere; your
  change to {field} was not applied." with "Redo" (several fields: "your
  changes to title and location were not applied."); Redo reapplies the
  dropped patch over the fresh row as a new op.
- **AC-4** - Given a delete op and an edit op for the same row from different
  devices, when both reach the server in either order, then the row ends
  deleted (the edit after a delete is dropped without a toast).
- **AC-5** - Given an op refused with a 4xx other than a conflict, when it
  drains, then it stays in the outbox marked failed, later ops still drain,
  the chip shows the danger ring with a "!" and its name ends ", not synced",
  and the toast "{title} couldn't sync." offers "Retry"; Discard removes the op
  and restores the server copy.
- **AC-6** - Given a 5xx or a network error, when an op drains, then it stays
  queued, unmarked, and is retried when the network next returns.
- **AC-7** - Given each state, when the sync status renders, then it is a
  `role="status"` element labelled "Synced", "Syncing {n} changes" ("Syncing
  1 change"), "Offline — changes will sync later" or "{n} changes couldn't
  sync" (`voice.md`), with a distinct glyph per state.
