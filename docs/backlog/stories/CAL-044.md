## Context

Filed when CAL-015 closed (its GREEN report, "for review"; `## Notes`, PO note
at GREEN, follow-up 1). CAL-015's drain, Block 3, handles a conditional write
that matched zero rows by re-fetching the row and, when the server copy is
**deleted**, dropping the op silently - the "an edit after a delete is dropped
without a toast" rule of AC-4. Read literally, that rule also swallows a
`restore` op: the owner deletes an event, presses Undo, and the restore's
conditional update misses because the other device re-stamped the row in the
meantime. The re-fetched row is deleted (that is what a restore is for), so the
drain drops the restore - and the undo is lost with no notice. Deletes winning
over *edits* was never meant to beat the owner's own undo of a delete.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given a queued `restore` op whose conditional update matches
  zero rows, when the re-fetched server row is deleted, then the restore is
  queued again over the fresh row (as a conflicted `delete` is over a live
  row), the cache row is live, and no notice is emitted. A test fails when the
  drain's conflict branch drops a restore the way it drops an edit.
- **AC-2** - Given a queued `restore` op whose re-fetched server row is
  **live** (another device restored it first), when it drains, then the op is
  dropped without a notice and the cache row takes the server copy. A test
  fails when a notice is emitted or the op stays queued.
- **AC-3** - Given an `update` op whose re-fetched row is deleted, when it
  drains, then CAL-015's behaviour is unchanged: dropped, no notice, the row
  leaves the views. A test fails when the restore rule leaks onto edits.

## Contract

**Writes:** `src/sync/drain.ts` (source), `src/sync/drain.test.ts` (test).
RED writes the test; GREEN changes the drain. RED may amend a block in

**Block 1 - the rule, as `drain.ts`'s header comment will state it.** On a
conflict (the conditional write matched zero rows) the drain re-fetches the
row with `repo.get(id)`; today (`drain.ts:206-241`):

| our op | fresh row | today | after this story |
|---|---|---|---|
| `update` / `insert` | deleted | replaced, dropped, silent | **unchanged** (AC-3) |
| `update` / `insert` | live | replaced, dropped, `conflict` notice | unchanged |
| `delete` | live | replaced, delete queued again, silent | unchanged |
| `delete` | deleted | replaced, dropped, silent | unchanged |
| **`restore`** | **deleted** | replaced, dropped, silent - **the undo is lost** | **replaced, restore queued again over the fresh row, the cache row live, silent** (AC-1) |
| **`restore`** | **live** | replaced, dropped, **`conflict` notice** | **replaced, dropped, silent** (AC-2) |

So there are two behaviour changes, and both are in the conflict branch:

1. A conflicted `restore` whose fresh row is deleted is queued again, as a
   conflicted `delete` over a live row is (`:221-224`): inside the same
   transaction, after `rows.put(row)` and `db.outbox.delete(op.seq)`, call
   `enqueueRestore(db, table, op.id)` (`outbox.ts`, already exported; it
   rewrites the cache row to `deletedAt: null` and appends a `restore` op
   whose `baseUpdatedAt` is the fresh row's `updatedAt`). Restore exists
   only for `events` and `reminders` (`DeletableTable` minus kinds, whose
   repo has no `restore`); GREEN narrows `table` accordingly - an
   `event_overrides` or `kinds` restore op cannot be queued, so the guard
   only has to type-check, not to be reachable.
2. A conflicted `restore` whose fresh row is live emits **no** notice: the
   owner asked for the row back and it is back. Today the notice condition
   is `isLive(row) && op.op !== "delete"` (`:226`), which lets a restore
   through; it becomes "and not a restore either".

The re-queued restore is sent again by the same pass (the pass takes any op
queued above the last seq it handled, `:12-14`), exactly as the re-queued
delete is.

**Block 2 - the harness, unchanged.** `drain.test.ts:51-108`: a real
`CalendarDb` over fake-indexeddb (`freshDb()`), `fakeRepos()` (`vi.fn`
repositories; `repos.events.restore`, `.get`, `.update`, `.remove`),
`createDrain(db, asRepos(repos), () => online)`, `notices` collected by
`drain.subscribe`, `ROW`/`OTHER` (events, `updatedAt: T1`), `server(row,
extra)` (the server's copy: `createdAt: SERVER_CREATED`, `updatedAt: S1`),
`okRow`, `of(kind)`, `opsWithoutSeq(db)`, the stamps `T1`, `S1`..`S9`,
`SERVER_DELETED`, `NOW_TS`. Import `enqueueRestore` from `./outbox` beside
`enqueueDelete`. The neighbours to mirror are "a delete that conflicts with
a newer live row is queued again over the fresh row" (`:511`) and "the
re-queued delete, while it waits, keeps the row out of the views and
records the fresh stamp" (`:536`). Add a new `describe` beside "deletes win
over edits"; do not edit existing cases.

**Block 3 - the cases.** All MECHANICAL: which repo member is called with
which token, what the cache and the outbox hold, which notices arrived.

- **AC-1 (a), the restore goes again and lands.** Cache: `ROW` deleted
  (`deletedAt: T1`-era stamp, `updatedAt: T1`). `enqueueRestore(db,
  "events", ROW.id)`. `repos.events.restore` → `conflict` once, then
  `okRow(finalRow)` where `finalRow = server(ROW, { deletedAt: null,
  updatedAt: S3 })`. `repos.events.get` → `okRow(theirs)` where `theirs =
  server(ROW, { deletedAt: SERVER_DELETED, updatedAt: S9 })` (the other
  device re-stamped the deleted row). After `drain.run()`:
  `repos.events.restore.mock.calls` is `[[ROW.id, T1], [ROW.id, S9]]`;
  `repos.events.get.mock.calls` is `[[ROW.id]]`; the cache row is
  `finalRow`; the outbox is empty; `notices` is `[]`.
- **AC-1 (b), while it waits.** The same, but the second `restore` →
  `{ status: "offline" }`: `drain.run()` resolves `{ sent: 0, stoppedAt:
  "offline" }`; `opsWithoutSeq(db)` is exactly one `{ op: "restore",
  table: "events", id: ROW.id, patch: null, baseUpdatedAt: S9, clientTs:
  NOW_TS, status: "queued" }`; the cache row is `theirs` with `deletedAt:
  null` (live, carrying the fresh stamp); `notices` is `[]`.
- **AC-2, another device restored it first.** `restore` → `conflict`;
  `get` → `okRow(server(ROW, { deletedAt: null, updatedAt: S9 }))`. After
  the run: `restore` called once; the cache row is that live server copy;
  the outbox is empty; `of("conflict")` is `[]` **and** `notices` is `[]`.
  Not vacuous: put a second, ordinary conflicted `update` on `OTHER` in the
  same pass (fresh row live) and assert its notice does arrive, so the
  subscriber was listening (the pattern of `:505-507`).
- **AC-3, edits after a delete are unchanged.** The existing case at `:489`
  ("an edit that reaches the server after a delete is dropped without a
  notice, and the row ends deleted") is the pin; RED adds no duplicate,
  and names it in the Test plan. Deferred verification 2 earns it against
  a leak.

**Expected RED.** Against the shipped drain: AC-1 (a) fails (`restore`
called once, the cache row stays `theirs` deleted, outbox empty); AC-1 (b)
fails (no op queued, `run()` resolves with `stoppedAt` absent or different);
AC-2 fails on `notices` (one `conflict` notice for `ROW`). AC-3's existing
case stays green.

**Oracle partition.** All mechanical; the stamps are the fixtures'.

**Callers of changed signatures.** None. No export changes; `drain.ts`
gains a run-time import of `enqueueRestore`, which `outbox.ts` already
exports (`outbox.ts:256-284`).

**Test command.** `pnpm exec vitest run --project unit src/sync/drain.test.ts`.
The whole unit project is 2968 on arrival (`main` at `2e45ece`).
