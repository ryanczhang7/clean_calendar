## Context

EPIC-06 (recurring events). An occurrence is an `Event` carrying the SERIES id
plus its `occurrenceDate` (`src/sync/useOccurrences.ts`, CAL-024), so the id
alone does not identify a chip. When one series has two occurrences visible on
the same day - a daily 23:00-01:00 series, whose previous occurrence runs into
today - the week/day time grid and the page's focus code still use the id
alone, and treat the two as one:

- `src/calendar/TimeGrid.tsx:142` resolves each block's event with
  `events.find((e) => e.id === c.id) ?? c`, the first match by id. Both blocks
  therefore render, open, move and delete the EARLIER occurrence. Measured by
  CAL-058's RED with a throwaway probe (both chips' sheets read
  `2026-11-02 23:00`; CAL-058 `## Handoff`, "Discovered").
- Both chips carry the same `data-event-id` (`src/calendar/EventChip.tsx:217`
  and `:251`), and `src/calendar/CalendarPage.tsx` finds a chip with
  `document.querySelector('[data-event-id="<id>"]')` - the first in the
  document - in `focusChip` (`:214`, after a keyboard move) and in
  `useOpenEventFromQuery` (`:524`, the opener a deep-linked sheet returns
  focus to). CAL-058 `## Diff review`, Review 1, finding 3. Read from the code,
  not yet observed in a test.

This is a `fix`: every criterion below reproduces the defect, RED watches each
one fail against today's code, and those tests stay as the regression tests.
The evidence quoted above is CAL-058's and is to be re-observed in RED, not
assumed.

The required gate that fails if this breaks is `unit` (and `coverage`, the same
suite instrumented): the tests are jsdom component tests beside the existing
ones. No optional gate carries a criterion, so `required_gates` stays empty.

## Acceptance criteria

All five share one fixture, Contract Block 1: the daily series **Night**
(23:00-01:00, first occurrence 1 November 2026, the device's zone), whose
occurrence dated 2 November carries an override titling it **Late shift**, on
the day view of 3 November 2026. That day shows two chips of the one series:
the 2 November occurrence running in from the night before (00:00-01:00) and
the 3 November occurrence (23:00-24:00).

- **AC-1** — Given the fixture, when the day view of 3 November is shown, then
  the block at 00:00 is a chip named "Late shift, ..." and the block at 23:00
  is a chip named "Night, ..." - one of each. (Today both blocks are named
  "Late shift, ...".)
- **AC-2** — Given the fixture, when the owner activates the 23:00 chip, then
  the event sheet opens titled "Night" with start 2026-11-03 23:00 and end
  2026-11-04 01:00; and when the owner instead activates the 00:00 chip, then
  it opens titled "Late shift" with start 2026-11-02 23:00 and end 2026-11-03
  01:00. (Today either chip opens the 2 November occurrence.)
- **AC-3** — Given the fixture, when the owner presses Delete on the 23:00 chip
  and confirms "This event only", then the occurrence cancelled is the one
  dated 2026-11-03: the "Night" chip is gone and the "Late shift" chip is still
  shown. (Today the 2 November occurrence is cancelled instead.)
- **AC-4** — Given the fixture, when the owner moves the 23:00 chip with
  Alt+ArrowDown and confirms "This event only", then the new times are written
  for the occurrence dated 2026-11-03, the "Late shift" chip keeps its times,
  and keyboard focus is on the moved "Night" chip. (Today the 2 November
  occurrence is moved, and focus goes to the first chip of the series in the
  document.)
- **AC-5** — Given the fixture, when `/day/2026-11-03?event={series id}` is
  opened and the sheet it opens (the 3 November occurrence, CAL-058 AC-3) is
  closed, then keyboard focus is on the "Night" chip at 23:00, not on the
  "Late shift" chip. (Today focus returns to the first chip of the series in
  the document, the "Late shift" one.)

## Contract

RED may amend any block, in place, with a reason; GREEN builds what the amended
block says.

**Writes:** `src/calendar/TimeGrid.tsx`, `src/calendar/EventChip.tsx`, `src/calendar/CalendarPage.tsx`, `src/calendar/TimeGrid.test.tsx`, `src/calendar/EventChip.test.tsx`, `src/calendar/CalendarPage.test.tsx`

**Block 1 - the fixture (settled; read it out).** The series is the one
CAL-058's tie-break test already builds (`src/calendar/CalendarPage.test.tsx`,
"of two occurrences on the day (one running in from the night before)"):
`timed("Night", nov(1, 23), nov(2, 1))` with
`recurrence: { freq: "daily", until: null, tz: DEVICE_TZ }`. Add one override
row for `occurrenceDate: "2026-11-02"` setting `title: "Late shift"` and
nothing else. The override exists for one reason: without it the two chips have
the SAME accessible name (`chipName` carries the time, 23:00 to 01:00, and no
date), and a test could tell them apart only by document order - which is the
very thing the defect gets wrong. With it, a
`getByRole("button", { name: /^Night, / })` cannot match the sibling. On
`/day/2026-11-03` the 2 November occurrence is clipped to 00:00-01:00 and the
3 November one to 23:00-24:00; a chip's label always carries its occurrence's
real, unclipped times (existing behaviour, and the purpose of the lookup at
`TimeGrid.tsx:142` - keep it).

**Block 2 - occurrence identity is `chipKey`.** `chipKey(event: Event): string`
in `src/sync/useOccurrences.ts`, unchanged: the id for a plain event,
`<id>@<occurrenceDate>` for an occurrence. It is already every chip's React
key (`TimeGrid.tsx:250`, `:307`; `MonthView.tsx:281`; `DayList.tsx:33`). This
story introduces no second identity scheme.

**Block 3 - markup.** `EventChip` puts `data-chip-key={chipKey(event)}` on its
`<button>`, in both variants (`EventChip.tsx:217` block, `:251` chip).
`data-event-id` stays exactly as it is - the series id: `e2e/a11y.spec.ts` and
the tests in `CalendarPage.test.tsx`, `EventChip.test.tsx`,
`MonthView.test.tsx` and `TimeGrid.test.tsx` read it, and
`useFocusEventFromState` still needs it (Block 5). No role, label or tab order
changes. `EventChip`'s props do not change.

**Block 4 - the time grid.** Each block in `TimeGrid`'s `columns` carries the
occurrence it was clipped from, not the first event sharing its id. Everything
the block hands that event to follows: the chip's label, `chips.onActivate`,
`onChipCommand`, `drag.chipProps`. How (an index, a map by `chipKey`, carrying
the original beside the clip) is GREEN's choice.

**Block 5 - focus in `CalendarPage.tsx`.**
- `focusChip` (private, `:212`; callers `:280` and `:348`) finds the chip by
  `data-chip-key`, given `chipKey(event)`. After a "This event only" move the
  override is keyed by the ORIGINAL occurrence date (architecture,
  `event_overrides`), so the key is the same before and after the move.
- `useOpenEventFromQuery` (`:524`) passes as opener the chip whose
  `data-chip-key` is `chipKey(event)` for the occurrence it opens. The id is
  already UUID-validated (CAL-058 Block 2) and an occurrence date is
  `yyyy-MM-dd`, so the key is safe inside a quoted attribute selector.
- `useFocusEventFromState` (`:439`) is NOT changed: its navigation state
  (`src/capture/ConfirmPage.tsx:318`, `focusEventId: row.id`) names an event,
  not an occurrence. See Out of scope.

**Block 6 - the semantics behind the keys and numbers.** Delete or Backspace on
a chip is the delete command; Alt+ArrowDown on a time-grid chip is a move by
`STEP_MINUTES` (15, `src/domain/moveEvent.ts`). RED reads the direction and the
resulting times out of the existing CAL-013 / CAL-025 keyboard-move tests in
`CalendarPage.test.tsx`; AC-4 deliberately fixes only WHICH occurrence is
written and where focus lands. The scope dialog's first radio is "This event
only", checked on every open (`src/events/EditScopeDialog.tsx`).

**Block 7 - oracle partition.** Every criterion is **mechanical**: pin exactly
which chip, which occurrence date, which element holds focus. The dates and
times in AC-2 are **settled** by the fixture - read them out. Nothing is
oracle-free; there is no metric to invent.

**Block 8 - signatures and dependencies.** No existing export changes
signature, so there is no caller list. No test-only dependency is needed.

## Out of scope

- **CAL-058 diff-review finding 2 - the deep link's tie-break across time
  zones.** `useOpenEventFromQuery` prefers the match whose series-zone
  `occurrenceDate` equals the device-zone path date; for a series saved in
  another zone it can pick an already-ended occurrence. That is a different
  defect: it is about WHICH occurrence a reminder link means, not about telling
  two chips apart, and giving chips an occurrence-level identity does not
  change which one the rule picks. Fixing it changes CAL-058's Block 3 rule (a
  product decision), and the architecture excludes full time-zone support (the
  "Dates" row of its decisions table), so whether it is fixed at all is the
  owner's call. It deserves its own story; nothing here touches the tie-break.
  AC-5 holds with device zone and series zone equal, as the fixture has them.
- **Overlap layout keyed by id.** `overlapColumns`
  (`src/domain/timeGrid.ts:79`) returns a map keyed by event id and
  `TimeGrid.tsx:137` reads it by id, so two same-day occurrences of one series
  share one layout entry and the later cluster's entry wins. Reasoned from the
  code, not measured: with a third event overlapping only the 00:00 occurrence,
  that occurrence would be drawn full width over it. Same root cause, a
  different observable (geometry) and a different module with its own tests -
  its own story. GREEN does not change `src/domain/timeGrid.ts` here.
- **Month view and the phone's day list.** Neither has the first-match lookup:
  `MonthView` (`:281`) and `DayList` (`:33`) render each chip straight from
  `eventsOnDay`, so each already opens its own occurrence. They get Block 3's
  attribute because they render `EventChip`; no criterion here pins their
  behaviour. In the month view one overnight occurrence appears in two day
  cells, so even a chip key is not unique there; which of those cells gets
  focus after a keyboard move is not decided here.
- **The week view's two blocks of one overnight occurrence.** The same holds
  across two day columns of a week. The criteria are on the day view, where a
  chip key is unique.
- **Focus after capture (`useFocusEventFromState`).** The navigation carries an
  event id and no occurrence, so "the first chip of that event" is a defensible
  answer and not this defect.
- **Two chips with identical accessible names.** Without an override, the two
  occurrences are both announced "Night, ..., 23:00 to 01:00, repeats daily".
  Whether a chip should say its date is a design question for the Lead
  Designer, not part of this fix. `chipName` is not changed.
- **Pointer drag.** A dragged block will carry the right occurrence as a
  consequence of Block 4; no criterion pins it and no drag test is added.
- **Reminders on a chip** (`ChipRemindersContext`, keyed by series id): correct
  as it is, the reminder belongs to the series' template.
- `seriesOf` and the sheet's series lookup (`CalendarPage.tsx:256`, `:694`)
  look up the stored series row by id on purpose. Leave them.
- No data-model, sync, expander (`shared/recurrence`) or service-worker change.
