## Context

EPIC-02. Source: `docs/wiki/audits/EPIC-02-2026-11-25.md`, Decided 6 and
Evidence `### E-WHOLE` (W04, W05). Two behaviours of the kind editor
(`src/kinds/KindEditor.tsx`, CAL-007) are correct today and are not pinned.
Each can be broken with all 3423 unit tests green:

- **W04, `:226` `useState(false)` -> `useState(true)` for `confirming`.** The
  delete confirmation "Delete the kind {name}?" then opens on top of every
  Edit, before Delete is pressed. The confirmation's own test ("asks first",
  `KindEditor.test.tsx:718` today; `:615` when the audit ran, before CAL-092
  added 103 lines above it) presses Delete and then finds the dialog. It
  never asserts that the dialog was absent before the press.
- **W05, `:247` `chooseCustom` treats every theme as light.** Pressing Custom…
  in the **Dark** theme group then puts the light group into custom mode, and
  the dark group shows no hex input. With a palette colour on the dark side,
  a custom dark colour cannot be entered at all. The one Custom… test
  (`:230`) presses it in the Light group only. The audit's survivors at
  `:249-251` (the dark branch emptied, or `setDarkTouched(true)` -> `false`)
  sit on the same line of behaviour. AC-2 and AC-3 are what kill them; the
  audit reasoned that and ran only the `:247` form. PLANNED has since run two
  of them against scratch copies of the tests (`## Notes`), and the `:251`
  one is DV-3.

This is a test-only story: the production code is right, and the tests pin it.
Each new test passes on arrival, so it has to be earned by putting the
audit's mutant back (see `## Deferred verifications`).

Required gate that would fail if this broke: `unit` (required). It runs
`src/kinds/KindEditor.test.tsx`.

## Acceptance criteria

- **AC-1** - Given the editor opened on an existing kind (Gym), before
  anything is pressed, then the only dialog shown is "Edit Gym": there is no
  dialog named "Delete the kind Gym?", and `deleteKind` has not been called.
- **AC-2** - Given the editor opened on Gym (a palette colour in both themes),
  when Custom… is pressed in the **Dark** theme colour group, then Custom… is
  the only checked radio in the Dark group, the Dark group's Hex input holds
  `#9BD69B`, and the Light group's checked radio is still Gym's palette entry
  with no Hex input shown.
- **AC-3** - Given AC-2's state, when a palette colour is then picked in the
  **Light** group, then the Dark group's Hex input still holds `#9BD69B`.
  Choosing Custom… on the dark side counts as editing it by hand, and the dark
  side stops following the light one.

### Block 2 - AC-1, the editor opens without the delete question

- **Title:** `"opens with the editor as the only dialog, before Delete is pressed (CAL-093 AC-1)"`.
- **Setup:** `const { dialog, actions } = renderEditor({ kind: GYM });` and
  nothing else. No `user`, no press, no `await`: the claim is about the
  first render, so the test is synchronous. `dialog` is what `renderEditor`
  found by `screen.getByRole("dialog", { name: "Edit Gym" })`.
- **Markup this reads.** Each `Dialog` (`src/ui/Dialog.tsx`) is a native
  `<dialog role="dialog" aria-labelledby=...>` whose name is its `<h2>`
  title, opened with `showModal()`. The confirmation is a **sibling** of the
  editor's dialog (`KindEditor.tsx:410-440`), not inside it, so every query
  here is on `screen`, never `within(dialog)`. Only an open dialog is in the
  accessibility tree; `<ToastHost />` is not a dialog.
- **Assertions, in this order:**
  1. `expect(screen.getAllByRole("dialog")).toStrictEqual([dialog])` -
     "the only dialog shown is Edit Gym". Exact: one element, and that one.
  2. `expect(screen.queryByRole("dialog", { name: "Delete the kind Gym?" })).toBeNull()`
     - the AC's named negative. The same query, positively, is what the
     "asks first" test (`:718`) finds after the press, so the needle is
     known to match the real confirmation.
  3. `expect(actions.deleteKind).not.toHaveBeenCalled()`.
- **Why the first assertion carries the weight.** A negative on a name is
  also true when the name is misspelt. Assertion 1 has no name in it: any
  second open dialog fails it. Under the mutant it receives two dialogs
  (measured, `## Notes`).

### Block 3 - AC-2, Custom… in the Dark group opens the dark hex

- **Title:** `"pressing Custom… in the Dark group checks it there and shows the dark hex, leaving the Light group alone (CAL-093 AC-2)"`.
- **Setup:** `const { user } = renderEditor({ kind: GYM });` then one
  `await user.click(radio("Dark", "Custom…"))`. Gym is a palette colour in
  both themes, so both groups open with `Gym` checked and no Hex input
  (pinned already at `:198` and `:223`).
- **Markup this reads.** Each theme's group is
  `role="radiogroup"` named `"Light theme colour"` / `"Dark theme colour"`
  (`group("Light" | "Dark")`). Its radios are `role="radio"` buttons with
  `aria-checked`, the eleven palette entries named by `aria-label` and the
  last by its text `Custom…` (U+2026, one character, as at `:72` and
  `:230`). The Hex input is a `textbox` named `Hex` inside the group, and is
  rendered only while that group's Custom… is checked.
- **Assertions, in this order:**
  1. `expect(checked("Dark")).toStrictEqual(["Custom…"])` - Custom… is the
     **only** checked radio in the Dark group.
  2. `expect(hexInput("Dark")).toHaveValue("#9BD69B")`.
  3. `expect(checked("Light")).toStrictEqual(["Gym"])`.
  4. `expect(within(group("Light")).queryByRole("textbox", { name: "Hex" })).toBeNull()`
     - the same query the test at `:223` uses.
- **`#9BD69B`** is Gym's dark colour, read out, not derived: the `GYM`
  fixture (`:52`) and the palette (`src/kinds/defaultKinds.ts:24`). The
  editor shows it exactly as stored: `chooseCustom` keeps the side's `hex`
  and only sets `custom` (`KindEditor.tsx:250`). Confirmed by running it
  (`## Notes`).

### Block 4 - AC-3, the dark side stops following the light one

- **Title:** `"a dark side put into Custom… keeps its hex when a light colour is picked afterwards (CAL-093 AC-3)"`.
- **A test of its own**, repeating AC-2's press, not more assertions in
  AC-2's test: then the mutant that loses the "edited by hand" flag (DV-3)
  turns exactly one test red, and AC-2's stays green under it.
- **Setup and steps, in this order:**
  1. `const { user } = renderEditor({ kind: GYM });`
  2. `await user.click(radio("Dark", "Custom…"))`
  3. `expect(hexInput("Dark")).toHaveValue("#9BD69B")` - the given, "AC-2's
     state". One assertion is enough here; AC-2's test owns the rest.
  4. `await user.click(radio("Light", "Entertainment"))` - "a palette colour
     is then picked in the Light group". **Entertainment**, because its dark
     colour `#F5CC6A` differs from Gym's, so a dark side that followed would
     show it. Not `Gym`: that pick proposes `#9BD69B` again and would hide
     the difference in the hex.
  5. `expect(checked("Light")).toStrictEqual(["Entertainment"])` - the
     anchor: the light pick did happen.
  6. `expect(checked("Dark")).toStrictEqual(["Custom…"])`
  7. `expect(hexInput("Dark")).toHaveValue("#9BD69B")` - the AC's claim.
- **Semantics.** `darkTouched` (`KindEditor.tsx:222`) is what stops
  `proposeDark` (`:234-236`) from overwriting the dark side when the light
  one changes. `chooseCustom("dark")` sets it at `:251`. Without that line
  the light pick at step 4 replaces the dark side with Entertainment's
  palette entry: Custom… is unchecked and the Hex input is gone (measured).
- Not asserted: what Save then sends. The AC is about what the editor shows.
