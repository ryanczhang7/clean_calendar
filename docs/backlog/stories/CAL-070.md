EPIC-05. Source: `docs/wiki/audits/epic-05-2026-11-11.md` (Decided 4;

The re-audit confirms that every ConfirmPage gap CAL-049 was filed for is now
killed against the whole unit project (R1 to R5, R15, and the Stryker survivors
at the old `:200`, `:260`, `:262`, `:279` and `:324`). Two lines written
**since** the 10-31 audit survive the whole unit project, 3020 tests:

- **N1, CAL-049's own fallback**: `src/capture/ConfirmPage.tsx:103`,
  `if (lastDay > value.startDate) value.endDate = lastDay;` with the condition
  replaced by `true`. CAL-049 Block 4 says an all-day proposal whose `endsAt` is
  *earlier* than its start leaves End date on the start's day. Nothing pins
  that. CAL-049's test plan says so itself ("Out of scope not pinned: the
  all-day `endsAt` before the start"). Under the mutant, an all-day proposal of
  14 Nov with `endsAt` 12 Nov opens with End date 12 Nov. Save then refuses it
  with the end error on a field the owner never touched. Nothing wrong is
  stored. The cost is a capture the owner has to correct by hand, and the
  prompt does not stop the model from answering that way.
- **N2, CAL-024's focus rule on this page**: `ConfirmPage.tsx:276`,
  `found.end !== undefined` replaced by `true`. CAL-024 Block 7 (EPIC-06) made
  `focusField` go to Title, else End date, else Repeat until. On the confirm
  screen the third branch is never asserted. The existing case
  `ConfirmPage.test.tsx:1388` ("Ends on 2 November, before the start") checks
  the error text and `aria-invalid` and does not check focus. Under the mutant,
  a submit refused only for Repeat until puts focus on End date, which is valid,
  and the keyboard or screen-reader owner is left on the wrong field.

The code was filed under EPIC-05 because both lines are in the confirm screen
and both tests go in its one test file. N2's behaviour is CAL-024's (EPIC-06).

Test-only: the shipped page is believed correct, so each case passes on
arrival and is earned by its mutant.

Required gate that would fail if this broke: `unit` (and `coverage`, which runs
the same suite).

## Acceptance criteria

- **AC-1** - Given an all-day proposal with `startsAt` `"2026-11-14"` and
  `endsAt` `"2026-11-12"` (an end before its start), when the confirm screen
  opens, then Start date and End date both read `2026-11-14`. When the owner
  then presses Save event, `createEvent` is called once with an all-day event
  covering 14 Nov only. A test fails under
  `103s#lastDay > value.startDate#true#` on `ConfirmPage.tsx`.
- **AC-2** - Given the confirm form with a valid end, Repeat set to weekly and
  Ends "On date" 2 Nov (before the 3 Nov start), when the owner presses Save
  event, then focus is on the Repeat until input and `createEvent` is not
  called. A test fails under `276s#found.end !== undefined#true#` on
  `ConfirmPage.tsx`.

## Out of scope
