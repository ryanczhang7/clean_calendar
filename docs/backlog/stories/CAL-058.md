## Context

EPIC-07's done-when says a tapped reminder "opens the event". CAL-028 makes
the notification open `/day/{yyyy-MM-dd}?event={id}` (its AC-6), but nothing
reads an `event` query parameter today: `src/app/routes.tsx` routes
`/day/:date` to `CalendarPage`, which opens the sheet only from a chip
(`onOpenEvent`, CalendarPage.tsx:574). Filed from CAL-028 PO decision 4 so the
gap is a story rather than a surprise at the end of the epic.

Required gate that would fail if this broke: `unit`
(`src/calendar/CalendarPage.test.tsx`, RTL over a memory router).

## Acceptance criteria

- **AC-1** - Given `/day/2026-11-03?event={id}` where `{id}` is a cached event
  on that day, when the page renders, then the day view shows and the event
  sheet opens on that event once, and the `event` parameter is removed from
  the URL (so Back and a reload do not reopen it).
- **AC-2** - Given an `event` id that is not in the cache, or the row arrives
  only after the first render, when the page renders, then no sheet opens on
  the first render and, if the row arrives within the same mount, the sheet
  opens once when it does; a malformed id opens nothing.
- **AC-3** - Given `/day/2026-11-03?event={id}` for a recurring series, when
  the page renders, then the sheet opens on the occurrence dated 2026-11-03
  (the date in the path), not on the series' first occurrence.

### Block 1 - where it lives, and what does not change

One hook inside `src/calendar/CalendarPage.tsx`, called by `CalendarPage`
(suggested name `useOpenEventFromQuery`; not exported, so the name is GREEN's).
**No export changes signature**: `CalendarPage`'s props, `SheetRequest`
(`src/events/EventSheet.tsx:59`) and `occurrencesIn`
(`src/sync/useOccurrences.ts:41`) are used as they are. There are therefore
no callers to list. The tests drive it through the page over a memory router,
as `renderSheetPage` already does, with an initial entry such as
`/day/2026-11-03?event=<id>`.

### Block 2 - reading the parameter

- The parameter is the query key `event` on a **day path** (`/day/:date`, i.e.
  `period.view === "day"`). On `/`, `/month/...` and `/week/...` it is ignored
  and left in the URL.
- It is read on **every location that carries it**, not only at mount: the
  service worker may navigate an already-open app to the URL
  (`src/pwa/pushHandlers.ts:65` builds it, in the device's time zone, so the
  path's date is the device-local day of the event).
- A well-formed id is a UUID: `/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`.
  Anything else (empty, `evt 1`, `"]`, a repeated key's first value that does
  not match) is **malformed**: nothing becomes pending, nothing is ever opened,
  and no selector is built from it (the page builds
  `[data-event-id="${id}"]` selectors, which a raw `"` would break).
- **The parameter is removed as soon as it is read**, well-formed or not,
  found or not (PO decision 1): one `navigate(..., { replace: true })` to the
  same pathname with `event` deleted, every other query key kept and
  `location.state` passed through. Replace, not push: the history length does
  not grow, so Back leaves the day rather than returning to the `?event=` URL,
  and a reload does not reopen the sheet.

### Block 3 - opening the sheet

- The wanted id is held for the life of that day path ("pending"). It is
  resolved against **the day the path names**: `occurrencesIn(events,
  overrides, dayStart, nextMidnight(dayStart))` over the page's events and
  overrides stores, taking the entry whose `id` equals the pending id. That is
  the list the day view itself renders, so the sheet can only open on something
  the day shows. If two entries share the id (a series occurrence running over
  midnight plus that day's own), the one whose `occurrenceDate` equals the
  path's `yyyy-MM-dd` wins; otherwise the first.
- It resolves only once the overrides store is not `loading` (an occurrence
  must not open before a cancellation or an edit of it has been read).
- On resolving, the page sets the same request a chip does
  (`onOpenEvent`, CalendarPage.tsx:609): `{ mode: "edit", event, opener }`, and
  for an occurrence (`event.occurrenceDate !== undefined`) also `series`, the
  stored row from the events store. `opener` is that event's chip in the
  document if one is rendered at that moment
  (`[data-event-id="<id>"]`), else `null` - so closing the sheet returns focus
  to the chip, as it does after a click.
- **Once.** After it opens, pending is cleared: closing the sheet does not
  reopen it, and a later store update does not either.
- **Not found on the first render (AC-2):** nothing opens; pending stays. When
  a later store update within the same mount brings the row in, the sheet opens
  then, once. Pending is dropped, without opening anything, when the pathname
  changes, or when the row arrives while another sheet is already open (the
  user's sheet is not replaced).
- An id that is cached but has nothing on that day - a non-recurring event on
  another date, a cancelled occurrence, a soft-deleted row - opens nothing
  (AC-1 says "on that day").
- AC-3: for a weekly series whose stored row starts weeks earlier, the sheet's
  event is the occurrence with `occurrenceDate === "2026-11-03"`, so its date
  fields read 3 November, not the series' first date.

### Oracle partition

- **Mechanical (pin exactly):** which event the sheet opens on (title and date
  fields; for a series the occurrence's date), that it opens once (still one
  sheet after a store update; closed stays closed), the URL after (path
  unchanged, no `event` key, other keys kept), history not grown, the malformed
  cases, the pending-then-arrives case, the dropped cases.
- **Settled / oracle-free:** none.

Assertions that pass against today's tree ("a malformed id opens nothing", "an
unknown id opens nothing on the first render") assert nothing alone: today no
sheet ever opens from a URL. Pair each with its positive in the same test (the
same render later receives the row and opens; the same path with a good id
opens), or leave it to the deferred verification.
