## Context

EPIC-06. Split out of CAL-025 on 2026-11-01 (CAL-025, Notes, PO decision
3): editing or deleting one occurrence writes an `event_overrides` row, and
every write in this app goes through the outbox (CAL-015) - but the outbox,
the drain and `discardOp` know two tables, `events` and `kinds`
(`src/sync/outbox.ts` `CacheTable`, `src/sync/drain.ts` `repoFor`), and the
overrides repository (`src/data/eventOverrides.ts`, CAL-005) has no `get`.
This story is the sync layer only: an `OverrideActions` facade over the
outbox, and the outbox/drain/discard support for a third table. CAL-025 puts
the dialog and the callers on top of it. The cache table `db.overrides`,
realtime (`realtime.ts`) and hydration (`hydrate.ts`) already carry
`event_overrides`; nothing there changes.

An override has no `deleted_at`: "deleting" an occurrence is `cancelled =
true` on its override, and undoing that is `cancelled = false` on the same
row. So the outbox never queues `delete` or `restore` ops for this table -
only `insert` and `update`.

Required gate that would fail if this broke: `unit`.


## Acceptance criteria

- **AC-1** - Given an occurrence with no override in the cache, when
  `setOverride(eventId, occurrenceDate, fields)` is called, then one override
  row is added to the cache (`eventId`, `occurrenceDate`, `cancelled: false`,
  the given fields, every other field `null`), one `insert` op on
  `event_overrides` is queued, the call resolves `{status: "ok", row}` with
  that row, and `useOverrides` sees it.
- **AC-2** - Given an override already in the cache for that event and date,
  when `setOverride` is called with other fields, then the same row (same
  `id`) is updated with only the given fields, every field not given keeps
  its value, and one `update` op whose patch holds only the given fields is
  queued.
- **AC-3** - Given an occurrence, when `cancelOccurrence(eventId,
  occurrenceDate)` is called, then its override has `cancelled: true`
  (inserted if absent, updated if present, as AC-1/AC-2) and one op is
  queued; when `restoreOccurrence(row)` is then called with the row
  `cancelOccurrence` returned, then that row has `cancelled: false` and one
  `update` op `{cancelled: false}` is queued.
- **AC-4** - Given queued `event_overrides` ops, when the drain runs online,
  then an `insert` op calls the overrides repository's `insert(patch, id)`
  and an `update` op calls `update(id, patch, <the cache row's updatedAt>)`;
  on `ok` the cache row takes the server's stamps and the op is deleted; on
  `conflict` the fresh server row replaces the cache row, the op is deleted,
  and a `conflict` notice is emitted naming the patch's fields in
  `voice.md`'s words ("title", "start time", "end time", "all day",
  "location", "notes", "kind", "cancelled").
- **AC-5** - Given a queued `event_overrides` `insert` op, when `discardOp`
  is called with its `seq`, then the op and the cache row are both gone;
  given a queued `update` op, then the op is gone and the cache row is
  replaced by the repository's `get(id)` result.
- **AC-6** - Given the app offline, when the three actions are called, then
  each resolves `ok` at once, `queuedCount` counts their ops, and nothing
  reaches the repository until a drain run.

**Block 1 - the facade (`src/sync/overrideActions.ts`).**

```ts
export type OverrideFields = Partial<
  Pick<NewEventOverride, "title" | "kindId" | "startsAt" | "endsAt" | "allDay" | "location" | "notes">
>;
export type OverrideActions = {
  /** Upsert for (eventId, occurrenceDate): merge `fields` into the existing override, or create one. */
  setOverride(eventId: string, occurrenceDate: string, fields: OverrideFields): Promise<Result<EventOverride>>;
  /** cancelled = true on that occurrence's override (created if absent). */
  cancelOccurrence(eventId: string, occurrenceDate: string): Promise<Result<EventOverride>>;
  /** cancelled = false on the row cancelOccurrence returned. */
  restoreOccurrence(cancelled: EventOverride): Promise<Result<EventOverride>>;
};
export function createOutboxOverrideActions(
  db: CalendarDb,
  drain: Pick<Drain, "run">,
  online?: () => boolean,          // default () => navigator.onLine
): OverrideActions;
export const overrideActions: OverrideActions;   // over the app's db and appDrain
```

- "Existing override" means the cache row with that `eventId` and
  `occurrenceDate` (`db.overrides.where({eventId, occurrenceDate})`), the
  unique key the database enforces. Lookup and write happen in one Dexie
  transaction over `db.overrides` and `db.outbox`, as `outbox.ts`'s
  `rewrite` does.
- A new override's id is `newId()`; its `createdAt`/`updatedAt` are
  `nowTs()` (the optimistic stamps `enqueueInsert` already writes for
  events); a merged one keeps its `updatedAt` (never touched by an
  optimistic write - CAL-015 PO decision 3).
- `setOverride` with `{}` is a no-op that resolves `ok` with the existing row,
  or, with no existing row, inserts one with every field null (a caller
  sends an empty patch only by mistake; RED may pin either and GREEN follows).
- Results follow `queuedResult`: `ok` with the cache row, a drain run
  kicked off when online, never awaited.

**Block 2 - the outbox (`src/sync/outbox.ts`).**
- `CacheTable` becomes `"events" | "kinds" | "event_overrides"`; `Row` gains
  `EventOverride`; `cacheTable(db, "event_overrides")` is `db.overrides`.
- `enqueueInsert` and `enqueueUpdate` gain an `event_overrides` overload
  (`NewEventOverride` / `EventOverridePatch`). `enqueueDelete` and
  `enqueueRestore` do **not**: their `table` type stays `"events" | "kinds"`,
  so a delete on an override is a type error.
- `Repos.overrides: Pick<EventOverridesRepo, "insert" | "update" | "get">`.
- `discardOp` handles the third table exactly as the other two (AC-5).

**Block 3 - the drain (`src/sync/drain.ts`).**
- `repoFor("event_overrides")` is `repos.overrides`; `send` is unchanged in
  shape (`restore` on a repo without one already returns `"skipped"`; an
  override op is never `delete`/`restore`, see Block 2).
- The `ok` branch copies `updatedAt` and `createdAt` only - an override has
  no `deletedAt` (RED pins that the cache row has no `deletedAt` key after
  a send).
- `fieldNames("event_overrides", patch)`: `OVERRIDE_FIELDS` =
  `[["title","title"],["startsAt","start time"],["endsAt","end time"],["allDay","all day"],["location","location"],["notes","notes"],["kindId","kind"],["cancelled","cancelled"]]`.
- `titleOf` for an override row is `row.title ?? ""` (the conflict toast
  may name an empty title; CAL-025 decides the user-facing copy).
- The pass loop's `if (op.table !== "events" && op.table !== "kinds")
  continue;` admits the third table.
