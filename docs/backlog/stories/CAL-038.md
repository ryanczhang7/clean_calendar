## Context

EPIC-01, from `docs/wiki/audits/epic-01-2026-10-15.md` (Decided 8;
Evidence E-flake). This is **not** a surviving-mutant cluster. It is filed
because it makes mutation results untrustworthy: in the audit, 12 of 340
full-suite mutant runs (3.5%) failed one of two `SignInPage` offline tests
for reasons unrelated to the mutant, and in 3 of them that was the only
failure, so Stryker recorded a kill no assertion earned. The tests:

- `src/auth/SignInPage.test.tsx` › offline (AC-5) › "re-enables the button
  when the connection comes back" (`expect(button).not.toHaveAttribute("aria-disabled", "true")`
  fails). CAL-005 saw this once in about 15 full gate runs, and CI has passed it.
- … › "disables the button when the connection drops while the page is
  open" (`toHaveAttribute("aria-disabled", "true")` receives `null`). This
  one is newly observed in the audit.

Both dispatch `online`/`offline` synchronously right after awaiting the
button, then assert without waiting. The page subscribes in a `useEffect`
(`useOnline`, `SignInPage.tsx:54–66`). **The cause was not established when
this was filed** (it is now, 2026-10-26: `## Notes`, "Cause, with evidence"). It
could be the test (asserting before the listener is attached or before the
re-render lands) or the hook (an event missed between the first render and
the subscription, which a real browser could also hit). CAL-005 recorded
that it touched neither file. Load made it more frequent in the audit: up to
four parallel vitest processes plus a db suite. CAL-005 also says the flake
was "filed as a follow-up for its own story". No such story file existed on
2026-10-15.

Required gate that would fail if this broke: `unit` and `coverage` (where
CAL-005 saw it).

## Acceptance criteria

- **AC-1** — Given the unit suite under the load the audit used (four
  concurrent `pnpm exec vitest run --project unit` processes), when
  `src/auth/SignInPage.test.tsx` runs 200 times, then all of its tests pass

  measured and recorded first, so "it did not fail" is compared with a

- **AC-2** — Given the fix, when `useOnline`'s `online` listener is not
  registered (`SignInPage.tsx:58`, event name → `""`), then "re-enables the
  button when the connection comes back" fails on every run. And when the
  `offline` listener is not registered (`:59`), "disables the button when
  the connection drops while the page is open" fails on every run. The
  tests must still detect the defect they exist for.
- **AC-3** — Given the sign-in card has rendered while online, when the
  connection drops after that render but before the page starts listening
  (so the `offline` event reaches no listener of the page's), then the
  button is still marked `aria-disabled="true"` and "Sign-in needs a
  connection" shows. This is the defect the cause investigation found (see
  `## Notes`), reproduced deterministically rather than by load.
- **AC-4** — `src/auth/SignInPage.test.tsx` passes 20 runs in a row under
  `pnpm exec vitest run --project unit --coverage`, the gate where CAL-014
  and CAL-020 saw it fail.

### Cause, with evidence (2026-10-26, orchestrator)

**The page's `offline` listener is sometimes not attached yet when the test
sends the event, and every such run fails. No run fails while it is attached.**

The button is in the DOM once `SignInCard` commits, but `useOnline`
subscribes in a passive effect that React runs in a later scheduler task.
`findByRole` can resolve in between. An event sent in that gap reaches no
listener. The hook never reads `navigator.onLine` again after its first
render, so the state stays `true` for good, not just late. That last part is
a defect in the product as well: a real connection that drops between the
first render and the effect leaves the button enabled.

Probe: a throwaway test (`src/auth/__probe_signin_race.test.tsx`, deleted
after) ran the flaky test's exact sequence 60 times per file, spying
`window.addEventListener`/`removeEventListener` to record whether an
`offline` listener was registered at the moment of dispatch. Six files, run
while three full `vitest run --project unit` suites looped as load (four
concurrent vitest processes, 12 cores):

    {"attached":59,"notAttached":1,"failedWhenAttached":0,"failedWhenNot":1}
    {"attached":59,"notAttached":1,"failedWhenAttached":0,"failedWhenNot":1}
    {"attached":58,"notAttached":2,"failedWhenAttached":0,"failedWhenNot":2}
    {"attached":58,"notAttached":2,"failedWhenAttached":0,"failedWhenNot":2}
    {"attached":57,"notAttached":3,"failedWhenAttached":0,"failedWhenNot":3}
    {"attached":59,"notAttached":1,"failedWhenAttached":0,"failedWhenNot":1}

10 of 360 iterations dispatched before the subscription, and all 10 failed.
All 350 that dispatched after it passed. Without load, four files (240
iterations, one under `--coverage`) had the listener attached every time
and no failure. The plain file passed 12 of 12 runs and 20 of 20 under
`--coverage` with four file-only processes in parallel. So load is what
opens the gap, which matches the audit (3.5% under four processes) and
CAL-006 (0 of 16 isolated, 2 of 15 in `--fast`).

Only `SignInPage.tsx` and `src/sync/syncState.ts` register
`online`/`offline` listeners in `src/`. `syncState`'s are in the app shell,
not on `/signin`.
