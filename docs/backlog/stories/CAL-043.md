## Context

EPIC-03, from `docs/wiki/audits/epic-03-2026-10-21.md` (Decided 6;
Evidence E-STRYKER `src/domain/eventForm.ts`, hand mutant H13, E-CLEAR).

`src/domain/eventForm.ts` (CAL-012, Block 1) is well pinned on valid input:
Stryker killed 149 of 169 mutants, and every patch, duration and
inclusive-end mutant died. No test hands it a **cleared** field, though. A
date input reports `""` while cleared or half-typed, and `EventForm.tsx:99-111`
passes that straight to `moveStart`. Two guards keep that safe, and either
can be deleted with all 156 tests of `eventForm.test.ts`,
`EventForm.test.tsx` and `EventSheet.test.tsx` green:

- `moveStart`'s validity guards (`:136` all-day, `:144` timed; eight
  mutants). Without them, clearing the start date or time throws
  `RangeError: Invalid time value` (E-CLEAR, measured by calling the
  function).
- `local()`'s null guard (`:66`; four mutants). Without it, `moveStart` and
  `validate` throw `TypeError: Cannot read properties of null (reading '1')`
  on any empty date or time.

Two smaller gaps in the same module:

- `:137` `if (oldEnd < oldStart) return moved` → `false`. For an all-day
  value whose end date is already before its start, moving the start drags
  the end along. The Contract says only the start moves.
- `:193` `text.trim() === ""` → `text === ""`. A location or notes field of
  spaces is stored as typed instead of `null`.

Test-only: the shipped module is believed correct, so each new assertion
passes on arrival and is earned by its mutant.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given a timed value 14 Oct 09:00–10:30, when `moveStart` is
  called with the start date `""` (and, separately, the start time `""`),
  then it returns the value with only that field changed: end date and end
  time unchanged, nothing thrown. **And** given the same value with its end
  time already `""` (and, separately, its end date `""`), when the start
  moves to a valid 15 Oct 09:00, then only the start changes and nothing
  throws. A test fails when the guard at `:144` is removed (audit H13) and
  under each of the four Stryker forms there (`:144:7`: `false`,
  `false || !valid(newStart)`, and the two `&&` forms). The second half is
  what kills the forms that still check `newStart`. A test also fails when
  `local()`'s null guard (`:66`) is removed.
- **AC-2** - Given an all-day value 12–14 Oct, when `moveStart` is called
  with the start date `""`, then only the start date changes. And given the
  same value with its end date `""`, when the start moves to 15 Oct, then
  only the start changes. Neither throws. A test fails under each of the
  four Stryker forms of the guard at `:136`.
- **AC-3** - Given a timed value with the end date `""` (and, separately,
  the end time `""`), when `validate` runs, then it returns
  `{ end: END_ERROR }` and does not throw. A test fails when `local()`'s null
  guard (`:66`) is removed or reduced to either half.
- **AC-4** - Given an all-day value whose end date (10 Oct) is before its
  start date (12 Oct), when the start moves to 15 Oct, then the end date is
  still 10 Oct. A test fails when `:137` is `if (false)`.
- **AC-5** - Given a value whose location and notes are each three spaces,
  when it becomes a new event (`toNewEvent`) and a patch against an event
  with `location: null, notes: null` (`patchOf`), then both are `null` in the
  new event and absent from the patch. A test fails when `:193`'s
  `trim()` is removed.
- **AC-6** - Given the event form open on a timed event, when the user
  clears the start date input, then no error is thrown or logged, the end
  date and end time inputs keep their values, and Save shows the form's
  error rather than sending a request. A test fails under the audit's H13
  mutant.
