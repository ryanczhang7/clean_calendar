## Context

EPIC-07. Source: `docs/wiki/audits/EPIC-07-2026-11-23.md` (Decided 4,
Evidence E-DENO).

The send-reminders function runs unattended every minute. Its `deps.log`
lines (`console.error` in `index.ts`) are the only record of a push, a
prune or a `sent_at` write that went wrong. CAL-028's GATES notes say the
`sent_at` write's failure line is "not constrained by any test; noted for
review". The audit found that eight mutants of these lines survive the
send-reminders Deno suite (94 tests at `c6a1bac`). Six are gaps. The two
`?.`-dropped variants (`:281:22` and `:305:18` OptionalChaining) differ only
when `null` or `undefined` is thrown, and the audit judged them equivalent.

- `supabase/functions/send-reminders/handler.ts:302:19`, the `catch` of the
  `sent_at` PATCH emptied to `{}`, and `:303:7`, `:304:9`, `:305:18` (two)
  within it: the call dropped, the message blanked, the message read as
  `message && err` or without `?.`. No test makes that PATCH throw.
- `:273:15`, `if (!res.ok)` -> `if (true)` on the subscription DELETE. A
  successful delete then logs a failure line. No test asserts that a
  successful delete logs nothing.
- `:281:22` (two), the DELETE's thrown-error message read as
  `?.message && err` (giving `TypeError: connection reset` instead of
  `connection reset`) or without `?.`. The one test of a failed DELETE,
  "AC-4: a DELETE that fails is logged ..." (`handler_test.ts:882`), checks
  `w.log.some((l) => l.includes("sub-a"))`. That needle floats: any line
  naming the subscription passes it.

No surviving mutant removes the PATCH's `try` itself, because Stryker does
not generate that mutant. But no test shows that a PATCH which throws
leaves the run going. AC-1 pins that as well, because the reminders after it
in the same run depend on it.

Test-only. The shipped handler is believed correct for all three criteria,
so each passes on arrival and is earned by its mutant (DV-1 to DV-3).
Required gate that would fail: `deno-test`.

## Acceptance criteria

- **AC-1** - Given two due reminders, one subscription that accepts every
  push, and a PATCH of the **first** reminder's `sent_at` that throws
  `TypeError("connection reset")`, the response is 200 with
  `{ due: 2, sent: 2, pruned: 0, failed: 0, materialised: 0 }`, the second
  reminder is pushed and then PATCHed, and `deps.log` holds exactly one
  line, `send-reminders: marking reminder <first id> sent failed: connection reset`.
  A test fails when `handler.ts:303-307` (the `deps.log` call in that
  `catch`) is deleted.
- **AC-2** - Given a push answered `gone` (410) and a DELETE answered 204,
  `deps.log` holds no line naming that subscription. A test fails under
  `273s/if (!res.ok) {/if (true) {/`.
- **AC-3** - Given a push answered `gone` (410) and a DELETE that throws
  `TypeError("connection reset")`, `deps.log` holds exactly
  `send-reminders: delete of subscription <id> failed: connection reset`,
  compared whole and not by `includes`. A test fails under
  `281s/)?.message ?? err)/)?.message \&\& err)/`.

## Out of scope

- Logging, or retrying, a `sent_at` PATCH that **answers** non-2xx (as
  opposed to throwing). `handler.ts:293-301` ignores the response, so a
  reminder whose PATCH answers 5xx stays unmarked, and the next minute's run
  pushes it again while it is inside the five-minute window. That is a
  behaviour change, not a missing test. CAL-028's notes left it open for
  review. The audit puts it to the PO (Decided 6) and does not file it here.
- The `?.` mutants on thrown values (`:225:18`, `materialise.ts:152:24`).
  They differ only when `null` or `undefined` is thrown. The audit judged
  them equivalent.
