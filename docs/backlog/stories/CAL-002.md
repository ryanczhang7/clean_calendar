## Context

The **walking skeleton** (EPIC-01). After bootstrap the repository builds but
does nothing; this story makes the routed, themed app shell that every later
screen slots into, so that no later story has to edit the router or the shell
to add its screen. It emits `docs/wiki/design/tokens.md` as real CSS custom
properties, renders the top bar and the phone bottom nav from
`docs/wiki/design/layout.md` and `components.md` ("App shell and top bar"),
hosts the single toast live region and the dialog primitive
(`components.md`, "Shared primitives"; `accessibility.md`, "Live regions"),
and registers a placeholder page per route, each a file a later story
replaces.

Required gate that would fail if this broke: `unit` (Testing Library over the
shell, routes, toast and dialog; a test that parses `tokens.css`).

## Acceptance criteria

- **AC-1** - Given `src/styles/tokens.css`, when a test lists the custom
  properties declared on `:root` and those declared in the dark block, then
  `:root` declares every property named in `tokens.md`, the dark block
  declares every `--color-*` property and nothing that `:root` lacks, `:root`
  sets `color-scheme: light dark`, and the dark declarations appear both under
  `@media (prefers-color-scheme: dark)` guarded by
  `:root:not([data-theme="light"])` and under `:root[data-theme="dark"]`.
  *Control:* deleting one `--color-*` line from the dark block must fail the
  test and name the property.
- **AC-2** - Given the router, when each of `/`, `/month/2026-10`,
  `/week/2026-10-12`, `/day/2026-10-14`, `/welcome`, `/kinds`, `/capture`,
  `/capture/confirm`, `/settings/notifications` and `/signin` is visited, then
  the placeholder page for that route renders exactly one `<h1>`; and an
  unknown path renders a page whose `<h1>` reads "Nothing here" with a link
  named "Go to today" to `/`.
- **AC-3** - Given any calendar route, when the shell renders, then the top bar
  contains a link named "Capture" to `/capture`, a button named "Legend", and
  an account menu button whose menu holds links named "Kinds" (`/kinds`) and
  "Notifications" (`/settings/notifications`); and a navigation landmark named
  "Bottom navigation" holding links Month, Week, Day and Capture and a button
  named "Legend" comes **after** the `main` landmark in DOM order.
- **AC-4** - Given a route change, when the new page renders, then focus is on
  that page's `<h1>` (`accessibility.md`, Focus).
- **AC-5** - Given the shell, when `showToast({text, action?})` is called, then
  the text appears inside the one element with `role="status"`; a toast
  without an action is removed after 6 s and one with an action after 10 s
  (fake timers); a second toast replaces the first; a toast with
  `tone: 'alert'` renders in a `role="alert"` element instead; and clicking
  the action button calls its handler and dismisses the toast.
- **AC-6** - Given the `Dialog` primitive opened from a button, when it opens,
  then it is a modal `<dialog>` named by its title, focus is on its first
  non-destructive control, Escape closes it, and focus returns to the button
  that opened it.

### Toast (`src/ui/Toast.tsx`, `Toast.module.css`, `Toast.test.tsx`) - AC-5

- `export type Toast = { text: string; action?: { label: string; onClick:
  () => void }; tone?: "status" | "alert" }` - `tone` defaults to
  `"status"`.
- `export function ToastProvider({ children }: { children: ReactNode })`
- `export function ToastHost(): JSX.Element` - renders **always** one
  `<div role="status" aria-live="polite">` (empty when no status toast)
  and, only while an alert toast is showing, a `<div role="alert">`.
  Inside: the text, and if `action`, one `<button type="button">` named
  `action.label`.
- `export function useToast(): { showToast(t: Toast): void; dismiss():
  void }` - throws outside the provider.
- Timing semantics (`components.md`, Toast): a toast **without** an
  action is removed **6 000 ms** after `showToast`; one **with** an action
  after **10 000 ms**. The timer starts at `showToast`, measured with
  `vi.useFakeTimers()` + `vi.advanceTimersByTime`. At 5 999 / 9 999 ms the
  toast is still present; at 6 000 / 10 000 it is gone. A second
  `showToast` **replaces** the first immediately and restarts the timer.
  Clicking the action calls `onClick` once, then dismisses. Pause on
  hover/focus is **not** pinned here (not in the AC; GREEN may add it
  without changing the numbers above).
- Tests render `<ToastProvider><ToastHost/><Trigger/></ToastProvider>`
  with a `Trigger` test component that calls `useToast()` from a button.

### Dialog (`src/ui/Dialog.tsx`, `Dialog.module.css`, `Dialog.test.tsx`) - AC-6

- `export function Dialog(props: { open: boolean; title: string; onClose:
  () => void; children: ReactNode; actions?: ReactNode }): JSX.Element`
- Renders a native `<dialog aria-labelledby={id}>` with `<h2 id={id}>{title}</h2>`,
  the `children`, then `actions`. When `open` becomes true it calls
  `dialogEl.showModal()` (so `:modal` / `aria-modal` semantics come from the
  element), records `document.activeElement` as the opener, and moves focus
  to the **first non-destructive control**: the first element in DOM order
  inside the dialog matching `button, [href], input, select, textarea,
  [tabindex]:not([tabindex="-1"])` whose `data-variant` is not `"danger"`.
  `Escape` (the dialog's `cancel` event) calls `onClose`; when `open` turns
  false it calls `close()` and restores focus to the recorded opener.
- **jsdom caveat, measured 2026-10-13:** jsdom 30.1.2 (the installed
  version) does **not** implement `HTMLDialogElement.prototype.showModal`
  (`typeof el.showModal === "undefined"`). So `src/test/setup.ts` (a test
  file, writable in RED) installs a minimal stub: `showModal()` sets the
  `open` attribute, `close()` clears it and dispatches a `close` event; the
  handoff says so, and GREEN must not rely on anything the stub does not do.
  A dialog's `cancel` event on Escape may also need to be dispatched by the
  test (`fireEvent.cancel` or `user.keyboard("{Escape}")` + a keydown
  handler that calls `onClose` - GREEN decides, the test asserts the
  outcome: `onClose` called and the opener focused).
- **Amended by RED, 2026-10-13.** The stub in `src/test/setup.ts` does
  one thing more than the paragraph above says, so that the test can press
  Escape as a user does (`user.keyboard("{Escape}")`) instead of firing a
  synthetic event: on an Escape `keydown` reaching `document` while a dialog
  opened with the stubbed `showModal()` is open, it dispatches a
  **cancelable `cancel` event** on that dialog and, unless the event was
  `preventDefault()`ed, calls `close()` - the browser's close-request
  behaviour. `close()` is a no-op on a dialog that is not open, and
  dispatches `close` only when it closed something. Consequence for GREEN:
  handle Escape through the dialog's `cancel` event (React `onCancel`) or
  its native `close` event, not both without `preventDefault()` - the test
  asserts `onClose` is called **exactly once** per Escape, which is what a
  real browser produces from the same wiring. Reason: without it the
  test would have to dispatch `cancel` itself, which passes against a Dialog
  no keyboard user could close.

2. A guarded global `jest` shim. `@testing-library/react` 16.3.3
   `dist/pure.js` `asyncWrapper` awaits a `setTimeout(0)` and flushes it only
   when `jestFakeTimersAreEnabled()` - `typeof jest !== 'undefined'` **and**
   `setTimeout` has an own `clock` property (the fake-timers marker). The shim
   is a getter on `globalThis.jest` returning
   `{ advanceTimersByTime: ms => vi.advanceTimersByTime(ms) }` only while
   `Object.hasOwn(globalThis.setTimeout, "clock")`, `undefined` otherwise, so
   tests on real timers (and the Date-only fakes in `AppShell`/`routes`) see
   no `jest` at all.

**Why the shim and not `vi.useFakeTimers({ shouldAdvanceTime: true })`.**
The boundary assertions need the fake clock to move only when the test moves
it. `shouldAdvanceTime` advances the fake clock by real elapsed time (every
`advanceTimeDelta`, default 20 ms) in the background; the toast timer starts
inside `await user.click(...)`, so real time spent between that click and
`advance(5_999)` is added to the 5 999 ms and can carry the toast past
6 000 ms before the "still present" assertion reads it - an exact-boundary
test made dependent on machine speed, i.e. a CI flake. The shim calls
`vi.advanceTimersByTime(0)`: it fires the zero-delay timer RTL is waiting on
and moves the clock by nothing. The 1 ms resolution is demonstrated below in
both directions (5 000 and 6 001). Known limit, recorded in the setup
comment: `@testing-library/dom`'s `waitFor`/`findBy*` also consult `jest`,
and under a faked `setTimeout` advance the fake clock by their polling
interval. No current test fakes `setTimeout` and uses them.
