CAL-054 added `e2e/downscale.spec.ts`, the only test of the downscaler's real
canvas path (`browserDeps`, `src/capture/downscale.ts:53-74`). Its size and
pixel assertions are earned (CAL-054's `drawImage`, width/height-swap and
`toBlob` mutants). Four of its other assertions are not:

- **`:210-212`, theatre.** `expect(decoded.byteLength).toBe(Buffer.from(posted.image,
  "base64").length)` decodes the same posted string twice (`atob` in the page,
  `Buffer` in Node) and compares the results. No implementation can make it
  fail. Confirmed by the orchestrator by reading the line on 2026-11-11.
- **`:215-216`, never seen to fail.** AC-2's JPEG start (`FF D8`) and end
  (`FF D9`) markers - added by CAL-054's RED amendment 1 precisely so that
  AC-2 was not vacuous - pass on arrival and no mutant has been run against
  them. The audit predicts `69s#mime,#"image/png",#` (the canvas asked for
  PNG while the request still says JPEG) fails them; not run, it needs Docker.
  They are two hard `expect`s in a row, so one mutant can only ever show the
  first of them failing: as written, `:216` cannot be seen to fail by the
  mutant that fails `:215`.
- **`:169`** (AC-1's `posted.mime` is `image/png`) and **`:228-230`** (AC-3's
  posted base64 is non-empty) are likewise unearned through the real canvas.

CAL-054's own Notes say the finding was "closed" by the width/height swap;
that holds for the size assertions only.

Test-only, in the integration gate: the downscaler is believed correct, so
each earned assertion passes on arrival and is earned by its mutant.

Required gate that would fail if this broke: `integration` (`pnpm exec
playwright test`, covers `e2e/**`; `optional` for the repository, bound here

## Acceptance criteria

- **AC-1** - Given the AC-2 case of `e2e/downscale.spec.ts` (a 1200 x 800
  JPEG), then no assertion in it compares a value with itself: the
  self-comparison at `:210-212` is removed or replaced by a check against an
  independent value, and the story's `## Notes` says which and why.
- **AC-2** - Given the same case, when the canvas is asked to encode PNG while
  the request is still labelled JPEG (`src/capture/downscale.ts`
  `69s#mime,#"image/png",#`), then the AC-2 case fails on its JPEG marker
  check, the failure output shows both the first two bytes (`[137, 80]`
  where `[255, 216]` is expected) and the last two (`[96, 130]` where
  `[255, 217]` is expected), and the AC-1 and AC-3 cases still pass.
- **AC-3** - Given the AC-1 case (a 3000 x 1000 PNG), when the page posts a
  wrong `mime` label (`src/capture/CapturePage.tsx`
  `153s#base64, mime }#base64, mime: "image/jpeg" }#`), then the AC-1 case
  fails on its `posted.mime` check.
- **AC-4** - Given the AC-3 case, when the encoder resolves an empty blob
  (`src/capture/downscale.ts` `68s#resolve(blob)#resolve(new Blob([]))#`),
  then the AC-3 case fails on its non-empty check, not on the 10 s wait.
