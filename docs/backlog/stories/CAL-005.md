## Context

EPIC-01. `architecture.md` puts one typed repository per table in `src/data/`,
the only code that calls supabase-js for data, and only `src/sync/` calls it.
This story builds the three the calendar needs first - `kinds`, `events`,
`eventOverrides` - with the two properties sync depends on later: an update
is conditional on the `updated_at` the client last saw (the conflict rule in
`architecture.md`, "Where state lives"), and a delete is always a soft delete.
The remaining repositories (`reminders`, `pushSubscriptions`, `captureJobs`)
are written by the stories that first need them.

Required gate that would fail if this broke: `unit` (MSW intercepts the
PostgREST HTTP calls; nothing here needs a database).

## Acceptance criteria

- **AC-1** - Given PostgREST rows in snake_case, when a repository returns
  them, then they are camelCase domain objects (`startsAt`, `kindId`,
  `allDay`, `deletedAt`…) with event times (`startsAt`, `endsAt`) as `Date`
  and the server's bookkeeping stamps (`createdAt`, `updatedAt`,
  `deletedAt`) kept as the server's exact strings, and writing maps them
  back; a round trip of every column of each table is the identity - byte
  for byte on every column except the `Date`-typed ones, which are equal as
  instants.
- **AC-2** - Given `kinds.listLive()`, when called, then it requests only rows
  with `deleted_at is null` ordered by `sort_order` ascending.
- **AC-3** - Given `events.listSince(t)` (and the same on `kinds` and
  `eventOverrides`), when called, then it requests rows with `updated_at > t`
  **including** soft-deleted rows, so a deletion on another device can be
  applied.
- **AC-4** - Given `update(id, patch, expectedUpdatedAt)` on any of the three,
  when the server matches one row, then it returns `{status: 'ok', row}`; when
  it matches zero rows (the request filters on both `id` and `updated_at`),
  then it returns `{status: 'conflict'}` and does not throw.
- **AC-5** - Given `remove(id, expectedUpdatedAt)`, when called, then it issues
  a PATCH setting `deleted_at` - never an HTTP DELETE - with the same
  conflict semantics as AC-4.
- **AC-6** - Given a 4xx response, when any call is made, then it returns
  `{status: 'error', code, message}`; given a network failure, it returns
  `{status: 'offline'}`. Neither throws.

### Why the client is injected

`src/lib/supabase.ts` builds its client from `import.meta.env` at import
time and is mocked whole by every existing test. These repositories take
the client as a parameter instead, so a test can hand them a real
supabase-js client pointed at a fake origin that MSW intercepts, and the
production caller (`src/sync/`, later) passes the one from `src/lib/supabase.ts`.
Nothing in `src/data/` imports `src/lib/supabase.ts`.

### Domain types and mappers (`src/data/rows.ts`, `rows.test.ts`) - AC-1

- Row types come from the generated file:
  `type KindRow = Database["public"]["Tables"]["kinds"]["Row"]` etc.
- `export type Kind = { id: string; name: string; colorLight: string; colorDark: string; sortOrder: number; isDefault: boolean; deletedAt: string | null; createdAt: string; updatedAt: string }`
- `export type Recurrence = { freq: "daily" | "weekly" | "yearly"; until: string | null; tz: string }`
  (`until` is a `YYYY-MM-DD` date string, as stored).
- `export type Event = { id: string; title: string; kindId: string; startsAt: Date; endsAt: Date; allDay: boolean; location: string | null; notes: string | null; recurrence: Recurrence | null; origin: "manual" | "capture"; captureJobId: string | null; deletedAt: string | null; createdAt: string; updatedAt: string }`
- `export type EventOverride = { id: string; eventId: string; occurrenceDate: string; cancelled: boolean; title: string | null; kindId: string | null; startsAt: Date | null; endsAt: Date | null; allDay: boolean | null; location: string | null; notes: string | null; createdAt: string; updatedAt: string }`
  (`occurrenceDate` is a `YYYY-MM-DD` string - a calendar date, not an
  instant, so never a `Date`.)
- **Why the stamps stay strings:** `updatedAt` is the token the conditional
  update sends back as `updated_at=eq.<token>`; Postgres renders it with
  microseconds and `Date` keeps milliseconds, so a `Date` round trip would
  make every update a conflict. `createdAt`/`deletedAt` follow the same rule
  for consistency. `startsAt`/`endsAt` are user-authored instants the client
  writes at millisecond precision, so `Date` is lossless for them.
- Mappers, one pair per table, total functions (no throwing):
  `toKind(row: KindRow): Kind`, `fromKind(kind: Kind): KindRow`;
  `toEvent`/`fromEvent`; `toEventOverride`/`fromEventOverride`.
  `from*` writes `Date` as `date.toISOString()`; `to*` parses with
  `new Date(value)`. `recurrence` is validated structurally by `toEvent`
  (`freq` in the three values, `tz` a string) - a malformed JSON object maps
  to `null` and is the one lossy case, stated here.
- Insert and patch shapes: `export type NewKind = Omit<Kind, "id" | "createdAt" | "updatedAt" | "deletedAt">`
  (and `NewEvent`, `NewEventOverride` likewise), `export type KindPatch = Partial<NewKind>`
  (and the two others). `fromKindPatch(patch: KindPatch): Partial<KindRow>`
  maps only the keys present (a patch of `{}` is `{}`; `undefined` values are
  dropped), so a PATCH body never carries a column the caller did not name.
- **AC-1's identity test:** for a fixture row carrying every column with a
  non-null, non-default value (and a second with every nullable column
  null), `fromX(toX(row))` equals `row` byte for byte on every column except
  the `Date`-typed ones, which are compared as `Date.parse` instants.
  Fixtures use timestamps the server would return (`+00:00` suffix,
  microseconds on the bookkeeping stamps, none on event times) so the
  comparison is meaningful.

### Results (`src/data/result.ts`) - AC-4, AC-6

- `export type Result<T> = { status: "ok"; row: T } | { status: "conflict" } | { status: "error"; code: string; message: string } | { status: "offline" }`
- `export type ListResult<T> = { status: "ok"; rows: T[] } | { status: "error"; code: string; message: string } | { status: "offline" }`
- `export function fromPostgrest<Row, T>(res: { data: Row[] | null; error: PostgrestError | null; status: number }, map: (r: Row) => T): ListResult<T>`
  and `export function fromPostgrestOne<Row, T>(res, map): Result<T>` -
  `data` of exactly one row → `ok`; of zero rows → `conflict`; `error` with
  an HTTP status ≥ 400 → `error` (`code` = PostgREST `error.code`, e.g.
  `PGRST301`, `23505`, `42501`; `message` = `error.message`); **no HTTP
  response** → `offline`.
- **Offline is a mechanism RED measures.** supabase-js v2 catches a rejected
  `fetch` and resolves `{ data: null, error: { message: "TypeError: Failed
  to fetch", code: "", … }, status: 0 }` in the shape this Contract
  *expects*; RED confirms the exact `status`/`code` an MSW
  `HttpResponse.error()` produces with the installed supabase-js 2.117 and
  records it, amending this block if the discriminator is different. The
  rule to implement is whatever discriminates "no HTTP response" from
  "HTTP ≥ 400" in that measurement - never `message` string matching.

### Repositories (`kinds.ts`, `events.ts`, `eventOverrides.ts`)

All three have the same shape; `KindsRepo` is spelled out, the others
substitute their types. Factory signature:
`export function kindsRepo(client: SupabaseClient<Database>): KindsRepo`.

- `listLive(): Promise<ListResult<Kind>>` -
  `GET /rest/v1/kinds?select=*&deleted_at=is.null&order=sort_order.asc`
  (AC-2). `events.listLive()` orders by `starts_at.asc`;
  `eventOverrides.listLive()` by `occurrence_date.asc`. (An override has no
  `deleted_at`; its `listLive` has no `deleted_at` filter.)
- `listSince(since: string): Promise<ListResult<Kind>>` -
  `GET /rest/v1/kinds?select=*&updated_at=gt.<since>` with **no**
  `deleted_at` filter (AC-3), ordered by `updated_at.asc`. `since` is the
  exact server string from the last sync, never a `Date`.
- `insert(input: NewKind): Promise<Result<Kind>>` -
  `POST /rest/v1/kinds` with `Prefer: return=representation`, body
  `fromKind`-shaped without `id`/stamps; `select=*` so the row comes back.
- `update(id: string, patch: KindPatch, expectedUpdatedAt: string): Promise<Result<Kind>>` -
  `PATCH /rest/v1/kinds?id=eq.<id>&updated_at=eq.<expectedUpdatedAt>&select=*`
  with `Prefer: return=representation`, body = `fromKindPatch(patch)`.
  One row back → `ok`; `[]` → `conflict` (AC-4). The builder uses
  `.select()` (array), never `.single()`, so zero rows is data, not a
  `PGRST116` error.
- `remove(id: string, expectedUpdatedAt: string): Promise<Result<Kind>>` -
  the same PATCH with body `{ deleted_at: <now ISO> }`; **never** HTTP
  `DELETE` (AC-5). `now` is `new Date().toISOString()`; tests pin the
  method and the body key, and that the value parses as an instant within
  the test's run. `eventOverridesRepo` has **no** `remove` - an override is
  hard-deleted or cancelled by its owner story; this story gives it
  `listLive`, `listSince`, `insert`, `update` only. (Overrides have no
  `deleted_at` column; a `remove` here would have nothing to set.)
- Every method resolves; none throws (AC-6). supabase-js is called with
  `throwOnError` left off.

### Test harness (`src/test/msw.ts`)

- `export const server = setupServer()` (msw 2, already a dev dependency);
  `export function installServer(): void` - `beforeAll(() => server.listen({ onUnhandledRequest: "error" }))`,
  `afterEach(() => server.resetHandlers())`, `afterAll(() => server.close())`.
- `export const TEST_ORIGIN = "http://supabase.test"`;
  `export function testClient(): SupabaseClient<Database>` -
  `createClient<Database>(TEST_ORIGIN, "test-anon-key", { auth: { persistSession: false, autoRefreshToken: false } })`.
  PostgREST requests therefore hit `http://supabase.test/rest/v1/<table>`,
  which MSW intercepts in Node (undici). Tests assert on
  `request.method`, `new URL(request.url)` (path and `searchParams`),
  `request.headers.get("prefer")`, and `await request.json()`.
- Under jsdom (the `unit` project's environment) `fetch` is Node's; MSW's
  `setupServer` intercepts it. RED confirms this with the first passing
  interception and records it; if jsdom's environment breaks it, the data
  tests get `// @vitest-environment node` at the top of each file (a
  per-file directive, not a config change).
