## Context

EPIC-02. Source: `docs/wiki/audits/EPIC-02-2026-11-25.md`, Decided 4 and
Evidence `### E-WHOLE` (W10, W11). The legend CAL-008 built
(`src/kinds/KindLegend.tsx`) behaves correctly today. What is missing is a test
for each of two of its rules, so either can be broken with all 3423 unit tests
green:

- **W10, `KindLegend.tsx:68`.** The shortcut handler returns early for every
  key that is not `l` or `L`. With that line dropped, **every** key pressed
  outside a text field toggles the legend: Tab, Enter, Space, the arrows. The
  existing tests press only `l`, `L` and Escape, so nothing notices. This is
  the highest-impact gap the audit found. It would make the shell unusable
  from the keyboard.
- **W11, `KindLegend.tsx:98`.** After an outside pointerdown closes the legend,
  a deferred check returns focus to the opener only when the pointer left focus
  on `<body>` (the Block 2 amendment: "When that pointer put focus on another
  control, it keeps it"). With the check replaced by `if (true)`, a click into
  a text field outside the open legend has its focus pulled back to the Legend
  button. The one outside-pointer test clicks plain text, so it cannot tell.

This is a test-only story: the production code is right, and the tests pin it.
Each new test passes on arrival, so it has to be earned by putting the audit's
mutant back (see `## Deferred verifications`).

Required gate that would fail if this broke: `unit` (required). It runs
`src/kinds/KindLegend.test.tsx`.

## Acceptance criteria

- **AC-1** - Given the legend is closed, focus is on `<body>` and no modifier
  key is held, when the user presses one of `k`, `Enter`, Space, `Tab`,
  `ArrowDown`, `ArrowUp`, `ArrowLeft` or `ArrowRight`, then `onToggle` is not
  called and no legend is shown, and this holds for each of the eight keys;
  and when the user then presses `l` with focus on the Legend button, the
  legend opens (the anchor that proves the listener is live).
- **AC-2** - Given the legend was opened with a click on the Legend button and
  is open, when the user clicks the harness's "Notes" text input, which is
  outside the legend, then the legend closes, `onToggle` was last called with
  `false`, and once the deferred focus return has run, `document.activeElement`
  is that input and not the Legend button.

- **Shape:** one `it.each` over those eight rows, so each key is its own test
  with its own render. Title:
  `"%s pressed outside a text field does not toggle the legend (CAL-091 AC-1)"`.
- **Where:** the last test inside the existing
  `describe("the L shortcut (AC-2, Block 2)", ...)`, after "L pressed inside
  an open modal dialog does not toggle the legend". That describe's "AC-2"
  is CAL-008's numbering; the `CAL-091` tag in the title is what tells them
  apart.
- **Target of the key:** `document.body`. The test calls `renderLegend()` with
  `repo.listAll` resolving `rows(MOVIES)`, focuses nothing, and first asserts
  `document.activeElement` is `document.body`. Focus is in no text field and
  on no control. The key is pressed once, with no modifier held.
- **Why `<body>` and not the Legend button:** Enter and Space on a focused
  button click it, and the harness's Legend button opens the legend on click.
  That would show a legend under correct code, for a reason that has nothing
  to do with the shortcut handler.
- **Assertions after the key:** `onToggle` not called (`not.toHaveBeenCalled()`)
  and `queryLegend()` is null.
- **The anchor, same test:** `legendButton().focus()`, then
  `user.keyboard("l")`, then `legend()` is in the document. The explicit focus
  is needed because `Tab` moves focus from `<body>` into the "Notes" input,
  where `l` is typing. It is the same move the file's other anchors make.
- **Modifiers:** none of the eight is pressed with a modifier. `L` with
  Control, Meta or Alt is already pinned by the existing `it.each`, and that
  rule is `KindLegend.tsx:69`, not `:68`.
- **Not in the list, on purpose:** Escape while closed. It returns at `:63`,
  before `:68` is reached, so the W10 mutation cannot earn a case for it and
  it would be an assertion nobody watched fail. A bare Control, Meta or Alt
  press is left out for the same reason: `:69` returns for it even with `:68`
  broken.

### Block 3 - AC-2, the outside click that keeps focus

- **Shape:** one `it`. Title: `"a pointer going down on a text field outside
  the legend closes it and leaves focus in that field (CAL-091 AC-2)"`.
- **Where:** inside the existing
  `describe("closing the legend and returning focus (AC-2, Block 2)", ...)`,
  directly after "a pointer going down outside the legend closes it and
  returns focus to Legend", so the two outside-pointer cases read together.
- **Setup:** `renderLegend()` with `rows(MOVIES)`, then `openWithClick(user)`.
  The opener is therefore the Legend button, which is where a wrong focus
  return would land.
- **The target that keeps focus:** `screen.getByLabelText("Notes")`, the
  harness's `<input type="text">`. It is a real focusable element, it is
  outside the legend's root, and it is not a `[data-legend-toggle]`. The test
  clicks it with `user.click`, so the pointerdown closes the legend and the
  click's own mousedown puts focus in the input.
- **Assertions, in this order:** `queryLegend()` is null;
  `onToggle` last called with `false`; then the wait below; then
  `expect(document.activeElement).toBe(notes)` and
  `expect(legendButton()).not.toHaveFocus()`.
- **The wait, and why it is not `vi.waitFor`:** the production code decides
  inside a `setTimeout(..., 0)` queued during the pointerdown. A negative
  claim ("focus did not move") polled with `vi.waitFor` passes on its first
  poll, possibly before that timer has run, and then proves nothing. So after
  the click the test awaits one macrotask of its own,
  `await new Promise((resolve) => setTimeout(resolve, 0));`, and asserts
  after it. Timers with the same delay fire in the order they were queued,
  and the component's was queued first. The file uses real timers; this test
  must not install fake ones. The W11 mutation is what proves the wait is
  long enough: if the test stays green with `:98` broken, the wait is wrong.
