## Context

The case "no tracked text file assigns a literal to any of the six secret
names" (`src/deploy/noSecrets.test.ts:378`, CAL-030 AC-5, EPIC-08) runs on
vitest's default 5000 ms limit and has timed out in the full unit project on
this machine at least four times, in four stories, none of which touched it.
Each time it was cleared by running again:

- `docs/backlog/stories/CAL-065.md:27-29`: unit project, 2999 of 3000, the one
  failure this timeout (no figure kept).
- `docs/backlog/stories/CAL-066.md:45-46`: unit project, the one failure this
  timeout (no figure kept).
- `docs/backlog/stories/CAL-069.md:370-372`: `coverage`, 7290 ms. (`:509-511`
  says 8070 ms; that is the file's total in the same log, not the case's.)
  `:533`: it did not recur on CI.
- CAL-071 `## Notes`, "GATES full run 1" (on branch
  `story/CAL-071-the-downscaler-e2e-spec-s-jpeg-and-byte`, not yet on `main`):
  `coverage`, 6985 ms, `unit` at 152 s against 57-69 s idle; "GATES full run
  2" on the same tree passed (`coverage` 64 s).

Where the time goes is in `## Notes`, "What was measured at PLANNED". In
short: the scan is not slow. Alone it takes 135-160 ms, with or without
coverage instrumentation, so nothing in the file is worth making cheaper. In a
full run on a busy host the same work has taken 45 times that. What stretches
it is not shown by any evidence on record.

The decision (PO, 2026-11-18): give that one case an explicit budget derived
from the recorded durations by the house's quarter rule (`tdd-cycle`, "The
gates run your tests differently": a test stays under a quarter of its
timeout, measured under local instrumentation). The scan itself does not
change. The alternative, moving the search out of the test, and why it was
not taken, is in `## Notes`, "Decision".

Required gates that fail if this breaks: `unit` and `coverage`. Both run this
file; neither is optional. Test-only story: no source or config changes, so
GREEN is a verified no-op (as in CAL-069 and CAL-071).

## Acceptance criteria

- **AC-1** - Given the unit project runs `src/deploy/noSecrets.test.ts`, when
  the case "no tracked text file assigns a literal to any of the six secret
  names" runs, then the timeout vitest holds for that case equals
  `SCAN_TIMEOUT_MS`, a constant of that file, and is not the framework default
  of 5000 ms.
  *Control:* with the timeout option taken off that case (the defect put
  back), this check fails and reports 5000.
- **AC-2** - `SCAN_TIMEOUT_MS` is the smallest multiple of 5000 ms that is at
  least 4 x `SCAN_MAX_RECORDED_MS`, and a check in the file fails when either
  literal is changed without the other. `SCAN_MAX_RECORDED_MS` is the largest
  duration vitest has reported for that case in an instrumented run of the
  whole unit project, over every row of this story's "Measurements" table
  (`## Notes`): the rows on record at PLANNED and the five runs RED adds
  before it edits the file. No row is left out and no run is repeated to
  replace one.
  *Control:* `SCAN_MAX_RECORDED_MS` doubled alone fails the check (the budget
  is under 4x); `SCAN_TIMEOUT_MS` raised by 5000 alone fails it too (not the
  smallest). At the 7290 ms on record the budget is 30 000 ms.
- **AC-3** - Given a quoted literal planted on a real tracked line that names
  a secret (`supabase/functions/capture/handler_test.ts`, the first line
  naming the Gemini key, through `scripts/mutate.sh`), when the file runs,
  then that case fails and its message names that path, that line number and
  the secret's name; the enumeration case ("the scan enumerates the tracked
  tree through git") still passes; and with the line restored the whole file
  passes.
- **AC-4** - Given the committed change, when the whole unit project runs
  under coverage instrumentation three times in a row, then the case passes
  in all three, each duration vitest reports for it is at most
  `SCAN_MAX_RECORDED_MS` (so under a quarter of its budget), and the three
  figures are in the "Measurements" table with each run's total duration.
  *Control:* the same case under the old limit is on record failing at 6985
  and 7290 ms.

### Decision (PO, 2026-11-18): a measured budget, not a cheaper scan

- **Taken: (b), an explicit budget on the one case.** The work is ~150 ms and
  already reads the file list once, so there is no waste to remove. The house
  already prescribes this for a whole-collection loop (`tdd-cycle`: "Set an
  explicit, generous timeout on ... anything that loops over a generated
  collection") and does it in `CalendarPage.test.tsx:2593-2602` and
  `geminiBoundary.test.ts:93-103`. The scan's detection is untouched by
  construction, and AC-3 shows it.
- **Not taken: (a), make the scan cheaper.** The only change that cuts the
  work by much is to stop opening every file in the test: let `git grep` name
  the 16 files that contain a name and match only those. That replaces the
  reading half of a secrets guard, needs its own proof that tracked,
  untracked, ignored, deleted and binary files are treated as before, and is
  aimed at a cause nobody has measured. An in-process prefilter keeps all 637
  opens and saves about 60 of 150 ms.
- **What would change this.** The stop rule in `## Contract` (a run over
  15 000 ms), or the budget being exceeded after this story merges. Either
  one says the cost is unbounded and (a), or a spike on the cause, is next.
- **For the user, before RED, only if you disagree:** this is the cheaper and
  safer of the two, and it does not make the case any faster on a busy host;
  it stops a 7 s run from failing a gate. Say so if you want (a) instead.
