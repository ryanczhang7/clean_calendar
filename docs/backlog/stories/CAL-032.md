## Context

EPIC-01, from `docs/wiki/audits/epic-01-2026-10-15.md` (Decided 2, Evidence
E-SQL-3, mutants M3 and M4). `public.is_owner()` in
`supabase/migrations/0001_core_schema.sql` is the real enforcement of "one
allowed account". Measured on 2026-10-15 in rolled-back transactions against
the shipped migration: with `app_config.owner_email` set to `''` or `'   '`,
`is_owner()` returns **true** for a JWT whose `email` claim is `'   '`. The
guard `coalesce(auth.jwt() ->> 'email', '') <> ''` tests the claim before
trimming, and the trimmed equality then compares `''` with `''`. CAL-003's
client rule (`isOwnerEmail`, "both sides are normalised BEFORE the emptiness
check, so an owner configured as spaces admits nobody") refuses the same
case, so the two disagree. Severity is low. It needs an operator to blank
`owner_email` (no CHECK prevents it) and a token with a whitespace e-mail
claim. But this is the security predicate, and no test pins its emptiness
rule: removing the guard entirely (M4) passes all 129 db tests.

A second, smaller gap is M3. Only the claim side's `lower(trim())` is
tested, because the seed owner is already lower-case. If the owner side
loses its normalisation, an owner configured as `Owner@Example.com` is
locked out by RLS while the client admits them.

Required gate that would fail if this broke: `db` (optional repo-wide, so it
is in `required_gates`).

## Acceptance criteria

- **AC-1** — Given `app_config.owner_email` is `''` or only whitespace, when
  `public.is_owner()` is evaluated as `authenticated` with an `email` claim
  of `''`, `'   '`, or no claim, then it returns `false`. A test fails
  against the migration as shipped today (it returns `true` for
  `owner_email = ''` and claim `'   '`), and fails again when the
  emptiness guard is removed (`select coalesce(...) <> ''` → `select true`,
  audit M4).
- **AC-2** — Given `app_config.owner_email` is stored with upper-case letters
  and surrounding spaces (e.g. `'  Owner@Example.COM '`), when `is_owner()`
  is evaluated with the claim `owner@example.com`, then it returns `true`.
  A test fails when `lower()` or `trim()` is removed from the **owner** side
  of the comparison only (audit M3).
- **AC-3** — Every existing `is_owner()` case in
  `supabase/tests/schema.db.test.ts` and every `rls.db.test.ts` case still
  passes, and `app_config` ends each test holding the seeded
  `owner@example.com` row (tests that change it restore it).

### Pinned blocks

**Block 1 — the migration body.** `supabase/migrations/0002_is_owner_blank_claim.sql`:

```sql
-- CAL-032: is_owner() refuses a blank claim when the configured owner is
-- blank. 0001 tested the claim for emptiness BEFORE trimming, so a claim of
-- '   ' against an owner_email of '' compared '' with '' and was admitted.
-- Both sides are normalised first, then both must be non-empty and equal -
-- the same rule as CAL-003's isOwnerEmail. Same OID, same grants: the
-- policies' rendered `is_owner()` is untouched.
create or replace function public.is_owner()
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select claim <> '' and owner <> '' and claim = owner
  from (
    select
      lower(trim(coalesce(auth.jwt() ->> 'email', ''))) as claim,
      lower(trim(coalesce(
        (select owner_email from public.app_config limit 1), ''))) as owner
  ) as sides
$$;
revoke execute on function public.is_owner() from public, anon;
grant execute on function public.is_owner() to authenticated, service_role;
```

The guard is the one line `claim <> '' and owner <> '' and`; removing it is
audit M4 put back (`'' = ''` is true). The owner side's `lower(trim(` is
audit M3's target. `create or replace` keeps the function's OID, so
`pg_policies.qual` still renders `is_owner()` and
`src/data/database.types.ts` needs no regeneration (signature unchanged).

**Block 2 — the truth table** (owner × claim → `is_owner()`), as
`authenticated` with `request.jwt.claims` set for the transaction:

| `''` | `''` | false | AC-1 |

**Block 3 — the test shape.** One new `describe` in
`supabase/tests/schema.db.test.ts`, after the existing predicate `describe`,

`{ sub: … }` with no `email` key, like the existing case. No new helper
exports are required; if RED adds one to `helpers.ts`, name it in the
handoff.
