## Context

EPIC-07: the gym reminder must fire every week, the birthday every year.
`architecture.md`, "Reminders": each scheduler run first materialises a
`reminders` row per occurrence of a recurring event starting in the next 48
hours that does not yet have one, using the template row (`occurrence_date
null`) and the shared expander (`shared/recurrence.ts`, CAL-023) under Deno,
then fires due rows exactly as CAL-028 does. The unique
`(event_id, occurrence_date)` index from CAL-004 makes materialisation
idempotent.

Required gates that would fail if this broke: `deno-test`, `deno-check`.

## Acceptance criteria

- **AC-1** - Given a weekly series with a 30-minute template reminder, when the
  run at Monday 08:00 materialises, then one row per occurrence starting
  before Wednesday 08:00 exists with `occurrence_date` set and the template's
  `minutes_before`, and a second run creates none (inserts conflicting on
  `(event_id, occurrence_date)` are ignored).
- **AC-2** - Given a cancelled override for an occurrence in the window, when
  materialising, then no row is created for it; given an override that moves
  its start to 10:00, the materialised row fires 30 minutes before 10:00.
- **AC-3** - Given a materialised row, when it is due, then the push's `url`
  points at the occurrence's date (`/day/{occurrence date}?event={series id}`)
  and its body shows the occurrence's time.
- **AC-4** - Given the series' `recurrence.tz` of `Europe/London` and a 09:00
  weekly occurrence on Monday 26 October 2026 (after the DST change), when it
  is materialised, then it fires at 08:30 London time, 08:30 UTC.
- **AC-5** - Given a series that is soft-deleted, or whose template reminder is
  soft-deleted, when the run happens, then nothing is materialised or fired
  for it.

**Block 2 - `materialise.ts`, pure, no I/O.**
`supabase/functions/send-reminders/materialise.ts`:

```ts
import type { Occurrence, Override, Recurrence, Series } from "../../../shared/recurrence.ts";

export const LOOKAHEAD_MS = 48 * 3_600_000;   // AC-1: "the next 48 hours"
export const LOOKBACK_MS = 5 * 60_000;        // equal to handler.ts's WINDOW_MS, by value

/** One embedded reminder of a series, materialised or the template. */
export type SeriesReminderRow = {
  id: string;
  minutes_before: number;
  sent_at: string | null;
  occurrence_date: string | null;   // null = the template
  deleted_at: string | null;
};
export type OverrideRow = {
  occurrence_date: string;
  cancelled: boolean;
  title: string | null;
  kind_id: string | null;
  starts_at: string | null;
  ends_at: string | null;
  all_day: boolean | null;
  location: string | null;
  notes: string | null;
};
/** One row of the series read (Block 4), PostgREST shape. */
export type SeriesRow = {
  id: string;
  title: string;
  kind_id: string;
  starts_at: string;
  ends_at: string;
  all_day: boolean;
  location: string | null;
  notes: string | null;
  recurrence: unknown;              // jsonb; validated by toRecurrence
  reminders: SeriesReminderRow[];
  event_overrides: OverrideRow[];
};
export type NewReminder = {
  event_id: string;
  occurrence_date: string;
  minutes_before: number;
};
/** A live materialised row joined to the occurrence it is for. */
export type OccurrenceReminder = {
  id: string;
  minutes_before: number;
  sent_at: string | null;
  occurrence: Occurrence;
};
export type Plan = {
  inserts: NewReminder[];
  candidates: OccurrenceReminder[];
  skipped: { seriesId: string; reason: string }[];
};

export function toRecurrence(value: unknown): Recurrence | null;
export function toSeries(row: SeriesRow, recurrence: Recurrence): Series;
export function toOverride(row: OverrideRow): Override;
export function liveTemplate(row: SeriesRow): SeriesReminderRow | null;
export function expansionRange(now: Date): Range;
export function plan(rows: readonly SeriesRow[], now: Date): Plan;
```

Semantics, one sentence per number:

- `toRecurrence` is `src/data/rows.ts`'s rule, verbatim: a non-array object
  with `freq` one of `daily|weekly|yearly`, `tz` a string, `until` a string
  or null; anything else is `null`.
- `toSeries` maps snake to camel and parses `starts_at`/`ends_at` with
  `new Date(...)`; `toOverride` likewise, with `null` kept as `null` (null =
  keep the series value), exactly `src/sync/useOccurrences.ts`'s `toOverride`
  one level up.
- `liveTemplate` is the one embedded reminder with `occurrence_date === null
  && deleted_at === null`, else `null` (AC-5: a soft-deleted template is no
  template).
- `expansionRange(now)` is `{ start: now − LOOKBACK_MS, end: now + LOOKAHEAD_MS }`,
  half-open as `expand` reads it. The 5-minute lookback exists so that an
  occurrence whose reminder fires inside the due window is still returned
  by `expand` when the occurrence itself has already started or ended (a
  one-minute event with `minutes_before = 0` three minutes ago). Both
  materialisation and the due look-up use this one range.
- `plan(rows, now)`, for each row **in order**:
  1. `toRecurrence(row.recurrence)` null → `skipped` with reason
     `"recurrence"`; nothing else for that series.
  2. `liveTemplate(row)` null → the series contributes **nothing**: no
     inserts, no candidates (AC-5). Not recorded in `skipped`: it is the
     normal state of a series without a reminder.
  3. `expand(toSeries(row, rec), row.event_overrides.map(toOverride), expansionRange(now))`;
     a throw → `skipped` with reason `String(err.message)`, nothing else.
  4. For each occurrence, in `expand`'s order: if **no** embedded reminder
     has that `occurrence_date` - in any state, deleted or sent included -
     push `{ event_id: row.id, occurrence_date, minutes_before: template.minutes_before }`
     onto `inserts` (AC-1; a soft-deleted materialised row stays deleted,
     which is CAL-057's door). A cancelled override's occurrence is not
     returned by `expand`, so it is never inserted (AC-2).
  5. For each embedded reminder with `occurrence_date !== null &&
     deleted_at === null` whose `occurrence_date` matches an occurrence
     from step 3, push `{ id, minutes_before, sent_at, occurrence }` onto
     `candidates`. A materialised row whose occurrence is no longer returned
     (cancelled since, or outside the range) is not a candidate. The
     candidate's `minutes_before` is the **row's**, not the template's.
  Rows inserted this run are not candidates this run: they have no id yet,
  and the next run, one minute later, finds them well inside the window.

`fireAt` for a materialised row is `occurrence start − minutes_before`
(AC-2's moved occurrence: the override's 10:00, so 09:30). `startsAt` in
the payload is the occurrence's start, overrides applied, as an ISO instant
with milliseconds (`toISOString()`), so the worker's existing `reminderBody`
shows the occurrence's time and `reminderUrl` derives the day from it
(AC-3; PO decision 1 below). `eventId` is the **series** id, never an
override's. The response body becomes
`{ due, sent, pruned, failed, materialised }`, `materialised` the number of
rows the POST of Block 4 step 2 carried (0 when it was skipped).

The run, in order (numbers continue CAL-028 Block 2's; 1-3 are unchanged -
service-role check, method, VAPID):

4. GET the non-recurring candidates (CAL-028's `CANDIDATES_QUERY`, unchanged).
   Null → 502 `{error:"upstream"}`.
5. GET the series (Block 4 step 1). Null → 502, before anything is written
   or pushed.
6. `p = plan(series, now)`. Each `p.skipped` entry logs one line
   `send-reminders: series {seriesId} skipped: {reason}`; the run continues.
7. If `p.inserts` is non-empty, POST them (Block 4 step 2). A non-2xx or a
   throw logs `send-reminders: materialising {n} reminders failed: {status|message}`
   and the run **continues** to fire what exists; `materialised` then
   reports the rows the POST carried, not what the server kept.
8. `due = [...dueReminders(rows, now) as plain, ...dueOccurrences(p.candidates, now)]`,
   plain rows first in response order, then candidates in `plan`'s order.
   `counts.due` is the length of that list. Empty → 200 with the counts and
   **no** subscriptions read (CAL-028 step 5 still holds).
9-11. Unchanged: one subscriptions read, the push loop with the gone-set and
   the DELETE, one PATCH of `sent_at` per due row by its id - a materialised
   row's id is its own row's. The payload for a plain row is `payloadFor`,
   for a candidate `payloadForOccurrence`.

**Block 4 - the two PostgREST calls, verbatim.** Base `${SUPABASE_URL}/rest/v1`,
headers `apikey` and `authorization: Bearer <service key>` as CAL-028.

1. The series read, one GET:
   `events?select=id,title,kind_id,starts_at,ends_at,all_day,location,notes,recurrence,reminders(id,minutes_before,sent_at,occurrence_date,deleted_at),event_overrides(occurrence_date,cancelled,title,kind_id,starts_at,ends_at,all_day,location,notes)&deleted_at=is.null&recurrence=not.is.null`
   A soft-deleted series is excluded **here** (AC-5); its reminders and
   overrides come embedded, in every state, so `plan` can see which
   occurrences already have a row. The embeds are left joins: a series with
   no reminder arrives with `reminders: []`.
2. The materialisation, one POST, only when there is something to insert:
   `POST reminders?on_conflict=event_id,occurrence_date` with headers
   `prefer: resolution=ignore-duplicates,return=minimal` and
   `content-type: application/json`, body the JSON array of `NewReminder`
   in `plan`'s order. `on_conflict` names the columns of
   `reminders_event_occurrence_key` (`unique nulls not distinct`, migration
   0001), and `ignore-duplicates` makes PostgREST emit `on conflict do
   nothing`: a second run, or two runs racing, creates no row (AC-1). This
   header pair is the mechanism claim of the story - Deferred verification 2
   proves it against the real stack.

The test's routing table is keyed by `METHOD url` after `decodeURIComponent`,
as CAL-028's is, so the implementation may percent-encode; the parameters
and their order may not change.

**Block 5 - what AC-4 pins, with numbers.** Series: weekly, `tz:
"Europe/London"`, first occurrence Monday 19 October 2026 09:00 BST =
`2026-10-19T08:00:00Z` (ends 10:00 BST), template `minutes_before: 30`.
Clocks go back on Sunday 25 October 2026 01:00 UTC. Run at `now =
2026-10-24T10:00:00Z` (Saturday): `expansionRange` is
`[2026-10-24T09:55:00Z, 2026-10-26T10:00:00Z)`, so the one occurrence in it
is Monday 26 October 09:00 GMT = `2026-10-26T09:00:00Z`, `occurrenceDate
"2026-10-26"`; the inserted row is `{event_id, "2026-10-26", 30}`. A run at
`now = 2026-10-26T08:31:00Z` with that row embedded fires it: `fireAt` =
`2026-10-26T08:30:00Z`, inside `[08:26, 08:31]`. Expanding in UTC instead
would put the occurrence at `08:00Z` and the fire at `07:30Z`, which is the
Deferred verification 1 mutation and what makes the Chicago-style control
below discriminate. Note `now` must be **after** 09:00Z on the Saturday if
the test wants Monday 09:00Z inside a 48 h half-open range: `10:00Z` is
chosen so the occurrence is 1 h inside the end, not on it.

**Block 6 - AC-1's numbers.** Weekly series, first occurrence Monday 2
November 2026 08:30 `tz: "UTC"` (so the fixture reads plainly), run at
