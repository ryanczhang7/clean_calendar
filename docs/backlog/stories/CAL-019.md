## Context

EPIC-05, brief §4.3: the Android share sheet's commonest payload is a
**screenshot** of the booking e-mail. Gemini 2.5 Flash takes images inline
(`inline_data` with a MIME type and base64 bytes) in the same
`generateContent` call, so this story extends the CAL-018 function's input
rather than adding a function. The image is never stored; only its hash is
(`architecture.md`, "Limits worth knowing").

Required gates that would fail if this broke: `deno-test`, `deno-check`.

## Acceptance criteria

- **AC-1** - Given a POST `{image: <base64>, mime: 'image/png'}` (or
  `image/jpeg`, `image/webp`) with the owner's JWT, when the handler runs,
  then the Gemini request carries one `inline_data` part with that MIME type
  and the same base64 payload, plus the prompt text part with the kind names,
  and the reply is handled exactly as for text.
- **AC-2** - Given an image whose decoded size exceeds 4 MB, the handler
  returns 413; given any other MIME type, 415. Gemini is not called.
- **AC-3** - Given both `text` and `image`, when the handler runs, then only
  the image is sent (`components.md`: the image wins).
- **AC-4** - Given an image capture, when the job row is written, then
  `input_kind` is `'image'` and `input_hash` is the SHA-256 hex of the
  **decoded bytes**, not of the base64 string.
- **AC-5** - Given base64 that does not decode, the handler returns 400.

### Block 1 - the request body and its checks (AC-2, AC-3, AC-5)

`handler.ts` keeps `MAX_TEXT_CHARS` and adds:

```ts
export const MAX_IMAGE_BYTES = 4 * 1024 * 1024;   // 4,194,304 decoded bytes; that many passes, one more is 413
export const IMAGE_MIME_TYPES = ["image/png", "image/jpeg", "image/webp"] as const;
```

The body is JSON. **If it has an `image` key, the image path is taken and
`text` is ignored entirely** (AC-3; PO decision 3) - the user's text appears
in no part of the Gemini request. Otherwise CAL-018's text path runs
unchanged. On the image path, in this order (PO decision 7), each step
returning JSON `{error}` as CAL-018 does:

1. `image` not a string, or the body not JSON -> **400** `{error: "bad_request"}`.
2. `mime` not exactly one of `IMAGE_MIME_TYPES` (lowercase, no parameters;
   missing counts) -> **415** `{error: "unsupported_media_type"}`.
3. `image` not strict standard base64 (PO decision 6: alphabet
   `A-Za-z0-9+/`, `=` padding only at the end and at most two, length a
   multiple of 4, no whitespace, no `-`/`_`, not empty) -> **400**
   `{error: "bad_request"}`.
4. decoded length `> MAX_IMAGE_BYTES` -> **413** `{error: "payload_too_large"}`.

None of these fetches anything, and none writes a job row. Only then the
owner check (403), the kinds read, Gemini and the row, exactly as in
CAL-018 Block 2 steps 4-9.

### Block 2 - the Gemini request with an image (AC-1)

`gemini.ts`:

```ts
export type InlineImage = { mimeType: string; data: string };   // data = the base64 exactly as received
export type GeminiPart = { text: string } | { inline_data: { mime_type: string; data: string } };
export type GeminiRequest = {
  contents: [{ role: "user"; parts: GeminiPart[] }];
  generationConfig: { /* unchanged */ };
};
export function buildGeminiRequest(prompt: string, image?: InlineImage): GeminiRequest;
export async function callGemini(args: { prompt: string; image?: InlineImage; apiKey: string; base: string; fetch: typeof fetch; now: () => number }): Promise<GeminiOutcome>;
```

- With an image, `parts` is exactly `[{ inline_data: { mime_type, data } }, { text: prompt }]`:
  the image part first, then the prompt. `data` is the base64 string as
  received, byte for byte (not re-encoded). `mime_type` is the request's
  `mime`.
- Without an image, `parts` is `[{ text: prompt }]` as today, so every
  existing `gemini_test.ts` assertion (`buildGeminiRequest("PROMPT TEXT")`,
  `assertEquals(JSON.parse(call.body), buildGeminiRequest("the prompt"))`)
  holds unchanged. The second argument is optional for that reason.
- The REST field names are snake_case, `inline_data` / `mime_type`, as the
  story's Context says. **Checkable, not sacred**: v1beta accepts camelCase
  too; if RED or GREEN finds the snake_case form rejected, amend this block
  with what was measured.
- The response path, the headers, the URL, `generationConfig` and the three
  outcomes are unchanged.

### Block 3 - the prompt for an image

`prompt.ts` keeps `buildPrompt(text, kindNames)` unchanged (its tests in
`gemini_test.ts` are frozen and pass today) and adds:

```ts
export function buildImagePrompt(kindNames: readonly string[]): string;
```

Same rules block as `buildPrompt` (every live kind name verbatim, no guessed
dates, nulls for the unknown, the confidence/missing vocabulary), but the
message section says the message is the attached image (a screenshot, most
often of a booking e-mail) and that the event is to be read from it. The
prompt contains no user text. Wording is GREEN's; the test asserts the kind
names and the absence of the `<<<` text delimiter.

### Block 4 - the job row for an image (AC-4)

`input_kind: "image"`; `input_hash` is the lowercase SHA-256 hex of the
**decoded bytes**. Settled vector: `image: "YWJj"` (the bytes `abc`) with
`mime: "image/png"` gives `input_hash`
`ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`, which is
NOT the hash of the string `"YWJj"`
(`sha256("YWJj") = 35d95694d3f160215db293c7899daa5907837838fb4b8119ed713e32446c1266`,
computed with `sha256sum` at PLANNED; RED pins both). The MIME type is not checked against the
bytes (PO decision 5), which is what makes a three-byte "image" a legal test
input. Every other column is as in CAL-018: `model`, `status`, `error`,
`latency_ms`, `proposal`, `confidence`. Neither the base64 nor the bytes
appear in any column; the test asserts the serialised row body does not
contain the base64 string.

### Block 5 - oracle partition

- **Settled:** the three MIME strings; the byte limit 4,194,304 (accepted) /
  4,194,305 (413); the status codes 400/413/415 and their `error` strings;
  the part order and field names; the two SHA-256 vectors (`abc` bytes vs
  `"YWJj"` string); `input_kind "image"`.
- **Oracle-free, with a control:** AC-4 "over the bytes, not the base64" -
  the control is Deferred verification 1; AC-3 "the image wins" - Deferred
  verification 2.
- **Mechanical:** the base64 rejections (whitespace, URL-safe alphabet, bad
  length, `!`, empty, padding in the middle), the check order (a 5 MB
  non-base64 string is 400, not 413; an oversized image from a non-owner is
  413 with no owner call), "nothing fetched" on 400/413/415, the text path
  unchanged (all 46 CAL-018 handler tests still pass in GREEN).

### PO decisions at PLANNED (Lead PO, 2026-10-26)

1. **Gates.** `deno-test` and `deno-check` (required) read
   `supabase/functions/**`; `unit`/`coverage` read `shared/**`. Every artifact
   has a required gate; `required_gates` stays empty.
2. **No new function, no new module.** The image path extends CAL-018's
   handler and Gemini client in place (Contract). `shared/captureSchema.ts` is
   expected NOT to change: the request body is not a shared schema, and the
   reply is handled exactly as for text (AC-1).
3. **The image path is taken whenever `image` is present**, whatever `text`
   holds (AC-3, `components.md`: "the image wins"). An `image` that is present
   but not a string is 400, like a `text` that is not a string.
4. **4 MB is 4,194,304 bytes of DECODED image** (`4 * 1024 * 1024`);
   exactly that many is accepted, one more is 413. Measured after decoding,
   not estimated from the base64 length.
5. **The MIME type is trusted, not sniffed.** CAL-020 sets it from the
   `File`; a wrong type is the model's problem, not a 415. `image/png`,
   `image/jpeg` and `image/webp`, exact and lowercase; anything else,
   including a missing `mime`, is 415.
6. **Base64 is standard, strict:** the alphabet `A-Z a-z 0-9 + /`, `=`
   padding only at the end, length a multiple of 4, no whitespace, no
   URL-safe `-`/`_`, not empty. Anything else is 400 (AC-5). GREEN chooses
   the decoder (`Uint8Array.fromBase64`, `atob`, or `@std/encoding`); the
   test pins only the verdicts.
7. **Check order for an image:** bearer (401) -> body is JSON with an
   `image` string (400) -> MIME (415) -> base64 decodes (400) -> size (413)
   -> owner (403) -> kinds -> Gemini. So a 5 MB payload that is not base64
   is 400, and an oversized PNG from a non-owner is 413 before 403, as with
   CAL-018's text checks, which precede the owner check. No job row before
   Gemini, as in CAL-018 (PO decision 3 there).
8. **Epic done-when.** "Share image ... reaches the same confirm screen" needs
   this function (here) and CAL-020/022 (the screens and the share target).
   No gap for this story to close.
