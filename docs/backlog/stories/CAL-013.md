## Context

EPIC-03, brief §4.1: move and delete events. Drag is the pointer path, and
every move also has a keyboard path and the sheet's date fields
(`accessibility.md`, "Keyboard paths"; `components.md`, Concern 2). Delete
needs no confirmation because it can be undone (`components.md`, "Undo toast
for delete"); a delete is a soft delete (CAL-005), so undo is clearing
`deleted_at`. Toast copy: `voice.md`, "Toasts".

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given an event, when `moveEvent(event, newStart)` is computed, then
  the end moves by the same amount so the duration is kept, and an all-day
  event moved to another day keeps its day count.
- **AC-2** - Given a chip dropped on another month cell (pointer events on the
  drag source and a drop on the target cell), when the drop lands, then the
  event's date changes and its time of day is kept; dropped on a time-grid
  slot, it starts at that slot. The sheet does not open, and the toast
  "Moved to {Wed 14 Oct, 10:00}" with "Undo" appears.
- **AC-3** - Given a focused chip, when `Alt+→` is pressed in the month view,
  then the event moves one day later; in week/day view `Alt+↓` moves it 15
  minutes later and `Alt+Shift+↓` lengthens it by 15 minutes ("Now ends at
  {11:30}" with Undo).
- **AC-4** - Given the sheet's "Delete {title}" button or `Delete` on a focused
  chip, when it is used, then the event disappears from the view at once,
  `removeEvent` is called, and "Deleted {title}" with "Undo" is shown.
- **AC-5** - Given the undo toast, when "Undo" is pressed or `Ctrl+Z` is
  pressed while it shows, then a moved event returns to its previous start and
  end, and a deleted event is restored with `deleted_at` cleared.

### Block 1 - `src/domain/moveEvent.ts` (pure)

```ts
import type { Event } from "../data/rows";
export type Span = { startsAt: Date; endsAt: Date };
type Movable = Pick<Event, "startsAt" | "endsAt" | "allDay">;
export const STEP_MINUTES = 15;
/** AC-1. Timed: the end moves by the same elapsed milliseconds as the start.
 *  All-day: `newStart` is read as a calendar day (its local midnight) and the
 *  end keeps the same number of calendar days - local midnights, so a move
 *  across a DST change still lands on midnight. */
export function moveEvent(event: Movable, newStart: Date): Span;
/** Month drop and month Alt+arrows: the date becomes `day`, the local time of
 *  day is kept (timed); all-day → moveEvent(event, day). */
export function moveToDay(event: Movable, day: Date): Span;
/** Time-grid drop: timed → starts at `slotStart`; all-day → moveToDay(event, slotStart)
 *  (it stays all-day, PO decision 2). */
export function moveToSlot(event: Movable, slotStart: Date): Span;
/** Alt+Shift+↓/↑: the end moves by `minutes` (±15). Null when the event is
 *  all-day, or when the new end would be less than STEP_MINUTES after the start. */
export function resizeBy(event: Movable, minutes: number): Span | null;
/** "Moved to Wed 14 Oct, 10:00" - date-fns `EEE d MMM, HH:mm`; all-day:
 *  "Moved to Wed 14 Oct" (`EEE d MMM`). No relative words (PO decision 5). */
export function movedLabel(span: Span, allDay: boolean): string;
/** "Now ends at 11:30" - `HH:mm` of `endsAt`. */
export function resizedLabel(span: Span): string;
/** "Deleted {title}". */
export function deletedLabel(title: string): string;
```

Worked examples (all local): timed 14 Oct 09:00-10:30, `moveEvent` to 15 Oct
14:00 → 15 Oct 14:00-15:30; all-day `[12 Oct, 15 Oct)` (three days) moved to
20 Oct → `[20 Oct, 23 Oct)`; all-day `[30 Oct, 2 Nov)` moved to 31 Oct →
`[31 Oct, 3 Nov)`, both ends at 00:00 local across the DST change;
`moveToDay` of 14 Oct 09:00-10:30 to 16 Oct → 16 Oct 09:00-10:30, and of
31 Oct 09:00-10:00 to 2 Nov → 2 Nov 09:00-10:00 (wall time kept across DST);
`moveToSlot` of 14 Oct 09:00-10:30 to 15 Oct 14:00 → 15 Oct 14:00-15:30;
`resizeBy` of 10:00-11:15 by +15 → 10:00-11:30, of 10:00-10:15 by -15 →
null, of 10:00-10:30 by -15 → 10:00-10:15.

*Amended by RED, 2026-10-20:* the all-day DST example above (`[30 Oct, 2 Nov)`
→ 31 Oct) does **not** tell a calendar-day implementation from an elapsed-ms
one - both spans cross the same change, 73 h each, and elapsed-ms also lands
on 3 Nov 00:00 (measured with node in America/Chicago). It stays, and two
contrasts are added that do discriminate: `[29 Oct, 31 Oct)` → 31 Oct is
`[31 Oct, 2 Nov)` (elapsed-ms: 1 Nov 23:00) and `[31 Oct, 2 Nov)` → 5 Nov is
`[5 Nov, 7 Nov)` (elapsed-ms: 7 Nov 01:00). Timed contrasts: `30 Oct 23:00 -
31 Oct 03:00` → 31 Oct 23:00 ends **1 Nov 02:00** (wall-time: 03:00);
`31 Oct 22:00 - 1 Nov 02:00` → 2 Nov 09:00 ends **14:00** (wall-time: 13:00);
`resizeBy` of 10:00-10:20 by -15 → **null** (an "end after start" rule gives
10:05). `moveToDay` reads only the date of `day` (16 Oct 18:45 counts as
16 Oct), and an all-day `moveEvent` reads only the date of `newStart`.
**The zone is pinned in `moveEvent.test.ts`** with `vi.stubEnv("TZ",
"America/Chicago")` and a first case asserting the offsets (300 on 31 Oct,
360 on 2 Nov): without it, under `TZ=UTC` (a CI runner's default) every DST
contrast is blind and two expected values are wrong - measured against a
throwaway candidate in RED (Handoff, negative controls).

### Block 2 - the repository and the store learn restore and hide

```ts
// src/data/events.ts - EventsRepo gains one member
restore(id: string, expectedUpdatedAt: string): Promise<Result<Event>>;
```
`restore` is `patchIfUnchanged(id, { deleted_at: null }, expectedUpdatedAt)`
- the mirror of `remove` (`components.md`, Undo toast: "undo is a patch of
`deleted_at = null`"). `events.test.ts` pins the body and both `eq` filters
the way its `remove` case does.

```ts
// src/sync/eventsStore.ts - EventsStore gains one member
/** Hide one event from every snapshot at once (AC-4's "disappears at once").
 *  It stays hidden across refreshes until the returned reveal() is called. */
hide(id: string): () => void;
```
`hide` publishes synchronously a snapshot without that event; `reveal()`
publishes one with it again if the store's rows still hold it (after a
successful delete, the refresh has already dropped it, so nothing returns).
Hiding twice and revealing once leaves it hidden only if the second hide is
still outstanding (a count per id). `getSnapshot()` stays referentially
stable between changes.

*Amended by RED, 2026-10-20:* each returned `reveal()` acts **at most once** -
calling the same one twice must not release a second, still-outstanding
`hide` of that id (pinned: "one reveal() called twice counts once").

### Block 3 - `src/sync/eventActions.ts`

```ts
export type EventActions = {
  createEvent(input: NewEvent): Promise<Result<Event>>;                                   // as CAL-012
  updateEvent(id: string, patch: EventPatch, expectedUpdatedAt: string): Promise<Result<Event>>; // as CAL-012
  /** AC-4. Hides the event at once, then repo.remove(id, event.updatedAt). */
  removeEvent(event: Event): Promise<Result<Event>>;
  /** AC-5. repo.restore(deleted.id, deleted.updatedAt) - `deleted` is the row removeEvent returned. */
  restoreEvent(deleted: Event): Promise<Result<Event>>;
};
export function createEventActions(
  repo: Pick<EventsRepo, "insert" | "update" | "remove" | "restore">,
  store: Pick<EventsStore, "refresh" | "hide">,
): EventActions;
```
`removeEvent`: `const reveal = store.hide(event.id)` **before** the write is
sent; ok → `await store.refresh()`, then `reveal()`, then the result; non-ok
→ `reveal()` (the event comes back) and the result, no refresh. Everything
else keeps CAL-012's discipline (nothing throws; ok refreshes before
resolving; non-ok is returned as is). The **move** is `updateEvent(id, {
startsAt, endsAt }, event.updatedAt)`; its undo is `updateEvent(id, {
startsAt: before.startsAt, endsAt: before.endsAt }, moved.updatedAt)` where
`moved` is the row the move returned - the undo carries the token the move
produced, not the original one.

### Block 4 - `src/calendar/useChipDrag.ts`

```ts
export type DropTarget = { kind: "day"; day: Date } | { kind: "slot"; start: Date };
export const DRAG_THRESHOLD_PX = 4;
export function useChipDrag(onDrop: ((event: Event, target: DropTarget) => void) | undefined): {
  /** Spread onto the chip: undefined members when onDrop is undefined. */
  chipProps(event: Event): { onPointerDown?: PointerEventHandler<HTMLElement>; onClickCapture?: MouseEventHandler<HTMLElement> };
  /** True while a drag is in progress (for the ghost styling; not asserted by markup tests). */
  dragging: boolean;
};
```
Semantics: a primary-button `pointerdown` on a chip arms a drag and records
`clientX/clientY`; a `pointermove` on `document` at least
`DRAG_THRESHOLD_PX` from that point starts it. A `pointerup` on `document`
while dragging resolves the drop target: the element from
`document.elementFromPoint(clientX, clientY)` when that function exists and
returns an element, else the `pointerup` event's own target; then
`closest("[data-drop-day], [data-drop-slot]")`. `data-drop-day` holds
`yyyy-MM-dd` (that local day), `data-drop-slot` holds `yyyy-MM-dd'T'HH:mm`
(that local slot start). No target, or `Escape` during the drag, cancels:
no `onDrop`. A `pointerup` before the threshold is an ordinary click (the
sheet opens as in CAL-012). After a drag that started, the `click` the
browser fires on the chip is swallowed (`onClickCapture` →
`preventDefault` + `stopPropagation`), so **the sheet does not open**
(AC-2). Listeners are removed on `pointerup`, cancel and unmount. In jsdom
`elementFromPoint` is absent, so tests dispatch `pointerup` on the target
cell itself (story Notes); whether `fireEvent.pointerMove` carries
`clientX/Y` in this jsdom is for RED to check - if it does not, amend the
threshold rule here with the reason.

*Amended by RED, 2026-10-20 (measured, jsdom 30.1.2):* `PointerEvent` exists,
and `fireEvent.pointerDown/Move/Up(el, { clientX, clientY, button })` carry
those values into the event, so the threshold rule stands as written.
`document.elementFromPoint` is absent. `fireEvent` leaves `isPrimary` false,
so **"primary" means `button === 0`**: do not also require `isPrimary`. The
tests pin the threshold on one axis only (3 px right: no drag; 4 px right and
4 px down: drag); the metric on a diagonal is the implementer's. The
swallowed click is **disarmed** once consumed, and must not outlive the next
interaction: a drop whose click a browser fires on the common ancestor (not
the chip) must not eat the next genuine click - pinned with a later task's
plain `pointerdown`/`pointerup`/`click`, so clearing at the next
`pointerdown` or at the end of the drop's task both satisfy it. One case
installs `document.elementFromPoint` and pins that it is called with the
`pointerup`'s `clientX, clientY` and decides the target; another pins the
fallback to the event target when it returns null.

### Block 8 - `src/calendar/CalendarPage.tsx`

The page owns the writes and the toasts (`const toast = useMaybeToast()`; no
toast is shown when it is null, and nothing throws - the CAL-009/011/012 page

- `onDropEvent(event, target)`: the new span is `moveToDay(event,
  target.day)` or `moveToSlot(event, target.start)`; unchanged instants → no
  write, no toast. Otherwise `actions.updateEvent(event.id, span,
  event.updatedAt)`; on ok, toast `{ text: movedLabel(span, event.allDay),
  action: { label: "Undo", undo: true, onClick: undo } }` where `undo`
  writes the previous span back with the moved row's `updatedAt` (Block 3).
- `onChipCommand(event, command, chip)`:
  - "delete" → the delete path below.
  - month view: "left"/"right" → `moveToDay` ±1 day; "up"/"down" → ±7 days
    (PO decision 3); "lengthen"/"shorten" → nothing.
  - week/day view: "left"/"right" → `moveToDay` ±1 day; "up"/"down" →
    `moveEvent(event, startsAt ± 15 min)` for a timed event, nothing for an
    all-day one; "lengthen"/"shorten" → `resizeBy(event, ±15)`, null →
    nothing; a resize toasts `resizedLabel(span)` with Undo.
  - after a keyboard move or resize, focus stays on the moved chip: the page
    focuses the chip of that event id once the store has refreshed
    (`[data-event-id]` - EventChip gains `data-event-id={event.id}` on its
    button; RED may pin another hook with a reason).
  - *Amended by RED, 2026-10-20:* every move and every resize writes the
    **whole span and nothing else** - `updateEvent(event.id, { startsAt,
    endsAt }, event.updatedAt)`, the patch compared with `toStrictEqual` (an
    all-day drop on a slot sends no `allDay`; a resize sends the unchanged
    start too). The `[data-event-id]` focus hook is pinned as written.
- Delete (sheet button or `Delete` on a chip): `actions.removeEvent(event)`
  (the event leaves the view at once - Block 3's hide); on ok, toast `{
  text: deletedLabel(event.title), action: { label: "Undo", undo: true,
  onClick: () => actions.restoreEvent(removedRow) } }`. Focus after a chip
  delete moves to the month gridcell that held it, or the time grid's tab
  stop cell; from the sheet, CAL-012's opener rule applies (the opener is
  gone, so nothing is focused by the sheet).
- Any non-ok write (move, resize, delete, or either undo) → toast `{ text:
  "Couldn't save. Try again.", tone: "alert" }` (CAL-012's copy, `voice.md`);
  the store is untouched by a refused update, and a refused delete is revealed
  (Block 3).
- Undo pressed twice, or after the toast was replaced, does nothing more: the
  closure runs its write at most once.
