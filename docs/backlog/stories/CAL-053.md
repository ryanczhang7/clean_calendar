## Context

EPIC-05. Source: `docs/wiki/audits/epic-05-2026-10-31.md` (Decided 5;
Evidence E-STRYKER `src/capture/CapturePage.tsx`, E-RECHECK R6 to R10).

`CapturePage.tsx` (CAL-020 Block 3, CAL-022 Block 5) numbers each request with
`runs` and drops a reply whose number is stale. Stryker left 34 of its 202
mutants alive. The 12 gaps below were rechecked where marked, and survive the
whole unit project (2,386 tests):

- `:88-90`, the unmount effect that bumps `runs`, removed. A reply that arrives
  after the owner has left `/capture` still calls
  `navigate("/capture/confirm")` and pulls them back (R6).
- `:135` and `:179`, `runs.current += 1` → `-= 1` in `run` or in Cancel. The
  counter returns to an earlier value. A cancelled request's late reply is then
  accepted as current once a new request is under way (R10).
- `:137`, `:146`, `cancelled()` never true. A Cancel pressed while the
  screenshot is being shrunk does not stop the request: `propose` is still
  called. Its reply is dropped later, at `:161`.
- `:148`, `setWorking(false)` → `true` after a failed shrink. "Asking the
  assistant…" and Cancel stay on screen beside the alert, and Propose stays
  blocked (R7).
- `:200`, the file input is not cleared on "Remove screenshot". Choosing the
  same file again then fires no `change` in a browser (R8). jsdom can show only
  that the input's `value` is not reset.
- `:254`, `file !== undefined` → `true`. A `change` with an empty `FileList` (a
  picker re-opened and dismissed) attaches `undefined` as the screenshot (R9).

Test-only: the shipped page is believed correct, so each assertion passes on
arrival and is earned by its audit mutant.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given a text capture in flight (the `propose` stub unresolved),
  when the owner navigates to another route, and the stub then resolves `ok`,
  then the location is still that other route. A test fails under
  `89s#runs.current += 1;#void 0;#`.
- **AC-2** - Given request A in flight, when the owner presses Cancel, presses
  Propose event again (request B, still unresolved), and A then resolves `ok`,
  then the page does not navigate. When B then resolves `ok`, it navigates with
  B's response. A test fails under `179s#+= 1#-= 1#` and under `+= 1` → `-= 1`
  at `:135`.
- **AC-3** - Given a screenshot whose `downscale` stub is unresolved, when the
  owner presses Cancel and the stub then resolves `ok`, then `propose` is never
  called. A test fails with `:137`'s `token !== runs.current` replaced by
  `false`.
- **AC-4** - Given a screenshot whose `downscale` resolves `too_large` (and, as
  a separate case, `unsupported`), when the owner presses Propose event, then
  the alert shows, no `role="status"` element shows the working text, Cancel is
  absent, and Propose event is not `aria-disabled`. A test fails under
  `148s#setWorking(false)#setWorking(true)#`.
- **AC-5** - Given a picked screenshot, when the owner presses "Remove
  screenshot", then the file input's `value` is `""`. A test fails under
  `200s#fileInput.current.value = "";#void 0;#`.
- **AC-6** - Given the empty capture screen, when the file input fires `change`
  with an empty `FileList`, then no screenshot is attached: no "Remove
  screenshot" button, and Propose event is still blocked. A test fails under
  `254s#if (file !== undefined) pick(file);#pick(file as File);#`.
