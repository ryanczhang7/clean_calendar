## Context

EPIC-05. Source: `docs/wiki/audits/epic-05-2026-10-31.md` (Decided 6;
Evidence E-STRYKER `src/capture/downscale.ts`).

`downscaleImage` (`src/capture/downscale.ts`, CAL-020 Block 2) is well pinned
through its injected `DownscaleDeps`: 58 of 61 non-`browserDeps` mutants are
killed. The real implementation, `browserDeps` (`createImageBitmap` plus a
canvas and `toBlob`, lines 53-75), says "Untested in jsdom". **All 17 of its
Stryker mutants survive**, among them:

- `context.drawImage(...)` deleted: every screenshot is sent to Gemini as a
  blank canvas of the right size;
- `decode` returning `{}`: width and height undefined;
- the `toBlob` promise never settling: Propose spins forever;
- the null-context and null-blob checks inverted.

jsdom has neither `createImageBitmap` nor a 2D canvas, so no unit test can
reach this code. The repository's `integration` gate (`pnpm exec playwright
test`, Chromium, `e2e/`) is the only real browser it has, and that gate is
optional, so this story lists it in `required_gates`.

Required gate that would fail if this broke: `integration` (bound by
`required_gates` above).

## Acceptance criteria

- **AC-1** - Given a 3000 x 1000 PNG whose left half is pure red and right half
  pure blue, when `downscaleImage(file)` runs with the default `browserDeps` in
  Chromium, then it resolves `ok` with width 2048 and height 683, and the
  returned `dataUrl`, decoded again, is 2048 x 683 with a pixel near (100, 340)
  red and a pixel near (1948, 340) blue (each channel within 8 of the
  expected value). A test fails when `drawImage` is deleted (`64s#context.drawImage(source as CanvasImageSource, 0, 0, width, height);##`).
- **AC-2** - Given a 1200 x 800 JPEG, when `downscaleImage` runs with
  `browserDeps`, then it resolves `ok` with `mime: "image/jpeg"`, width 1200
  and height 800, and `bytes` equals the decoded length of `base64`. A test
  fails when `decode` returns `{}`
  (`56s#return { width: bitmap.width, height: bitmap.height, source: bitmap };#return {} as never;#`).
- **AC-3** - Given the same run as AC-1, then it settles within 10 s. A test
  fails, rather than hanging the suite, when the `toBlob` callback is replaced
  by a no-op.

  fallback, not an AC change).** The posted body is `CaptureInput`,
  `{ image, mime }` (`captureClient.ts:18`, built at `CapturePage.tsx:152-153`):

  `OPTIONS` preflight with permissive CORS headers and **aborts** the POST, so
  nothing reaches the functions runtime or the Gemini stub; the page then
  shows its offline note, which no case looks at.

## Test plan

One Playwright spec, `e2e/downscale.spec.ts` (project `chromium`), three
cases. Level: end-to-end is the cheapest level that can reach `browserDeps` -
jsdom has no `createImageBitmap` and no 2D canvas, and PO decision 1 took
the `/capture` route over a fixture page or Vitest browser mode. No helper
under `e2e/fixtures/` was needed; the helpers are local to the spec.

Each case: `beforeEach` opens `/capture` as the owner (`session.ts`'s
`owner` fixture, which injects the session) and waits for the "Capture"
heading. The fixture image is drawn on an `OffscreenCanvas` in the page and
`convertToBlob`'d, read back to Node as base64, and handed to the hidden
`input[type="file"]` with `setInputFiles({ name, mimeType, buffer })`. A
`page.route('**/functions/v1/capture')` answers the CORS preflight and aborts
the POST; `page.waitForRequest` (POST to `/functions/v1/capture`, timeout
10,000 ms) is armed before "Propose event" is clicked; the request's
`postDataJSON()` is `{ image, mime }`. The posted base64 is decoded in the
page (`createImageBitmap` + `OffscreenCanvas` + `getImageData`).

| Case | Asserts | AC | Oracle |
|---|---|---|---|
| `a 3000x1000 red\|blue PNG screenshot is sent ... shrunk to 2048x683 with its red left half and blue right half still drawn (AC-1)` | posted `mime` `image/png`; decoded size `{2048, 683}`; pixel (100, 340) within 8 of RGBA `255,0,0,255`, pixel (1948, 340) within 8 of `0,0,255,255` | AC-1 | size mechanical (`planDownscale`); pixels the AC's settled tolerance, 8 per channel |
| `a 1200x800 JPEG screenshot is sent as image/jpeg at its own 1200x800, and the posted base64 is a whole JPEG (AC-2)` | posted `mime` `image/jpeg`; decoded size `{1200, 800}`; decoded length = request's base64 decoded length (RED amendment 1); 0 < length <= 4 MiB; first bytes `FF D8`, last `FF D9` | AC-2 | mechanical |
| `shrinking the 3000x1000 screenshot settles and the request is sent within 10000 ms of Propose event (AC-3)` | the POST arrives within the 10,000 ms `waitForRequest` timeout; its `image` is non-empty; measured click-to-request ms < 10,000 | AC-3 | mechanical |

Edges: the size cap is exercised once above it (3000 -> 2048, with the
683 rounding) and once below it (1200 x 800, unscaled). The PNG-to-JPEG
fallback and quality steps are out of scope (already pinned through
`DownscaleDeps`). The pixels are sampled 924 px either side of the seam at
x = 1024, so resampling at the edge cannot affect them.
