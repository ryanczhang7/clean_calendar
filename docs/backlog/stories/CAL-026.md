## Context

EPIC-07, brief §4.6: a per-event reminder time. Split on 2026-11-03 (Notes,
PO decision 1): this story is the **sync layer** for `reminders`; the sheet's
Reminder field, saving it with the event, and the chip's bell are CAL-057.
Delivery is CAL-027 (the device) and CAL-028/029 (the scheduler).

`architecture.md`, Data model: a `reminders` row holds `minutes_before`; for
a non-recurring event there is one row with `occurrence_date null`; for a
series that row is the template the scheduler materialises per occurrence.
Reminders are cached, synced and written through the outbox like events
(CAL-014, CAL-015). What is already there: the Dexie table `db.reminders`
(`src/sync/db.ts`), `"reminders"` in `OutboxOp.table`, Realtime streaming the
table into the cache (`src/sync/realtime.ts`, with its own mapper), and the
generated types. What is not: a repository, the outbox and drain (both skip
`reminders` ops today, `outbox.ts:277` and `drain.ts:242`), catch-up
(`hydrate.ts` pulls three tables), a store, and a way to delete - the table
has no `deleted_at` (Notes, PO decision 2).

Required gates that would fail if this broke: `unit` (the sync layer), and
`db` for the migration (AC-6), so `db` is in `required_gates`.

## Acceptance criteria

- **AC-1** - Given an event with no reminder in the cache, when
  `setReminder(eventId, minutesBefore)` is called, then one reminder row is
  added to the cache (`eventId`, `minutesBefore`, `occurrenceDate: null`,
  `sentAt: null`, `deletedAt: null`), one `insert` op on `reminders` is
  queued, and the call resolves `{status: "ok", row}` with that row; offline
  it resolves at once and nothing reaches the repository until a drain run.
- **AC-2** - Given a live template row for that event, when `setReminder` is
  called with another value, then the same row (same `id`) takes the new
  `minutesBefore` and one `update` op `{minutesBefore}` is queued; with the
  same value nothing is queued. The cache never holds more than one template
  row (`occurrenceDate` null) per event.
- **AC-3** - Given a live template, when `clearReminder(eventId)` is called,
  then the row gets a `deletedAt` and one `delete` op is queued; when
  `setReminder` is then called, that same row is restored (one `restore` op)
  and given the new value (one `update` op, none if the value is unchanged),
  never a second insert.
- **AC-4** - Given queued `reminders` ops, when the drain runs online, then
  `insert`, `update`, `delete` and `restore` call the reminders repository's
  `insert(patch, id)`, `update`, `remove` and `restore` with the cache row's
  `updatedAt`; on `ok` the cache row takes the server's stamps, `deletedAt`
  included; on `conflict` the fresh row replaces the cache row and the
  conflict notice names the field "reminder"; `discardOp`, the sync status's
  Redo and its problems list handle a reminder op as they do an event op,
  titled by the reminder's event's title.
- **AC-5** - Given sync, when it hydrates and catches up, then `reminders` rows
  are pulled after overrides into the cache like the other tables (a row with
  a queued op is not overwritten), and `useReminder(eventId)` returns that
  event's live template row, or `null` when it has none, only a soft-deleted
  one, or only per-occurrence rows.
- **AC-6** - Given `supabase db reset`, when the schema is inspected, then
  `reminders` has a nullable `deleted_at timestamptz`, and a soft-deleted
  template still holds its `(event_id, occurrence_date)` key, so a second
  template insert for that event is refused.

**Block 2 - the row type (`src/data/rows.ts`).**

```ts
export type ReminderRow = Tables["reminders"]["Row"];          // the Postgres row, as EventRow
export type Reminder = {
  id: string;
  eventId: string;
  minutesBefore: number;        // may be negative: -540 is 09:00 on an all-day event's day (CAL-057)
  sentAt: string | null;
  occurrenceDate: string | null; // null = the template; a date = a row the scheduler materialised
  deletedAt: string | null;
  createdAt: string;
  updatedAt: string;
};
export type NewReminder = Omit<Reminder, "id" | "createdAt" | "updatedAt" | "deletedAt">;
export type ReminderPatch = Partial<Pick<NewReminder, "minutesBefore">>;
export type ReminderInsert = Omit<ReminderRow, Bookkeeping>;
export function toReminder(row: ReminderRow): Reminder;
export function fromNewReminder(input: NewReminder): ReminderInsert;
export function fromReminderPatch(patch: ReminderPatch): Partial<ReminderRow>;
```

Stamps stay strings, as on `EventOverride`. `src/sync/db.ts` drops its own
`ReminderRow` type; `db.reminders` becomes `Table<Reminder, string>`. The
Dexie schema stays `version(1)`: no index changes (`reminders: "id,
eventId"`), and an unindexed field needs no upgrade. A cached row with no
`deletedAt` key (written by Realtime before this story) counts as live
(`deletedAt == null`). `realtime.ts`'s private `ReminderPgRow` and exported
`toReminderRow` are replaced by `ReminderRow` and `toReminder` from
`rows.ts`, which now map `deleted_at`.

**Block 3 - the repository (`src/data/reminders.ts`).**

```ts
export type RemindersRepo = {
  listSince(since: string): Promise<ListResult<Reminder>>;   // updated_at > since, ascending, soft-deleted included
  insert(input: NewReminder, id?: string): Promise<Result<Reminder>>;
  get(id: string): Promise<Result<Reminder>>;                // zero rows -> conflict
  update(id: string, patch: ReminderPatch, expectedUpdatedAt: string): Promise<Result<Reminder>>;
  remove(id: string, expectedUpdatedAt: string): Promise<Result<Reminder>>;   // deleted_at = now
  restore(id: string, expectedUpdatedAt: string): Promise<Result<Reminder>>;  // deleted_at = null
};
export function remindersRepo(client: SupabaseClient<Database>): RemindersRepo;
```

Every write is `.eq("id", id).eq("updated_at", expectedUpdatedAt)`, as
`events.ts`'s `patchIfUnchanged`; the test style is `eventOverrides.test.ts`'s.

**Block 4 - the facade (`src/sync/reminderActions.ts`; AC-1 to AC-3).**

```ts
export type ReminderActions = {
  /** Set the event's template to `minutesBefore`: insert, update, or restore + update. */
  setReminder(eventId: string, minutesBefore: number): Promise<Result<Reminder>>;
  /** Soft-delete the event's live template; `ok` with `row: null` when there is none. */
  clearReminder(eventId: string): Promise<Result<Reminder | null>>;
};
export function createOutboxReminderActions(
  db: CalendarDb,
  drain: Pick<Drain, "run">,
  online?: () => boolean,          // default () => navigator.onLine
): ReminderActions;
export const reminderActions: ReminderActions;   // over the app's db and appDrain
```

- "The event's template" is the cache row with that `eventId` and
  `occurrenceDate === null` (`db.reminders.where("eventId")`), live or
  soft-deleted. Lookup and writes run in one Dexie transaction over
  `db.reminders` and `db.outbox`, as `overrideActions.ts`'s `upsert`.
- `setReminder`: no template -> `enqueueInsert(db, "reminders", {eventId,
  minutesBefore, sentAt: null, occurrenceDate: null})`; a live one ->
  `enqueueUpdate(db, "reminders", id, {minutesBefore})`, or nothing when the
  value is the same (resolves `ok` with the row); a soft-deleted one ->
  `enqueueRestore`, then `enqueueUpdate` unless the value is the same.
- `clearReminder`: a live template -> `enqueueDelete(db, "reminders", id)`;
  none, or only a deleted one -> nothing queued, `{status: "ok", row: null}`.
- Results follow `queuedResult`: `ok` with the cache row, a drain run kicked
  off when online, never awaited.

## Notes

- Planned 2026-10-12 by `/plan-product`; body written by the resumed lead-po

- **PO decision - all-day "At time".** `components.md` says an all-day event's
