## Context

EPIC-07, brief §4.6 and §6 ("requires the user to grant permission once"):
each device that should ring asks for notification permission and registers a
Web Push subscription with the server (`push_subscriptions`, one row per
device, upserted by endpoint). Prompt: `components.md`, "Notification
permission prompt" - never on first open, shown the first time a reminder is
chosen and on Settings → Notifications; copy in `voice.md`. The VAPID public
key reaches the client as `VITE_VAPID_PUBLIC_KEY`; the private key is a
function secret (CAL-028).

Required gate that would fail if this broke: `unit` (`Notification`,
`navigator.serviceWorker` and `PushManager` are stubbed).

## Acceptance criteria

- **AC-1** - Given permission is `default`, when the app opens, then no prompt
  is shown; when the form's Reminder field holds anything other than None -
  chosen now, or already set on the event when the form opened - then the card
  "Get reminders on this device" with "Allow notifications" and "Not now"
  appears inline under the field.
- **AC-2** - Given the card, when "Allow notifications" is pressed, then
  `Notification.requestPermission()` is called from that click handler; on
  `granted` the service worker registration's `pushManager.subscribe` is called
  with `userVisibleOnly: true` and the VAPID public key, and the subscription's
  endpoint, `p256dh`, `auth` and user agent are upserted by endpoint.
- **AC-3** - Given the answer `denied`, when the card updates, then it reads
  "Notifications are blocked for this site. Turn them on in your browser's
  site settings to get reminders here." and the reminder field stays editable.
- **AC-4** - Given permission already `granted`, when the app starts, then the
  subscription is re-read (or re-created if missing) and upserted with a fresh
  `last_seen_at`.
- **AC-5** - Given `/settings/notifications`, when it renders, then it shows the
  same card in the state matching the current permission - the ask when
  `default`, the blocked notice when `denied`, and "Notifications are on for
  this device." with no buttons when `granted`; on a device that is not an
  installed Android PWA (no `display-mode: standalone` match or a non-Android
  user agent) it adds "Reminders are only reliable on your phone when the app
  is closed."
- **AC-6** - Given "Not now", when it is pressed, then nothing is requested and
  the card hides: under the Reminder field it stays hidden for the rest of this
  session; on `/settings/notifications` it hides until that page is next
  opened, where it is shown again.

### Block 1 - `src/data/pushSubscriptions.ts` (the repository)

Shaped as `captureJobs.ts`: a factory over a client and one module singleton.

    export type PushSubscriptionInput = {
      endpoint: string; p256dh: string; auth: string; userAgent: string | null;
    };
    export type PushSubscriptionsRepo = {
      upsert(input: PushSubscriptionInput): Promise<Result<{ id: string; endpoint: string }>>;
    };
    export function pushSubscriptionsRepo(client: SupabaseClient<Database>): PushSubscriptionsRepo;
    export const pushSubscriptions: PushSubscriptionsRepo; // pushSubscriptionsRepo(supabase)

`upsert` is one request: `POST /rest/v1/push_subscriptions` with
`on_conflict=endpoint` and `select=id,endpoint` in the query, a `Prefer` header
carrying `resolution=merge-duplicates` and `return=representation`, and a body
of exactly `{ endpoint, p256dh, auth, user_agent, last_seen_at }`.
`last_seen_at` is `new Date().toISOString()` taken at the call - that is AC-4's
"fresh": the column's default only fires on insert, so an upsert that omits it
leaves a returning device's `last_seen_at` stale. No `id`, `created_at` or
`updated_at` in the body. Results go through `fromPostgrestOne` (`result.ts`):
one row `ok`, a rejected fetch `offline`, an HTTP error `error` with `http`.
It never throws. Schema, unique key and owner RLS (select/insert/update)
already exist: `supabase/migrations/0001_core_schema.sql:126-152,254-260`.

### Block 2 - `src/reminders/pushSubscription.ts` (the browser side; no JSX)

    export type PermissionState = "default" | "granted" | "denied" | "unsupported";
    export function permissionState(): PermissionState;
    export function isInstalledAndroidPwa(): boolean;
    export function vapidKeyBytes(base64url: string): Uint8Array;
    export type RegisterOutcome =
      | { status: "ok" }
      | { status: "skipped"; reason: "unsupported" | "not-granted" | "no-key" }
      | { status: "error" };
    export function registerThisDevice(
      repo?: Pick<PushSubscriptionsRepo, "upsert">,   // default: pushSubscriptions
    ): Promise<RegisterOutcome>;

- `permissionState()` is `"unsupported"` when any of `globalThis.Notification`,
  `navigator.serviceWorker` or `globalThis.PushManager` is missing; otherwise
  `Notification.permission`. jsdom has none of the three, so every existing
  suite sees `"unsupported"` and renders no card - that is what keeps the
  EventForm, EventSheet, routes and App suites unchanged.
- `isInstalledAndroidPwa()` is true only when
  `window.matchMedia("(display-mode: standalone)").matches` **and**
  `/Android/i.test(navigator.userAgent)`; false when `matchMedia` is missing.
  (`src/test/media.ts` answers false for a `display-mode` query today; RED may
  extend that helper - it is a test path - or stub `matchMedia` directly.)
- `vapidKeyBytes` decodes unpadded base64url (`-`→`+`, `_`→`/`, pad to a
  multiple of 4, `atob`). A real VAPID public key is 87 characters and decodes
  to 65 bytes whose first byte is `0x04`.
- `registerThisDevice` **never rejects**. In order: not `granted` →
  `skipped/not-granted` (`unsupported` → `skipped/unsupported`); the key is
  `import.meta.env.VITE_VAPID_PUBLIC_KEY`, read **at call time** (so
  `vi.stubEnv` works), empty or undefined → `skipped/no-key` with nothing
  subscribed; `reg = await navigator.serviceWorker.ready`;
  `sub = (await reg.pushManager.getSubscription()) ?? (await reg.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey: vapidKeyBytes(key) }))`
  - "re-read, or re-created if missing"; then
  `repo.upsert({ endpoint: sub.endpoint, p256dh, auth, userAgent: navigator.userAgent })`
  with `p256dh` and `auth` from `sub.toJSON().keys` (base64url strings - the
  form `supabase/functions/send-reminders/push.ts:47` hands to web-push).
  A thrown `subscribe`, missing keys, or a non-`ok` upsert → `{ status: "error" }`.
- It never calls `Notification.requestPermission()`. Only Block 3's click
  handler does.

### Block 3 - `src/reminders/PermissionCard.tsx` (+ `PermissionCard.module.css`)

    export const NOT_NOW_KEY = "cc.notifications.notNow"; // sessionStorage, value "1"
    export function PermissionCard(props: {
      placement: "form" | "settings";
      /** Called after the card removes itself (granted in the form, Not now). */
      onGone?: () => void;
    }): JSX.Element | null;

What it renders, from `permissionState()` read once at mount, then its own state:

| state | `placement="form"` | `placement="settings"` |
|---|---|---|
| `unsupported` | nothing | nothing |
| `default` | the ask, unless `sessionStorage[NOT_NOW_KEY] === "1"` → nothing | the ask, whatever the session flag says |
| `denied` at mount | nothing (no nagging on every sheet) | the blocked notice |
| `denied` answered in this card | the blocked notice | the blocked notice |
| `granted` | nothing | the status line |

- Markup: `<section aria-labelledby={titleId}>` (a region named "Get reminders
  on this device"); the title is a `<p id={titleId}>`, **not a heading** (the
  page keeps exactly one `<h1>`, and the sheet its own `<h2>`).
- The ask: title, `<p>` "Allow notifications so reminders can reach you when
  the app is closed.", `<button type="button">Allow notifications</button>`
  then `<button type="button">Not now</button>`. `type="button"` is
  load-bearing: under the Reminder field the card sits inside the event
  `<form>`, and a default button would submit it.
- Allow: the click handler calls `Notification.requestPermission()`
  **synchronously, before any `await`** (Chrome requires the user gesture).
  While it is pending the Allow button carries `aria-busy="true"` and a second
  click requests nothing. When it resolves: `granted` → `void
  registerThisDevice()` (not awaited - `serviceWorker.ready` never resolves
  where no worker is registered, and the card must not hang on it), then the
  form card unmounts and calls `onGone`, the settings card shows the status
  line; `denied` → the blocked notice; `default` (prompt closed) → the ask
  again, not busy.
- Blocked notice: the region and title stay; one `<p role="status" tabIndex={-1}>`
  "Notifications are blocked for this site. Turn them on in your browser's site
  settings to get reminders here."; no buttons. When it replaces the ask after
  an answer it takes focus (the focused Allow button is gone).
- Status line (settings, `granted`): region and title; one
  `<p role="status" tabIndex={-1}>` "Notifications are on for this device.";
  no buttons; takes focus when it replaces the ask.
- Not now: sets `sessionStorage[NOT_NOW_KEY] = "1"`, calls no
  `requestPermission`, renders nothing from then on, calls `onGone`. A
  remounted settings card ignores the flag (PO decision 2).
- Copy is `voice.md`, "Notification permission", character for character.
