## Context

EPIC-02. Source: `docs/wiki/audits/EPIC-02-2026-11-25.md`, Decided 5 and
Evidence `### E-WHOLE` (W06, W07, W08, W09). The kind editor's submit path
(`src/kinds/KindEditor.tsx:264-310`, CAL-007) behaves correctly today. Four of
its lines can each be broken with all 3423 unit tests green:

- **W07, `:307` `event.preventDefault()` dropped.** The editor's `<form>`
  (`:360`) has no `method` or `action`. Without the call, a Save in a real
  browser submits it as a GET to the current URL, and the whole app reloads
  while the write is in flight. jsdom does not navigate, so no unit test can
  see it unless it asks whether the default was prevented. No e2e spec saves
  a kind (audit E-E2E). This one has the highest impact of the four.
- **W08, `:308` the busy guard dropped.** Save is not `disabled` while a save
  is pending, only `aria-busy` (`:353`). Without the guard, a second press
  before the first write settles sends a second `addKind`. That gives two
  cache rows with one name, and the server refuses the second on the
  live-name unique index.
- **W06, `:299` `setBusy(false)` -> `setBusy(true)`.** After a refused save,
  `busy` stays set, so every later press returns at `:308`. The alert says
  "Try again" and trying again does nothing. The existing refusal cases
  (`KindEditor.test.tsx:352-373`) stop at the alert. This is the shape
  CAL-088 fixed on the event sheet.
- **W09, `:276` `setFailed(false)` -> `setFailed(true)`.** The alert strip
  "Couldn't save. Try again." shows during every pending save.

This is a test-only story: the production code is right, and the tests pin it.
Each new test passes on arrival, so it has to be earned by putting the
audit's mutant back (see `## Deferred verifications`).

Required gate that would fail if this broke: `unit` (required). It runs
`src/kinds/KindEditor.test.tsx`.

## Acceptance criteria

- **AC-1** - Given the editor open on an existing kind with a changed, valid
  name, when Save is pressed, then the form's `submit` event reaches the
  document with `defaultPrevented` true, and `updateKind` is called once.
- **AC-2** - Given the "Add kind" editor with a valid name and an `addKind`
  that has not resolved yet, when Save is pressed twice, then `addKind` has
  been called exactly once. When it then resolves `ok`, the editor closes,
  and `addKind` has still been called exactly once.
- **AC-3** - Given the editor open on an existing kind whose first
  `updateKind` resolves `{ status: "offline" }` and whose second resolves
  `ok`, when Save is pressed, the alert strip shows; when Save is pressed
  again, then `updateKind` has been called twice with the same arguments and
  the editor closes.
- **AC-4** - Given a save whose `updateKind` has not resolved yet, while it is
  pending, no `role="alert"` element is inside the editor dialog. And given a
  save refused with `{ status: "offline" }` that has shown the alert strip,
  when Save is pressed again and the second `updateKind` has not resolved
  yet, then while it is pending no `role="alert"` element is inside the
  editor dialog.

### Block 2 - AC-1, the submit is prevented

- **Title:** `"pressing Save prevents the form's own submission (CAL-092 AC-1)"`.
- **Setup:** `renderEditor({ kind: GYM })`, then
  `replaceText(user, nameInput(), "Workouts")`.
- **The observation:** a `submit` listener on `document`, bubbling phase
  (`document.addEventListener("submit", listener)`), that pushes
  `event.defaultPrevented` onto an array. It is added before the press and
  removed in a `finally`, so a failing assertion cannot leak it into the next
  test. `document` is the outermost node on the path: the event passes the
  form, React's root container and `<body>` first, so what the listener reads
  is what the browser would act on.
- **The press:** one `user.click(saveButton(dialog))`. Save is
  `type="submit"` with `form={formId}`, outside the `<form>` element; the
  click is what raises the submit. Not `fireEvent.submit`: the AC says "when
  Save is pressed". *(PLANNED dropped the stub's "`fireEvent.submit(form)`
  returning `false`" alternative for that reason.)*
- **Assertions:** the array `toStrictEqual([true])` - exactly one submit
  event, and its default prevented - then
  `expect(actions.updateKind).toHaveBeenCalledTimes(1)`. The assertion is on
  `defaultPrevented` itself, never on the absence of an error.
- **What jsdom does with the mutant** (measured, `## Notes`): it does not
  navigate, the listener records `[false]`, and jsdom prints
  `Not implemented: HTMLFormElement's requestSubmit() method`, which fails
  nothing. The test must not depend on that message.

### Block 3 - AC-2, two presses send one add

- **Title:** `"a second press while the add is pending sends nothing more (CAL-092 AC-2)"`.
- **Setup:** `fakeActions()` with `addKind.mockImplementation` returning a
  promise the test resolves later, the deferred pattern of "marks Save busy
  while the save is pending" (`:336-350`). `renderEditor({ kind: null,
  actions })` with the default `KINDS`, then `user.type(nameInput(),
  "Reading")`. "Reading" matches no live kind, and the preselected colour
  pair is readable, so Save is enabled.
- **"Pressed twice"** is two `await user.click(saveButton(dialog))` calls,
  one after the other, before the promise is settled. Save is `aria-busy`
  and not `disabled` while pending, so the second click does raise a submit.
- **Assertions, in this order:**
  `expect(actions.addKind).toHaveBeenCalledTimes(1)` and
  `expect(onClose).not.toHaveBeenCalled()`; then resolve the promise with
  `{ status: "ok", row: <any Kind> }`; then
  `await vi.waitFor(() => expect(onClose).toHaveBeenCalledTimes(1))`; then
  `expect(actions.addKind).toHaveBeenCalledTimes(1)` again.
- The count is exact (`toHaveBeenCalledTimes(1)`), never "at least once".

### Block 5 - AC-4, first clause: no alert while a first save is pending

- **Title:** `"shows no alert while a save is pending (CAL-092 AC-4)"`.
- **Setup:** the deferred `updateKind` of Block 3's pattern,
  `renderEditor({ kind: GYM, actions })`,
  `replaceText(user, nameInput(), "Workouts")`, one
  `user.click(saveButton(dialog))`.
- **The anchor comes first, because the claim is a negative.** "No alert"
  is also true of an editor that never started saving. So before it, assert
  the save is in flight: `expect(actions.updateKind).toHaveBeenCalledTimes(1)`
  and `expect(saveButton(dialog)).toHaveAttribute("aria-busy", "true")`.
- **The assertion:** `expect(within(dialog).queryByRole("alert")).toBeNull()`,
  read once, synchronously, straight after the click. No `waitFor` and no
  `findBy`: polling a negative passes on its first poll. `setFailed` runs
  synchronously inside the submit handler, and `user.click` returns after
  React has rendered, so the mutant's strip is already in the DOM here
  (measured, `## Notes`).
- **Scope is the dialog**, as the AC says: `<ToastHost />` is rendered beside
  the editor and is not this story's.
- **Afterwards:** resolve the promise `ok` and
  `await vi.waitFor(() => expect(onClose).toHaveBeenCalledTimes(1))`, so no
  state update lands after the test ends.
