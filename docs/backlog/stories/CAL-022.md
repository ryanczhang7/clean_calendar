## Context

EPIC-05, brief §4.3: share a screenshot or selected text from the Android
share sheet straight into the app (Web Share Target). `architecture.md`,
"Share target": the manifest declares a `POST` multipart target at `/share`;
the service worker intercepts it, stores the fields and the file in a local
inbox, and redirects to `/capture?from=share`, which reads and clears the
inbox and pre-fills the capture screen (`components.md`, "Capture screen",
loading state). The inbox is its own small IndexedDB database
(`src/pwa/inbox.ts`) shared by the worker and the page, so the worker does not
import the app's cache schema.

Required gate that would fail if this broke: `unit` (the share handler is a
function from `Request` to `Response` that the worker calls; tested without a
worker).

## Acceptance criteria

- **AC-1** - Given `src/pwa/manifest.ts`, when it is read, then `share_target`
  is `{action: '/share', method: 'POST', enctype: 'multipart/form-data',
  params: {title: 'title', text: 'text', url: 'url', files: [{name: 'image',
  accept: ['image/*']}]}}`.
- **AC-2** - Given a multipart `POST /share` with `text` (and optionally
  `title`, `url`), when the handler runs, then the inbox holds one entry whose
  text is the non-empty parts joined by blank lines in the order title, text,
  url, and the response is a 303 to `/capture?from=share`.
- **AC-3** - Given a `POST /share` with an `image` file, when the handler runs,
  then the inbox entry holds the file's bytes and MIME type, and the response
  is the same 303.
- **AC-4** - Given `/capture?from=share` and an inbox entry, when the page
  opens, then it shows "Reading what you shared…" until the entry is read,
  pre-fills the paste box or the image thumbnail, and the inbox is empty
  afterwards; with an empty inbox it renders the normal empty capture page.
- **AC-5** - Given the worker, when a request that is not `POST /share`
  arrives, then the share handler does not respond to it.

### Block 2 - the inbox (AC-2, AC-3, AC-4)

`src/pwa/inbox.ts` - a Dexie database of its own, **never** importing
`src/sync/db.ts` (the worker must not pull the cache schema in; the
architecture row says so). Pattern: `src/sync/db.ts` (Dexie 4, `DexieOptions`
with `indexedDB`/`IDBKeyRange` injectable so a test gives each case its own
`new IDBFactory()` from `fake-indexeddb`; `src/sync/db.test.ts` line 56 is
the shape).

```ts
import Dexie, { type DexieOptions, type Table } from "dexie";
export const INBOX_DB_NAME = "clean-calendar-inbox";
export type SharedImage = { bytes: ArrayBuffer; mime: string; name: string };
export type ShareEntry = { id?: number; text: string; image: SharedImage | null; receivedAt: string };  // receivedAt: ISO 8601
export class InboxDb extends Dexie { shares!: Table<ShareEntry, number>; constructor(name?: string, options?: DexieOptions); }  // version(1).stores({ shares: "++id" })
export type Inbox = {
  /** Replace whatever is there: the inbox holds AT MOST ONE entry. */
  put(entry: ShareEntry): Promise<void>;
  /** The entry, and the inbox emptied, in ONE readwrite transaction; null when empty. */
  take(): Promise<ShareEntry | null>;
  count(): Promise<number>;
};
export function openInbox(db?: InboxDb): Inbox;   // default: new InboxDb() on the browser's own indexedDB
```

- **Bytes, not a Blob.** The image is stored as `ArrayBuffer` + `mime` +
  `name` (AC-3: "the file's bytes and MIME type"). Measured at PLANNED with a
  throwaway probe (deleted): Dexie on `fake-indexeddb` round-trips an
  `ArrayBuffer` field byte-for-byte under the jsdom project. A `Blob` in
  IndexedDB works in Chromium but its structured clone under
  `fake-indexeddb`/jsdom is **not** measured, so it is not the contract.
- `put` is `clear` then `add` in one `rw` transaction, so two shares in a row
  leave the second alone; `take` is `toArray` then `clear` in one `rw`
  transaction and returns the single entry (the last one, if an older
  database somehow holds two). After `take`, `count()` is `0` (AC-4; Deferred
  verification 1).
- `openInbox()` with no argument is the production path (the worker and the
  page each open their own `InboxDb` on the same name; IndexedDB is shared
  between a worker and its pages on one origin).

### Block 3 - the share handler, a function the worker calls (AC-2, AC-3, AC-5)

`src/pwa/shareTarget.ts`, no React, no `self`, no `workbox`, importable under
`tsconfig.json` (DOM lib) **and** `tsconfig.sw.json` (WebWorker lib) - so it
uses only `Request`/`Response`/`FormData`/`URL`/`Blob` members both libs
declare:

```ts
import { type Inbox, type ShareEntry, type SharedImage } from "./inbox";
export const SHARE_PATH = "/share";
export const CAPTURE_FROM_SHARE = "/capture?from=share";
/** POST and pathname exactly "/share" (any origin, any query). */
export function isShareRequest(request: { method: string; url: string }): boolean;
/** title, text, url: each trimmed, the empty ones dropped, the rest joined by "\n\n" in that order. */
export function sharedText(form: FormData): string;
/** form.get("image") when it is a Blob-like with size > 0: its bytes, type and (File) name; else null. */
export async function sharedImage(form: FormData): Promise<SharedImage | null>;
export async function entryFromForm(form: FormData, receivedAt: Date): Promise<ShareEntry>;
/** Reads the form, stores the entry (unless it carries neither text nor image), answers 303 → CAPTURE_FROM_SHARE resolved against request.url. */
export async function handleShare(request: Pick<Request, "url" | "formData">, inbox: Inbox, now?: () => Date): Promise<Response>;
```

- **The handler takes `FormData`, not a multipart body, and the tests give
  it a `FormData`.** Measured at PLANNED (probe deleted): under the `unit`
  project (jsdom), `new Request(url, { method: "POST", body: formData })`
  **throws** inside undici (`webidl.is.File(value)` is false - jsdom's `File`
  is not Node's), so a test cannot build a real multipart `Request`. A jsdom
  `FormData` holding a jsdom `File` is fine: `get("image")` has
  `arrayBuffer()`, `size`, `type`, `name`, and `instanceof Blob` is true.
  So the suite calls `handleShare({ url, formData: async () => form }, inbox)`
  and the pure helpers with a `FormData` built in the test. The platform does
  the multipart parsing in the real worker (`request.formData()`).
- **Blob-like, duck-typed**: `typeof v === "object" && v !== null && typeof
  (v as Blob).arrayBuffer === "function"` - never `instanceof Blob`, which is
  realm-dependent (the worker's `File` is the platform's; jsdom's is not
  Node's). `name` is `(v as File).name` when it is a string, else `"shared"`.
  `size === 0` → no image (Android sends no file field at all when none is
  shared, but a zero-byte file is not an image either).
- **The 303**: `new Response(null, { status: 303, headers: { Location:
  new URL(CAPTURE_FROM_SHARE, request.url).href } })`. Measured at PLANNED:
  `Response` and `Response.redirect(..., 303)` both exist under jsdom and
  carry the `location` header; the `new Response` form is pinned because
  `Response.redirect` demands an absolute URL and the resolution against
  `request.url` is the point (no `self.location` in the handler). Tests read
  `status` (303) and `headers.get("location")` (absolute,
  `https://app.test/capture?from=share` for a request to
  `https://app.test/share`).
- **Empty share**: neither text nor image → nothing is `put` (the inbox keeps
  what it had - nothing, normally) and the 303 is still returned; the page
  then renders the normal empty capture page (AC-4's second half). PO
  decision 2.
- `receivedAt` is `now().toISOString()`; `now` defaults to `() => new Date()`.
- `isShareRequest`: `request.method === "POST"` (exact case; the platform
  normalises) and `new URL(request.url).pathname === SHARE_PATH`. `GET /share`,
  `POST /share/`, `POST /capture`, `POST /shared` are all false.
- **Amended by RED, 2026-10-27** (made explicit what the tests pin; no
  mechanism changed): (a) `handleShare` **awaits** `inbox.put` before it
  resolves - a test holds `put` pending and asserts no Response yet, because
  in the real worker `respondWith`'s promise is what keeps the worker alive
  until the write lands. (b) `sharedImage` reads the form **only** through
  `form.get("image")`: the "no name → `"shared"`" case cannot be built with a
  jsdom `FormData` (measured: `append("image", blob)` turns a Blob into a File
  named `"blob"`), so the test passes a `{ get }` object holding a plain
  Blob-like (`size`, `type`, `arrayBuffer`, no `name`, not `instanceof Blob`).
  (c) `isShareRequest` is also false for `PUT /share` and lower-case `post`.

### Choices the tests left open

- `put`: `clear` then `add` in one `rw` transaction, and it **adds a copy
  without `id`** (`const { id: _id, ...fields } = entry`). Dexie writes the
  generated key back onto the object it adds, so this keeps the caller's
  entry unchanged and stops an incoming `id` from being reused.
- `take`: `toArray` then `clear` in one `rw` transaction, and returns
  `entries.at(-1) ?? null`. The returned entry **carries its Dexie `id`**.
  `ShareEntry.id` is optional, and the tests strip it.
- `sharedText` reads only string values (`form.get` can return a File).
- `sharedImage` duck-types on `arrayBuffer`, then `size === 0` → null, and
  uses `name` only when it is a string, else `"shared"`.
- `handleShare` builds the entry, `await`s `put` only when `text !== "" ||
  image !== null`, then returns `new Response(null, {status: 303, headers:
  {Location: new URL(CAPTURE_FROM_SHARE, request.url).href}})`.
- Page: `reading` starts as `fromShare`, so the first render already shows
  the status line and a non-share render never shows it. The fields block
  (paste box with its **Paste button**, and the picker) is replaced by
  `<p role="status" className={styles.status}>Reading what you shared…</p>`.
  The offline note and the footer still render, and `blocked` includes
  `reading`. The copy is exported as `READING_SHARE`, beside the CAL-020
  copy constants.
- Exactly once: a `took` ref guards the effect. No cleanup cancels the read.
  Under React `StrictMode` (`src/main.tsx`) the mount/unmount/mount cycle
  reuses the ref, so a cancel-on-cleanup would drop the only `take`. A
  `take` that resolves after a real unmount calls `setState` on an unmounted
  component, which React ignores. That case is untested, as RED noted.
- `openInbox()` is called lazily, only when `fromShare` and no `inbox` prop
  is given. Frozen cases and `routes.tsx` never open the inbox database.
- `take` rejecting → `setReading(false)`, nothing else (no alert).
