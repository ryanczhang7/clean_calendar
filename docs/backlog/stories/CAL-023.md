## Context

EPIC-06. Decided after the interview: v1 recurrence is daily, weekly or yearly
with an optional end date. `architecture.md`, "Recurrence": a series is one
`events` row with `recurrence = {freq, until}`; occurrences are expanded over
a range by one pure module in `shared/`, which runs in the browser (views,
CAL-024) and in Deno (`send-reminders`, CAL-029), with one Vitest suite and a
Deno smoke test asserting the same fixture results. Overrides
(`event_overrides`, keyed by the occurrence's original date) cancel or
replace fields of one occurrence.

Required gates that would fail if this broke: `unit` (the Vitest suite over
`shared/`) and `deno-test` (the same fixtures under Deno).

## Acceptance criteria

- **AC-1** - Given a weekly series starting Monday 12 October 2026 09:00-10:00
  with no end, when `expand(series, [], range)` is asked for 1 to 30 November
  2026, then it returns the Mondays 2, 9, 16, 23 and 30 November, each
  09:00-10:00 local wall time; daily and yearly behave likewise.
- **AC-2** - Given `until` = 26 October 2026, when the weekly series above is
  expanded over October and November, then the last occurrence is 26 October
  (`until` is inclusive).
- **AC-3** - Given a weekly 09:00 series in `Europe/London` crossing the end of
  daylight saving time (25 October 2026), when it is expanded, then every
  occurrence starts at 09:00 local, so the UTC instants differ by one hour
  across the change.
- **AC-4** - Given a yearly series on 29 February 2028, when it is expanded over
  2028 to 2033, then occurrences fall on 29 February 2028 and 29 February 2032
  only.
- **AC-5** - Given an override with `cancelled = true` for 19 October, and
  another for 2 November changing the title and the start to 10:00, when the
  weekly series is expanded, then 19 October is absent and 2 November has the
  new title and time while keeping `occurrenceDate` 2 November; every
  occurrence carries `seriesId` and `occurrenceDate`.
- **AC-6** - Given a range that starts in the middle of an occurrence (a
  multi-day yearly all-day event), when expanded, then that occurrence is
  included; an occurrence ending exactly at the range start is not.
- **AC-7** - Given `shared/tests/recurrence-fixtures.json`, when the Vitest
  suite and `supabase/functions/_shared/recurrence_test.ts` both run it, then
  both produce the fixture's expected occurrences exactly.

**Writes:** `shared/recurrence.ts`, `shared/recurrence.test.ts`, `shared/tests/recurrence-fixtures.json`, `supabase/functions/_shared/recurrence_test.ts`

**Block 1 - the module and its imports.** `shared/recurrence.ts` has **no
imports**: not `date-fns`, not `zod`, nothing. It runs in the browser (Vite)
and in Deno by relative path (`../../../shared/recurrence.ts`, as
`_shared/health.ts` already does), and `supabase/functions/deno.json` maps
only `zod` and `@std/assert`. Zone arithmetic uses `Intl.DateTimeFormat` with
`timeZone` - both runtimes ship full ICU. (PO decision 3 below; it supersedes
the `@date-fns/tz` note.) The module does not import `src/data/rows.ts`: it
declares its own types, structurally identical where they overlap.

**Block 2 - exported names and signatures.**

```ts
export type Freq = "daily" | "weekly" | "yearly";
export type Recurrence = { freq: Freq; until: string | null; tz: string };
//   until: "YYYY-MM-DD" or null (no end); tz: an IANA zone name.

export type Series = {
  id: string;
  title: string;
  kindId: string;
  startsAt: Date;          // first occurrence, an instant
  endsAt: Date;            // first occurrence's end, an instant (exclusive)
  allDay: boolean;
  location: string | null;
  notes: string | null;
  recurrence: Recurrence;
};

export type Override = {
  occurrenceDate: string;  // "YYYY-MM-DD", the ORIGINAL occurrence's date in tz
  cancelled: boolean;
  title: string | null;    // null = keep the series value, for every field below
  kindId: string | null;
  startsAt: Date | null;
  endsAt: Date | null;
  allDay: boolean | null;
  location: string | null;
  notes: string | null;
};

export type Range = { start: Date; end: Date };   // half-open [start, end)

export type Occurrence = {
  seriesId: string;
  occurrenceDate: string;  // "YYYY-MM-DD" in tz, of the ORIGINAL start; unchanged by an override
  title: string;
  kindId: string;
  startsAt: Date;
  endsAt: Date;
  allDay: boolean;
  location: string | null;
  notes: string | null;
};

export function expand(
  series: Series,
  overrides: readonly Override[],
  range: Range,
): Occurrence[];
```

`src/data/rows.ts` already exports a `Recurrence` with the same three fields;
`Series` is `Pick<Event, ...>` with `recurrence` non-null and `Override` is
`EventOverride` minus `id`, `eventId` and the stamps. Nothing in `src/` or
`supabase/` imports the new module in this story, so no caller list applies.

**Block 3 - how occurrences are generated.** Occurrence `k` (k = 0, 1, 2, ...)
is the series' first occurrence with its **wall-clock** start and end in
`recurrence.tz` both advanced by `k` days (`daily`), `k × 7` days (`weekly`)
or `k` years (`yearly`); hours, minutes and seconds of the wall time are kept.
Occurrence 0 is the series itself, byte for byte. Each wall time is converted
back to an instant in `tz`, which is what makes a 09:00 series stay 09:00
across a DST change (AC-3): the UTC instants of 19 and 26 October 2026 09:00
London are `08:00Z` and `09:00Z`. The end is shifted the same way, not by
adding the first occurrence's elapsed milliseconds, so a two-day all-day event
across the change is still two days.

- A shifted wall time that does not exist (spring forward, e.g. 01:30 on 29
  March 2026 in London) resolves to the instant the pre-transition offset gives
  (01:30 GMT = 02:30 BST). One that exists twice (fall back, 01:30 on 25
  October 2026 in London) resolves to the **earlier** instant (the BST one).
- `yearly` on a 29 February: a year with no 29 February has **no occurrence**
  (it is skipped, never moved to 28 February or 1 March) - PO decision in
  Notes. Only `yearly` can land on a missing date.
- The series' `startsAt` is in occurrence 0 regardless of `tz`; `tz` decides
  the wall clock every later occurrence keeps.

**Block 4 - `until`, range and order.** `until` is inclusive: occurrence `k`
is kept iff `until === null` or `occurrenceDate <= until` as `YYYY-MM-DD`
strings (AC-2: `until` = `2026-10-26` keeps Monday 26 October). The range is
half-open on instants and the test is **overlap on the original times**:
`originalStart < range.end && originalEnd > range.start` (AC-6: an
occurrence ending exactly at `range.start` is out; one straddling
`range.start` is in). Generation starts at `k = 0` and stops at the first
`k` whose original start is `>= range.end` (a later `k` cannot overlap, since
the override may not move the date). A range entirely before the series
yields `[]`. The result is in ascending `k`, which is ascending original
start.

**Block 5 - overrides.** Overrides match an occurrence by `occurrenceDate`
only. `cancelled: true` removes it (AC-5, 19 October absent). Otherwise each
non-null field replaces the series' value in the returned occurrence;
`occurrenceDate` and `seriesId` are never changed by an override, and the
range filter in Block 4 uses the original times, not the overridden ones. An
override whose date matches no generated occurrence, or one for an occurrence
outside the range, is ignored. Two overrides with the same date: the **last**
one in the array wins (the database's unique key makes this unreachable).

**Block 6 - errors.** `expand` is pure and never mutates its arguments.
An unknown `tz` throws the `RangeError` that `Intl.DateTimeFormat` throws;
`until` that is not `YYYY-MM-DD` and a `freq` outside the union are not
validated (the type is the contract; `src/data/rows.ts` already rejects
malformed JSON before it gets here).

**Block 7 - the fixture and the two suites (AC-7).**
`shared/tests/recurrence-fixtures.json` is:

```json
{
  "cases": [
    {
      "name": "weekly Mondays in November",
      "series": { "id": "s1", "title": "Gym", "kindId": "k1",
                  "startsAt": "2026-10-12T08:00:00.000Z", "endsAt": "2026-10-12T09:00:00.000Z",
                  "allDay": false, "location": null, "notes": null,
                  "recurrence": { "freq": "weekly", "until": null, "tz": "Europe/London" } },
      "overrides": [],
      "range": { "start": "2026-11-01T00:00:00.000Z", "end": "2026-12-01T00:00:00.000Z" },
      "expected": [
        { "seriesId": "s1", "occurrenceDate": "2026-11-02", "title": "Gym", "kindId": "k1",
          "startsAt": "2026-11-02T09:00:00.000Z", "endsAt": "2026-11-02T10:00:00.000Z",
          "allDay": false, "location": null, "notes": null }
      ]
    }
  ]
}
```

Every `Date` is an ISO-8601 UTC string with milliseconds (`toISOString()`
form). Each suite parses the strings to `Date`s, calls `expand`, serialises
the result the same way and asserts **deep equality with `expected`, in
order**. The fixture carries at least one case per AC-1 to AC-6, so AC-7 is
the same cases under both runtimes. The Vitest suite may hold further cases
inline; the Deno suite's job is the fixture, every case of it, one
`Deno.test` per case, read with `Deno.readTextFile(new URL("../../../shared/tests/recurrence-fixtures.json", import.meta.url))`
(`--allow-read` is in the gate command). Nothing in either suite may depend on
the host zone: every zone is `recurrence.tz`, every instant is UTC.

**Block 8 - oracle partition.** Every criterion is **settled**: each expected
instant is computable by hand from the zone's published offsets (London: BST
`+01:00` until 01:00Z on 25 October 2026, GMT `+00:00` after; the spring
transition is 29 March 2026) and RED reads them out. Nothing is oracle-free.
The mechanical pins are Blocks 3 to 6 word for word: the inclusive `until`,
the half-open range on original times, the skipped 29 February, the DST
resolution rules, the last-override-wins rule.

**Block 9 - test-only dependencies.** None. `@std/assert` is already mapped
for Deno; Vitest has what it needs.

**Block 10 - gates.** `unit` and `coverage` (required) read `shared/**`;
`deno-test` and `deno-check` (required) read `supabase/functions/**`. All four
fire on this story. `deno-check`'s floor is 12 modules and `deno-test`'s is
160 tests; both rise with this story and GREEN or GATES raises the floors in
`project.conf` to the new counts.

## Notes

- Planned 2026-10-12 by `/plan-product`; body written by the resumed lead-po
  run on a **model override: opus** (the fable run hit a usage limit).
- **PO decision - the series carries its time zone.** The server must expand
  occurrences in the owner's zone (CAL-029), and a UTC-only expansion drifts
  an hour at every DST change. So `recurrence` is
  `{freq, until, tz}` where `tz` is the IANA zone of the device that saved the
  series. `architecture.md` (Data model, Recurrence) records it.
  The brief's "device zone only" still holds for display.
- **PO decision - 29 February.** A yearly series on 29 February occurs only in
  leap years (as RFC 5545 and Google Calendar do). Recorded here; revisit if a
  birthday bites.
- Likely production dependency: `@date-fns/tz` (with `date-fns` 4) for zoned
  arithmetic, imported in Deno through `npm:`; a GREEN change.

- **PO decision 3 (2026-10-31, PLANNED → RED) - no runtime dependency.** The
  line above naming `@date-fns/tz` is superseded: the module uses
  `Intl.DateTimeFormat` for zone offsets, which Node, the browser and Deno all
  ship, so `shared/recurrence.ts` needs no import and `deno.json` no new
  mapping. Measured before dispatch, in Node 24 and Deno, that
  `Intl.DateTimeFormat('en-GB', {timeZone: 'Europe/London'})` renders
  `2026-10-19T08:00Z` as `09:00 BST` and `2026-10-26T09:00Z` as `09:00 GMT`.
- Epic done-when checked at PLANNED → RED: the calendar chips and the
  per-occurrence edits are CAL-024 and CAL-025; this story is only the
  expander. No gap.
- PLANNED → RED run 2026-10-31 by the lead-po orchestrator on
  `claude-fable-5-1` (Fable 5.1, the session model; `models.conf` says fable).
