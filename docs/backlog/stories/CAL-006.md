## Context

EPIC-02. The brief (§4.2) ships eleven default kinds; the Lead Designer's
palette is `docs/wiki/design/kinds-palette.md` (status: proposed, the owner
reviews it in the walkthrough). This story seeds them on the first owner
sign-in and builds the colour rule every chip relies on: a chip's text colour
is derived, never stored - whichever of `#1B1B1F` and `#FFFFFF` has the higher
WCAG contrast against the chip (`tokens.md`, "Chip text rule";
`accessibility.md`, Contrast). It also introduces `useKinds()`, the read hook
the walkthrough, the legend and the views share; it reads through the
repository online until CAL-014 moves it onto the local cache behind the same
signature.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - `DEFAULT_KINDS` lists the eleven kinds in `kinds-palette.md`'s
  order with exactly its names, `color_light` and `color_dark` hexes, and
  `sort_order` 1 to 11. (Settled: read the values out of the palette table.)
- **AC-2** - Given a hex colour, when `chipText(hex)` is called, then it returns
  the text colour (`#1B1B1F` or `#FFFFFF`) with the higher contrast ratio and
  that ratio rounded to two decimals; for every default in both themes it
  returns the text colour and ratio the palette table records (all ≥ 4.5);
  for `#808080`, `#7F7F7F`, `#FFFF00` and `#000080` it returns the higher of
  the two candidates. `contrast(a, b)` implements the WCAG 2.x formula.
  *Control:* `#808080` must report 4.35 with `#1B1B1F` - below 4.5, which
  CAL-007's editor refuses.
- **AC-3** - Given the owner signed in and the `kinds` table holding no rows at
  all, when the app finishes admitting the owner, then the eleven defaults are
  inserted with `is_default = true` and `ensureDefaultKinds()` reports
  `'seeded'`.
- **AC-4** - Given at least one `kinds` row exists - live or soft-deleted -
  when the owner signs in, then nothing is inserted and it reports
  `'existing'`. Deleting every kind never brings the defaults back.
- **AC-5** - Given two devices signing in for the first time together, when the
  second insert hits the unique live-name index (CAL-004), then the second
  call re-reads, reports `'existing'`, and the table holds exactly eleven
  live kinds.
- **AC-6** - Given kinds in the repository, when a component calls
  `useKinds()`, then it receives the live kinds in `sort_order`, and a
  lookup by id that also returns soft-deleted kinds (so an event whose kind
  was deleted can still be told apart from an unknown id).

### Block 1 - `src/domain/colour.ts`

```ts
export const CHIP_TEXT_DARK = "#1B1B1F";
export const CHIP_TEXT_LIGHT = "#FFFFFF";
export type ChipText = typeof CHIP_TEXT_DARK | typeof CHIP_TEXT_LIGHT;
/** WCAG 2.x relative luminance of a `#RRGGBB` colour, 0..1. */
export function relativeLuminance(hex: string): number;
/** (Lmax + 0.05) / (Lmin + 0.05): symmetric, unrounded, always >= 1. */
export function contrast(a: string, b: string): number;
/** The chip text colour with the higher contrast, and that ratio rounded to 2 dp. */
export function chipText(hex: string): { text: ChipText; ratio: number };
```

- Input: `#` followed by exactly six hex digits, either case (`#bd8200` is
  the same colour as `#BD8200`). Anything else - three digits, no `#`, an
  alpha channel, an empty string - throws `RangeError` whose message contains
  the offending input. No normalisation of the stored value is done here.
- Linearisation: `c/255`, then `c <= 0.04045 ? c/12.92 : ((c+0.055)/1.055)^2.4`;
  `L = 0.2126R + 0.7152G + 0.0722B`. No shortcuts, no lookup table.
- `chipText` rounds with `Math.round(ratio * 100) / 100` and returns the
  rounded number. A tie (both candidates equal to full precision) picks
  `CHIP_TEXT_DARK`.
- Expected values (PO, 2026-10-16, awk over the formula above, full
  precision then rounded). The palette table's 22 values agree with these to
  the digit:

### Block 3 - `src/data/kinds.ts`: two members added to `KindsRepo`

```ts
/** Every row, live and soft-deleted, ascending sort_order. */
listAll(): Promise<ListResult<Kind>>;
/** One POST carrying a JSON array; PostgREST inserts it as one statement. */
insertMany(inputs: NewKind[]): Promise<ListResult<Kind>>;
```

- `listAll`: `GET /rest/v1/kinds?select=*&order=sort_order.asc`, no
  `deleted_at` filter, mapped with `toKind` through `fromPostgrest`.
- `insertMany`: `POST /rest/v1/kinds` with body `inputs.map(fromNewKind)`,
  `Prefer` containing `return=representation`, `.select("*")`; `ok` carries the
  rows the server returned, in its order. A `23505` (the live-name index,
  CAL-004) resolves `{ status: "error", code: "23505", message }` - the
  existing `fromPostgrest` already does this; nothing retries. An empty
  `inputs` is not called by this story; its behaviour is unconstrained.
- Why not eleven `insert()` calls: two devices racing would each land a
  subset and both report a conflict; one atomic statement means exactly one
  device seeds all eleven (AC-5).
- Existing members are untouched. `src/data/kinds.test.ts` gains tests for the
  two new members in the same MSW style as the file's others.

### Block 4 - `src/kinds/seedKinds.ts`

```ts
import type { KindsRepo } from "../data/kinds";
import type { Kind } from "../data/rows";
export type SeedOutcome = "seeded" | "existing" | "unavailable";
export type SeedRepo = Pick<KindsRepo, "listAll" | "insertMany">;
export async function ensureDefaultKinds(repo: SeedRepo): Promise<{ outcome: SeedOutcome; kinds: Kind[] }>;
```

In order, and nothing else:
1. `listAll()`. Not `ok` → `{ outcome: "unavailable", kinds: [] }`; no insert
   is attempted.
2. One or more rows, **live or soft-deleted** → `existing`, `kinds` = those
   rows. (AC-4: deleting every kind never brings the defaults back.)
3. No rows → `insertMany(DEFAULT_KINDS)`. `ok` → `seeded`, `kinds` = the
   returned rows. `error` with `code === "23505"` → `listAll()` once more →
   `existing` with its rows (AC-5), or `unavailable` if that read fails too.
   Any other failure (`offline`, another code) → `unavailable`.
It never updates, deletes, or inserts a subset, and it calls `insertMany`
at most once.

### Block 5 - `src/sync/kindsStore.ts`

```ts
import type { Kind } from "../data/rows";
import type { SeedOutcome, SeedRepo } from "../kinds/seedKinds";
export type KindsStatus = "loading" | "ready" | "unavailable";
export type KindsSnapshot = {
  status: KindsStatus;
  /** Live kinds (deletedAt null), ascending sortOrder, then createdAt. */
  kinds: Kind[];
  /** Any row by id, soft-deleted included; unknown id → undefined. */
  byId: (id: string) => Kind | undefined;
};
export type KindsStore = {
  ensureSeeded(): Promise<SeedOutcome>;
  refresh(): Promise<void>;
  subscribe(listener: () => void): () => void;
  getSnapshot(): KindsSnapshot;
};
export function createKindsStore(repo: SeedRepo): KindsStore;
/** The app's one store, over `kindsRepo(supabase)` from `../lib/supabase`. */
export const kindsStore: KindsStore;
export function useKinds(store?: KindsStore): KindsSnapshot;
```

- `ensureSeeded()` runs `ensureDefaultKinds(repo)`; concurrent callers share
  the one in-flight promise; a settled `seeded` or `existing` is remembered
  for the store's life and returned without a request; `unavailable` is not
  remembered, so the next call tries again. Its `kinds` become the snapshot
  (`ready`), or the status becomes `unavailable` with the rows unchanged.
- `refresh()`: `listAll()` → `ready` with the rows, or `unavailable` keeping
  the last rows. `useKinds()` on a store that has never loaded calls
  `refresh()` once, from an effect, not during render.
- `getSnapshot()` returns the same object until the state changes
  (`useSyncExternalStore` requires it). `useKinds` defaults to the app
  store; tests pass `createKindsStore(fakeRepo)`.
