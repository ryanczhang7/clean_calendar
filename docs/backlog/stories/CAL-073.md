## Context

EPIC-07. Follow-up to CAL-027 (notification permission and the device's push
subscription), from the one Should fix of its `## Diff review` (PR #62,
merged at `3541223`). Line numbers are those of `main` at `3541223`.

**The defect.** `registerThisDevice` (`src/reminders/pushSubscription.ts:62-69`)
does `getSubscription() ?? subscribe({userVisibleOnly: true,
applicationServerKey: vapidKeyBytes(key)})` and upserts the result by
endpoint. `getSubscription()` returns whatever subscription the browser
holds, whichever VAPID key created it. After the key pair is regenerated,
every device that subscribed before keeps its old subscription and keeps
upserting that endpoint. The push service refuses a send signed with the new
key with 403, and `supabase/functions/send-reminders/push.ts:57-62` maps only
404 and 410 to `gone`; 403 is `failed`, so `handler.ts` never deletes the
row. The device gets no reminder again, and Settings still reads
"Notifications are on for this device."

**The fix.** On every call, compare the existing subscription's
`options.applicationServerKey` with `vapidKeyBytes(VITE_VAPID_PUBLIC_KEY)`,
byte for byte. If they differ, unsubscribe it, subscribe with the current
key and upsert the new endpoint. If they match, today's reuse path is
unchanged.

**What bounds it.** `docs/wiki/architecture.md`, "Where state lives": the
browser's `PushManager` is the source of truth for the subscription,
"Re-registered on every app start; endpoint changes are upserts." The
function still never rejects and never asks for permission (CAL-027
Contract, Block 2). No server change: a successful `unsubscribe()`
invalidates the old endpoint at the push service, which then answers 404 or
410, and `send-reminders` already prunes that row.

Required gate that would fail if this broke: `unit`
(`covers | unit | src/**`; the tests are `src/reminders/pushSubscription.test.ts`).

## Acceptance criteria

"Granted" below means: Notification, the service worker and PushManager all
present, `Notification.permission === "granted"`, `VITE_VAPID_PUBLIC_KEY` set
to key B, and an upsert that resolves ok. "Key A" is any byte string other
than the decoded bytes of B.

- **AC-1** — Given granted, and an existing subscription whose
  `options.applicationServerKey` is key A (a different, valid 65-byte key),
  when `registerThisDevice` runs, then the existing subscription's
  `unsubscribe()` is called exactly once; after it, `pushManager.subscribe`
  is called exactly once with exactly `{userVisibleOnly: true,
  applicationServerKey: <the bytes of B>}`; the upsert is called exactly once,
  with the NEW subscription's endpoint, p256dh and auth and this user agent
  (never the old endpoint); and the outcome is `{status: "ok"}`. This is the
  reproduction: on `main` today nothing is unsubscribed and the old endpoint
  is upserted.
- **AC-2** — Given granted, and an existing subscription whose
  `options.applicationServerKey` holds exactly the bytes of B, when
  `registerThisDevice` runs, then `unsubscribe()` and `subscribe` are not
  called, the upsert carries the existing subscription's endpoint, p256dh and
  auth, and the outcome is `{status: "ok"}`.
- **AC-3** — Given granted, and an existing subscription whose key cannot be
  read (`options` is absent, or `options.applicationServerKey` is `null`),
  when `registerThisDevice` runs, then it behaves as AC-2: no `unsubscribe()`,
  no `subscribe`, the existing endpoint is upserted, `{status: "ok"}`.
- **AC-4** — Given granted, and an existing subscription under key A whose
  `unsubscribe()` either rejects or resolves `false`, when
  `registerThisDevice` runs, then it resolves `{status: "error"}` (it does
  not reject), `subscribe` is not called and nothing is upserted. One case
  for each of the two failures.
- **AC-5** — The comparison is over every byte and the length. Given granted,
  each of these existing keys is treated as different from B (AC-1's
  behaviour: one `unsubscribe()`, one `subscribe`, the new endpoint
  upserted): (a) B with only its last byte changed; (b) B with only its
  first byte changed; (c) the first 64 bytes of B; (d) B followed by one
  extra byte.

## Contract

**Writes:** `src/reminders/pushSubscription.ts`, `src/reminders/pushSubscription.test.ts`, `src/test/push.ts`

RED may amend any block in place, with a reason; GREEN builds what the
amended block says.

**Block 1 — the module (`src/reminders/pushSubscription.ts`).** No export is
added, removed or changed. `registerThisDevice(repo?)` keeps its signature
and `RegisterOutcome` keeps its three shapes; a failed unsubscribe is
`{status: "error"}`, not a new reason. The early returns (`unsupported`,
`not-granted`, `no-key`) are unchanged and still come before any
`pushManager` call. Inside the existing `try`:

1. `existing = await reg.pushManager.getSubscription()`.
2. `existing === null` → `subscribe(...)` as today.
3. Otherwise read `existing.options?.applicationServerKey`. It is an
   `ArrayBuffer | null` in browsers (not a `Uint8Array`), and `options`
   itself is missing on some engines, so read it defensively.
   - absent or `null` → **unknown**: keep `existing` (AC-3).
   - same length as `vapidKeyBytes(key)` and every byte equal → keep
     `existing` (AC-2).
   - anything else → `await existing.unsubscribe()`; if it resolves `false`,
     return `{status: "error"}`; if it rejects, the existing `catch` returns
     `{status: "error"}`; if `true`, `subscribe(...)` with the same options
     shape as today, and continue with the new subscription.
4. The key check and the upsert that follow are as today (missing
   `p256dh`/`auth` → error; upsert not ok → error).

How the bytes are compared, and whether it is a local helper, is the
implementer's choice; no helper is exported.

**Block 2 — why unknown means keep (AC-3).** A browser that does not report
the key reports it on no call. Treating unknown as different would
unsubscribe and re-subscribe on every app start, giving the device a new
endpoint each time and leaving a dead row behind each time. Keeping it costs
only this: such a device is not healed after a rotation, which is today's
behaviour. Chrome, Firefox and Safari 16+ all report the key.

**Block 3 — why a failed unsubscribe stops (AC-4).** While the old
subscription is still active the browser refuses `subscribe` with a different
key (`InvalidStateError`), and upserting the old endpoint would refresh
`last_seen_at` on a row that cannot receive. So: error, nothing written; the
next app start tries again.

**Block 4 — the old row.** The client does not delete it. The repository has
no delete (`PushSubscriptionsRepo` is `upsert` only) and this story adds
none. After a successful `unsubscribe()` the push service answers 404 or 410
for the old endpoint and `send-reminders` deletes the row on its next send
to it (`handler.ts`, the `gone` branch). Until then the row costs one failed
send per reminder.

**Block 5 — the test fake (`src/test/push.ts`).** Additive only, so the
other files that import it keep compiling unchanged:
`src/app/App.test.tsx`, `src/events/ReminderField.test.tsx`,
`src/reminders/NotificationsPage.test.tsx`,
`src/reminders/PermissionCard.test.tsx`, `src/sync/overrideActions.test.ts`
(listed from the tree at `3541223`; RED confirms the list before editing).

- `FakeSubscription` gains two OPTIONAL members:
  `options?: { applicationServerKey: ArrayBuffer | null }` and
  `unsubscribe?: Mock<() => Promise<boolean>>`.
- `fakeSubscription(endpoint, keys)` keeps its two parameters and its
  result is unchanged (no `options`, no `unsubscribe`), so `EXISTING` and
  `CREATED` stay "key unknown" and every CAL-027 test keeps its meaning.
  The existing "re-reads an existing subscription" test is therefore already
  one of AC-3's cases (`options` absent); it stays as it is.
- A new helper builds a subscription that reports a key, for example
  `subscriptionUnderKey(endpoint, keys, applicationServerKey, unsubscribe)`
  where `applicationServerKey` is `ArrayBuffer | null` and `unsubscribe` is
  `"ok" | "false" | "reject"`, default `"ok"`. The key it stores is a real
  `ArrayBuffer` of exactly the key's length (a copy, not a view over a
  larger buffer), as a browser gives. RED names and shapes it.
- A second VAPID-shaped key constant for key A (65 bytes, first byte 0x04,
  different from `VAPID_KEY`).

**Block 6 — oracle partition.** All five criteria are **mechanical**: pin
call counts, the call order (AC-1: `unsubscribe` before `subscribe`, by
`mock.invocationCallOrder`), the subscribe options and the upsert argument
written out whole, as CAL-027's tests do. The expected bytes come from
Node's `Buffer.from(key, "base64url")`, the same independent decoder
CAL-027 used, never from `vapidKeyBytes`. Nothing here is statistical; there
is no metric to invent.

**Block 7 — what RED should expect.** AC-1, AC-4 and AC-5 fail on `main` for
the right reason (no `unsubscribe` call; the old endpoint upserted; `ok`
where AC-4 wants `error`). AC-2 and AC-3 **pass on arrival**, because
today's code reuses every existing subscription. RED says so in the
handoff; they are earned by Deferred verification 2.

**Test-only dependencies:** none.

**Callers of changed signatures:** none. `registerThisDevice` is called from
`src/app/App.tsx` and `src/reminders/PermissionCard.tsx`; neither changes.

## Out of scope

- **A 403 from the push service does not prune the row.** `push.ts` keeps
  mapping only 404 and 410 to `gone`. A 403 under VAPID means the
  subscription's key and the signing key disagree, which is permanent for a
  row made under an old key - but it is also exactly what a wrong
  `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` secret on the server produces for
  EVERY row, and pruning on it would delete every device's subscription
  because of one bad deploy. With this story a rotated device heals itself
  on its next app start, and its old endpoint then answers 404/410 and is
  pruned by the existing rule. Nothing under `supabase/` is written here.
  Possible follow-up, only if stale rows are seen to pile up: prune a row
  after N consecutive 403s, or one whose `last_seen_at` is older than some
  age.
- **The client deleting the old `push_subscriptions` row.** No `delete` is
  added to `src/data/pushSubscriptions.ts`; server pruning removes it
  (Contract, Block 4).
- **Healing a device that never opens the app after a rotation.** It keeps
  its old subscription until the app next starts; there is no
  `pushsubscriptionchange` handler in `src/sw.ts` in this story.
- **A browser that does not report `options.applicationServerKey`.** Kept
  as is (AC-3); no fallback such as remembering the key in `localStorage`.
- **Any UI.** `PermissionCard`, Settings and their copy are untouched; a
  failed re-subscribe is `{status: "error"}`, which the callers already
  handle. No new `RegisterOutcome` reason.
- **A rotation runbook in `docs/wiki/deployment.md`**, and any change to
  how the VAPID secrets are set.
- Retrying inside the call. One attempt per call; the next app start is the
  retry.
