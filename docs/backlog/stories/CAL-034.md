## Context

EPIC-01, from `docs/wiki/audits/epic-01-2026-10-15.md` (Decided 5; SQL
mutants M11 to M15 and M18). CAL-004's handoff left the CHECK constraints,
the `app_config` single-row constraint and the FK actions on `reminders`
"not pinned, so GREEN decides". GREEN built them as the Contract lists, but
no test notices if any one is dropped. Each of these deletions passed all
129 db tests:

- M11 `events`: `check (ends_at > starts_at)`. The calendar assumes every
  event has positive length.
- M12 `kinds`: `check (length(trim(name)) between 1 and 32)`.
- M13 `events`: `check (origin in ('manual','capture'))`. `toEvent`
  (`src/data/rows.ts:186`) maps any other value to `"manual"` *because*
  "a check constraint admits only these two".
- M14 `kinds`: `color_light`'s `^#[0-9a-fA-F]{6}$` check.
- M15 `app_config`: `constraint app_config_single_row check (singleton)`.
  `unique` alone admits a second row with `singleton = false`, and
  `is_owner()` reads `owner_email … limit 1` with no `order by`.
- M18 `reminders.event_id … on delete cascade`. Without it, a hard delete of
  an event that has reminders fails on the FK.

Test-only: the shipped constraints are believed correct, so each test passes
on arrival and is earned by its mutant.

Required gate that would fail if this broke: `db`.

## Acceptance criteria

- **AC-1** — Given the service role, when it inserts an `events` row with
  `ends_at = starts_at`, then the insert is refused with a check violation
  (`23514`). A test fails when `check (ends_at > starts_at)` is dropped
  (audit M11).
- **AC-2** — Given the service role, when it inserts a `kinds` row whose
  name is empty, only spaces, or 33 characters, then each is refused, and a
  32-character name is accepted. A test fails when the name length check is
  dropped (audit M12).
- **AC-3** — Given the service role, when it inserts an `events` row with
  `origin = 'other'`, then the insert is refused. A test fails when the
  `origin` check is dropped (audit M13).
- **AC-4** — Given the service role, when it inserts a `kinds` row with
  `color_light` (and, separately, `color_dark`) not matching
  `^#[0-9a-fA-F]{6}$` (e.g. `#12345`, `red`), then it is refused. A test
  fails when `color_light`'s check is dropped (audit M14).
- **AC-5** — Given the seeded `app_config` row, when the service role
  inserts a second row with `singleton = false`, then it is refused. A test
  fails when `app_config_single_row` is dropped (audit M15).
- **AC-6** — Given an event with a reminder, when the service role
  hard-deletes the event, then the delete succeeds and the reminder is gone.
  A test fails when `on delete cascade` is dropped from
  `reminders.event_id` (audit M18).

## Contract

**Writes:** `supabase/tests/constraints.db.test.ts`

- A **new** file, so this story does not conflict with CAL-032 or CAL-033
  on `schema.db.test.ts`. It uses `supabase/tests/helpers.ts` as the
  existing suites do, writes through the service client, and leaves the
  six client tables truncated and `app_config` with only its seeded row.
- Assert on the error `code` (`23514` for a CHECK, `23505` for a unique,
  `23503` for a FK), not only that an error occurred. An error from a
  missing column would otherwise satisfy it.
- Earning: one `mutate.sh` run per AC on
  `supabase/migrations/0001_core_schema.sql`, applied with `supabase db
  reset`, then reset again after the restore. The audit's SQL table gives
  the line and the `sed` expression for each, so the earning runs can
  reuse them.
- `discovery | db` already matches any `*.db.test.*` file, so no
  `project.conf` change is needed. Check that with `bash scripts/doctor.sh`.
