## Context

EPIC-01, from `docs/wiki/audits/epic-01-2026-10-15.md` (Decided 4; SQL
mutants M7 and M20). CAL-004's AC-6 says `updated_at` is strictly greater
after an update "whatever value the client sent". Sync depends on this
stamp twice: the conditional update (`updated_at = <token>`) and
`listSince(t)` (`updated_at > t`). Two mutants of the shipped
`public.set_updated_at()` pass all 129 db tests:

- **M20**: `greatest(clock_timestamp(), new.updated_at, old.updated_at + 1µs)`.
  It stores a client-sent **future** stamp. The only AC-6 test sends
  `2000-01-01`, a past value, which `greatest` discards either way.
- **M7**: `clock_timestamp()` alone, without the `greatest(..., old + 1µs)`
  guard. A stored stamp that is ahead of the server clock then goes
  *backwards* on update, and `listSince` never returns that row again.
  INSERT has no trigger, so a row inserted with an explicit future
  `updated_at` is enough to set this up. CAL-004 measured this mutant "not
  detected" against a scratch candidate. The audit confirmed it against the
  shipped migration.

Test-only: the shipped trigger is believed correct. Every new test will pass
on arrival and must be earned by its mutant (rules.md, non-negotiables).

Required gate that would fail if this broke: `db`.

## Acceptance criteria

- **AC-1** — Given a row in any client table, when the client updates it
  sending an `updated_at` far in the future (e.g. `2999-01-01`), then the
  stored `updated_at` is no later than the database's `now()` at the end of
  the statement plus a small bound, and strictly later than before. A test
  fails when the trigger honours `new.updated_at` (audit M20).
- **AC-2** — Given a row whose stored `updated_at` is ahead of the server
  clock (inserted through the service role with an explicit future
  `updated_at`), when it is updated, then the new `updated_at` is strictly
  greater than the old one. A test fails when the trigger is
  `clock_timestamp()` without the `greatest(..., old.updated_at + interval
  '1 microsecond')` guard (audit M7).

- **Files.** Only `supabase/tests/schema.db.test.ts` changes. Two new `it`
  cases inside the existing `describe("AC-1/AC-6: updated_at is maintained
  by a trigger")`, after the four that are there. No helper changes, no
  migration, no config. The test command for the one suite:
  `pnpm exec vitest run --project db supabase/tests/schema.db.test.ts -t "<name>"`.
- **The trigger under test** is `public.set_updated_at()` in
  `supabase/migrations/0001_core_schema.sql`; its one expression is line 171:
  `greatest(clock_timestamp(), old.updated_at + interval '1 microsecond');`
  INSERT has no trigger, so an explicit `updated_at` on insert is stored as
  sent - that is what AC-2 relies on.
- **AC-1 (future stamp from the client; mutant M20).** Insert a `kinds` row
  through `serviceClient(env)` with `rowFor("kinds", {})`, read its
  `updated_at::text` through `sql(env)`, then update through the service
  client with `{ name: "Touched future", updated_at: "2999-01-01T00:00:00Z" }`.
  Read back in one SQL statement, from `public.kinds where id = ${id}`:
  `updated_at > ${before}::text::timestamptz as later`,
  `updated_at <= now() + interval '1 minute' as bounded`,
  `extract(year from updated_at)::int as year`. Assert
  `{ later: true, bounded: true }` and `year !== 2999`. The bound is one
  minute: the comparison is server-side so no clock skew between the test
  process and Postgres enters, and it is narrower than the 973 years M20
  would store. The `::text::timestamptz` cast is the lossless form (see the
  "inside one transaction" test for why).
- **AC-2 (stored stamp ahead of the clock; mutant M7).** Through `sql(env)`,
  `insert into public.kinds (name, color_light, color_dark, updated_at)
  values (..., clock_timestamp() + interval '1 hour') returning id,
  updated_at::text as u0`. Then `update public.kinds set name = ... where id
  = ... returning updated_at::text as u1`. Compare server-side:
  `select ${u1}::text::timestamptz > ${u0}::text::timestamptz as later` and
  assert `later === true`. Do not assert `u1 = u0 + 1µs` - the exact step is
  an implementation detail; strictly-greater is the criterion. One hour is
  the margin: the whole db suite runs in well under that, so
  `clock_timestamp()` cannot overtake the stored stamp during the test.
- **Oracle partition.** Both criteria are mechanical: a boolean read out of
  SQL. No threshold to calibrate, no invented metric. The negative controls
  are the two mutants, run in RED (`## Deferred verifications`).
- **Clean-up.** `truncateClientTables` in the suite's existing hooks covers
  the inserted kinds; no new teardown.
- **Callers of changed signatures:** none - no export changes.
