## Context

EPIC-04, from `docs/wiki/audits/epic-04-2026-11-06.md` (Decided 2; Evidence
E-HAND EV72, KA55 and E-STRYKER `src/sync/eventActions.ts`).

CAL-015 routes the app's writes through the outbox: each action writes the
cache, queues one op and, **when the device is online**, starts one drain run
at once (`queuedResult`, `outbox.ts:326-334`, PO decision 7). "Online" is the
factory's third parameter, defaulting to `navigator.onLine`
(`eventActions.ts:72`, `kindActions.ts:55`). Every test of the outbox actions
passes its own `online` function, so the default the app actually runs on is
never exercised.

Replace that default with `() => false` and **the whole unit project still
passes** (EV72: 3000/3000. KA55: 2998/3000, and its two failures were
`ConfirmPage.test.tsx` cases, one a 5000 ms timeout, in a suite that does not
import `kindActions`; the narrowed re-run KA55b passed 765/765).
Under that defect an edit made online is queued and never
sent: no `online` event fires while the network stays up, the Realtime rejoin
and the foreground return run only the pull, and the status reads "Syncing 1
change" until the next sign-in or reconnection. EPIC-04's done-when ("back
online: the edit is on the server within seconds") would fail on every
device that never goes offline.

Test-only: the shipped defaults are believed correct, so each new assertion
passes on arrival and is earned by the mutant its criterion names.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given `createOutboxEventActions(db, drain)` with **no** `online`
  argument and `navigator.onLine` true, when `createEvent`, `updateEvent`,
  `removeEvent` or `restoreEvent` resolves ok, then `drain.run` has been
  called once for it; and with `navigator.onLine` false, not at all. A test
  fails when the default at `eventActions.ts:72` is `() => false`, and when
  it is `() => true` (the offline half).
- **AC-2** - The same for `createOutboxKindActions(db, drain)` and its
  `addKind`, `updateKind` and `deleteKind`. A test fails when the default at
  `kindActions.ts:55` is `() => false` or `() => true`.
- **AC-3** - Given the app's own `eventActions` and `kindActions` instances
  (the exported singletons, over `appDrain`), when one write resolves with
  the browser online, then the app's drain is asked to run (spy on
  `appDrain.run`, or observe the repository call it makes). A test fails when
  either singleton is constructed with an `online` that is always false.

### Block 3 - AC-1 and AC-2: the default, per action

Inside the existing `describe("createOutboxEventActions ...")` /
`describe("createOutboxKindActions ...")`, which already supply `db`
(`freshDb()`), `run` (a `vi.fn` returning a promise that never settles), the
faked `Date`, `crypto.randomUUID` returning `U1` once, and an `afterEach` that
closes the db, restores all mocks and deletes the own `navigator.onLine`.

- Build with **two arguments only**: `createOutboxEventActions(db, { run })`.
- **One case per action and per half**, not one cumulative case. A case stops
  at its first failed `expect`, so a single case walking four actions shows one
  red assertion under the mutant and leaves the other three unearned. With one
  case per action, one mutant run shows every action's assertion red.
  - events: `createEvent`, `updateEvent`, `removeEvent`, `restoreEvent`
  - kinds: `addKind`, `updateKind`, `deleteKind`
- Each case first makes the action resolve `ok` (assert `status: "ok"`), since
  a conflict asks no drain in either half and would make the offline assertion
  vacuous: seed the cache as the existing cases do (`db.events.put(CACHED)`;
  for `restoreEvent` `{ ...CACHED, deletedAt: T1 }`; `db.kinds.put(CACHED)`).
- Online half: `navigator.onLine` true, then `expect(run).toHaveBeenCalledTimes(1)`
  after the one action. Offline half: `navigator.onLine` false, then
  `expect(run).not.toHaveBeenCalled()`.
- **Set `navigator.onLine` explicitly in both halves.** jsdom's own value is
  `true`, so an online case that sets nothing passes by the environment's
  default rather than by what the case states.

### Block 4 - how `navigator.onLine` is controlled (unit project, jsdom)

Two idioms are in use in this repository and both pass in the `unit` gate
today (vitest 5.0.4):

1. `Object.defineProperty(navigator, "onLine", { configurable: true, value })`
   - the idiom of these two files and of `drain.test.ts`; undone by the
   `delete (navigator as { onLine?: boolean }).onLine` already in each
   `afterEach`. **Use this one**: its cleanup is already in place here.
2. `vi.spyOn(navigator, "onLine", "get").mockReturnValue(value)` - used in
   `src/auth/SignInPage.test.tsx`, `src/capture/captureClient.test.ts`,
   `src/capture/CapturePage.test.tsx`; undone by `vi.restoreAllMocks()`.

Not measured: idiom 2 inside these two files, next to idiom 1's `delete`. RED
may use it, and then says so here and shows that an offline case running after
an online one still reads `false`.

### Block 5 - AC-3: the real singletons, without a network

- **Route: a spy on the real `appDrain`, not a module mock of `./startSync`.**
  `vi.spyOn(appDrain, "run")` with a replaced implementation, as
  `src/sync/startSync.test.ts:191` and `src/sync/SyncStatus.test.tsx:411`
  already do. A `vi.mock("./startSync")` would hand the singletons a stand-in
  drain and prove only that the factory was called with whatever the mock
  exports; the spy leaves the singleton's real construction (its real third
  argument, or the absence of one) in the path, which is what AC-3's mutant
  changes. `import { appDrain } from "./startSync"` is new to both test files.
- The spy **replaces** `run` (`mockReturnValue(new Promise(() => {}))`, or a
  resolved `{ sent: 0, stoppedAt: "end" }`): the real pass would go to the
  mocked Supabase client, which is not this story's subject.
- `navigator.onLine` set to `true` explicitly (Block 4); one write through the
  singleton (`eventActions.createEvent(NEW_EVENT)`, `kindActions.addKind(NEW_KIND)`)
  resolves `ok`; then `expect(spy).toHaveBeenCalledTimes(1)`.
- One case in each file: AC-3 says "either singleton", and each singleton is
  its own construction site.
- **Reset between cases**, as the existing singleton cases do: the app's `db`
  (`(await import("./db")).db`) is shared by every case in the file and is not
  `freshDb()`, so clear every table before and after
  (`await Promise.all(appDb.tables.map((t) => t.clear()))`); the spy goes with
  the `afterEach`'s `vi.restoreAllMocks()`; `navigator.onLine` with its `delete`.
  `crypto.randomUUID` yields `U1` once per case from the `beforeEach`.
