## Context

EPIC-04, brief §4.7: installable on Android, works offline, and (in CAL-022)
a share target - which requires an installed PWA on a fixed secure origin.
`stack.md`: `vite-plugin-pwa` in `injectManifest` mode, so `src/sw.ts` is
ours; the manifest is a typed object in `src/pwa/manifest.ts` that
`vite.config.ts` hands to the plugin, so a unit test can read it. The app
shell (HTML, JS, CSS, icons) is precached so the page opens with no network;
the data for it comes from CAL-014's cache.

Required gates that would fail if this broke: `unit` (the manifest object,
registration) and `integration` (a real browser opening the built app
offline). `integration` is optional repo-wide, so it is in `required_gates`;
this story is the first to require it and therefore probes it.

## Acceptance criteria

- **AC-1** - Given `src/pwa/manifest.ts`, when it is read, then it has `name`
  "Clean Calendar", a `short_name`, `start_url` "/", `scope` "/", `display`
  "standalone", `theme_color` and `background_color` equal to the light
  `--color-surface-raised` and `--color-surface`, and icons of 192 and 512
  pixels plus a 512 `maskable` icon whose files exist under `public/icons/`.
- **AC-2** - Given `pnpm build`, when `dist/` is inspected, then it contains
  `manifest.webmanifest` with those fields, `sw.js`, and a precache manifest
  listing `index.html` and every emitted JS and CSS asset.
- **AC-3** - Given the app loaded once in Chromium from `vite preview`, when the
  context goes offline and the page reloads, then the app shell renders (the
  sign-in page with "Sign-in needs a connection", since the test has no
  session) rather than the browser's offline error.
- **AC-4** - Given a new build is deployed while the app is open, when the
  service worker updates, then the toast "A new version is ready." with
  "Reload" is shown; pressing it activates the new worker and reloads.
- **AC-5** - Given Chromium, when the built app is served, then the page is
  installable: the manifest is linked from `index.html` and Chromium's
  installability check reports no errors (Playwright via CDP
  `Page.getInstallabilityErrors`).

### Block 1 - the manifest object (AC-1)

`src/pwa/manifest.ts` exports one named constant and its type; no default
export, no side effects, importable from both `vite.config.ts` and a jsdom test:

```ts
export type ManifestIcon = { src: string; sizes: string; type: "image/png"; purpose?: "maskable" };
export const manifest: {
  name: "Clean Calendar"; short_name: string; start_url: "/"; scope: "/";
  display: "standalone"; theme_color: string; background_color: string;
  icons: ManifestIcon[];
};
```

- `theme_color` is `#f6f7f9` and `background_color` is `#ffffff` - the LIGHT
  `--color-surface-raised` and `--color-surface` in `src/styles/tokens.css`
  lines 14-15. The test reads both values out of `tokens.css` (the first
  declaration of each in `:root`, not the dark overrides at lines 111+/142+)
  rather than hard-coding them, so a token change fails the test instead of
  leaving the manifest stale.
- `short_name` is non-empty and at most 12 characters (Chromium truncates
  longer launcher labels). The value is GREEN's choice; "Calendar" fits.
- `icons` is exactly three entries: `/icons/icon-192.png` sizes `192x192`,
  `/icons/icon-512.png` sizes `512x512`, `/icons/icon-maskable-512.png` sizes
  `512x512` purpose `maskable`. The two plain icons carry no `purpose`.
- Each `src` maps to `public<src>` on disk; the test asserts the file exists
  AND that its PNG IHDR width and height (bytes 16-23, big-endian) equal the
  declared size - "a file exists" alone is satisfied by an empty file.

### Block 3 - the service worker (AC-3, AC-4's worker half)

`src/sw.ts`, compiled by the plugin to `dist/sw.js`:

- `precacheAndRoute(self.__WB_MANIFEST)` (workbox-precaching), and
  `cleanupOutdatedCaches()`.
- A `NavigationRoute` (workbox-routing) answering every navigation with the
  precached `index.html` via `createHandlerBoundToURL("index.html")`, so a
  reload of `/` or any client route (`/signin`, `/month/2026-10`) offline gets
  the shell, not Chromium's offline page.
- On a `message` event whose `data` is `{ type: "SKIP_WAITING" }`, call
  `self.skipWaiting()`. **No unconditional `skipWaiting()` at install** - that
  would activate a new build under an open page and make AC-4's prompt
  meaningless. `clientsClaim()` (workbox-core) on activate is required, so the
  FIRST install controls the open page without a reload (AC-3's test depends
  on it).

  no share target.

  `src/sw.ts`, so under pnpm they must be DIRECT dependencies; they go into
  `package.json` in GREEN (production-bundled into `sw.js`, so `dependencies`

### Block 4 - registration and the update prompt (AC-4's page half)

`src/pwa/registerSW.ts` (no JSX, no import of `virtual:pwa-register`, so the
unit project loads it without the plugin):

```ts
export type RegisterFn = (options: {
  onNeedRefresh?: () => void;
  onOfflineReady?: () => void;
}) => (reloadPage?: boolean) => Promise<void>;   // vite-plugin-pwa's registerSW shape

export type UpdateSignal = {
  /** Calls listener at once if an update is already waiting. Returns unsubscribe. */
  subscribe(listener: (apply: () => Promise<void>) => void): () => void;
};

export function registerServiceWorker(register: RegisterFn): UpdateSignal;
export function UpdatePrompt(props: { signal: UpdateSignal }): null;
```

- `registerServiceWorker` calls `register` once, with `onNeedRefresh`. When
  `onNeedRefresh` fires, every subscriber (and any later one) receives
  `apply`, which calls the function `register` returned with `true` -
  vite-plugin-pwa's `updateSW(true)`: post `SKIP_WAITING` to the waiting
  worker, then reload on `controllerchange`. Called before any update, a
  listener receives nothing.
- `UpdatePrompt` is a component that renders nothing itself; on an update it
  calls `useMaybeToast()?.showToast({ text: "A new version is ready.", action:
  { label: "Reload", onClick: apply } })` (`src/ui/Toast.tsx`; copy fixed in
  `voice.md`, Toasts). Outside a `ToastProvider` it does nothing and does not
  throw. `tone` is left at its default (`status`, a polite live region).
- `src/main.tsx` imports `registerSW` from `virtual:pwa-register`, calls
  `registerServiceWorker(registerSW)` once at module load, and passes the
  signal down; `src/app/AppShell.tsx` renders `<UpdatePrompt signal={...} />`
  inside its `ToastProvider`. How the signal reaches AppShell (a module-level
  export from a tiny `src/pwa/updateSignal.ts`, a context) is GREEN's choice,
  provided AppShell's existing props and every existing AppShell test are
  unchanged. `tsconfig.json`'s `types` gains `vite-plugin-pwa/client` for the
  virtual module's declaration.
- **Where the prompt shows: the app shell only (PO decision 3).** Signed-out
  screens (sign-in, walkthrough) have no `ToastProvider`; an update arriving
  there is applied on the next load, which is the plugin's default behaviour
  for a waiting worker. No AC is weakened: AC-4 says "while the app is open",
  and the app is the shell.
- The accessible result the unit test asserts: a `role="status"` region
  containing the text `A new version is ready.` and a button with accessible
  name `Reload`; clicking it calls `apply` exactly once.
