## Context

Filed when CAL-015 closed (its PO decision 9). `components.md`, "Event chip"
states: an outbox op refused with a 4xx marks the chip with the danger ring
and a "!" badge, "and opening it shows the error with Retry / Discard". CAL-015
built the chip marker and put Retry / Discard in the sync status indicator's
dialog; it left the sheet alone so as not to widen its scope. The owner who
opens a "not synced" chip still sees a sheet that says nothing about why.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given an event whose outbox op is `failed`, when its chip opens
  the sheet, then the header shows an inline error line (`components.md`,
  Inline error: `--color-danger` glyph and text) reading "{title} couldn't
  sync." followed by the stored error message, with buttons "Retry" and
  "Discard". A test fails when the line is missing or the copy differs.
- **AC-2** - Given that error line, when Retry is pressed, then the op is
  queued again and a drain pass runs; the line disappears once the op is
  gone. A test fails when `retryOp` is not called with the op's `seq`.
- **AC-3** - Given that error line, when Discard is pressed, then the op is
  removed and the cache row takes the server copy (CAL-015 `discardOp`), the
  sheet's fields show the server's values, and the line disappears. A test
  fails when the fields keep the discarded edit.
- **AC-4** - Given an event with no failed op (queued or synced), when its
  sheet opens, then no error line and no Retry / Discard render, and every
  CAL-012 sheet case is unchanged. A test fails when the line renders for a
  queued op.

**Block 1 - `src/sync/sheetSync.ts`, the sheet's door to the outbox.** The
sheet must not read Dexie itself (it is a component; the page and the
stores are where state comes from), and the page should not grow outbox
logic. So one small module, shaped like `eventActions` - a factory over
injected parts, plus the app's instance:

```ts
export type FailedOp = { seq: number; message: string };

export type SheetSync = {
  /** The event's failed `events` op with the lowest seq, or null. Queued ops never count. */
  failedOp(eventId: string): Promise<FailedOp | null>;
  /** retryOp(db, seq), then one drain pass (drain.run()). */
  retry(seq: number): Promise<void>;
  /** discardOp(db, seq, repos), then the event's cache row as it now is (null if gone). */
  discard(seq: number, eventId: string): Promise<Event | null>;
};

export function createSheetSync(
  db: CalendarDb,
  drain: Pick<Drain, "run">,
  repos: Repos,
): SheetSync;

/** The app's: db, appDrain, appRepos (startSync.ts). */
export const sheetSync: SheetSync;
```

`failedOp` reads `db.outbox` in seq order, keeps `status === "failed" &&
table === "events" && id === eventId`, and returns the first as `{ seq,
message: op.error?.message ?? "" }`. It does not consult `event.sync`.
`retry` and `discard` delegate to the shipped `retryOp` / `discardOp`
(`outbox.ts:290-321`); `discard` then returns `db.events.get(eventId)`
(`undefined` → `null`).

**Block 2 - the sheet, `src/events/EventSheet.tsx`.** `EventSheet` gains one
optional prop, `sync?: SheetSync`, defaulting to the app's `sheetSync`
(the same pattern as `actions = eventActions`; the sheet's import graph
already reaches `startSync` through `eventActions`). Behaviour, edit mode
only:

- **When it asks.** Only when `request.mode === "edit"` and
  `request.event.sync === "failed"` (the cached events store sets that
  flag, `cachedStores.ts:146-150`). Every other sheet - create mode, an
  event with no `sync` key, an event whose op is merely queued (`sync:
  "saving"`) - never calls `failedOp`, renders no strip, and is otherwise
  exactly CAL-012's sheet (AC-4). That gate is also why every existing
  `EventSheet.test.tsx` case keeps passing without a `sync` prop: none of
  their events carries `sync`.
- **The strip (AC-1).** When `failedOp` resolves non-null, the sheet shows,
  at the top of the form, **above** the existing `SAVE_FAILED` alert, one
  element with `role="alert"` (`components.md`, "Event sheet", error: "an
  outbox 4xx surfaces as an `role="alert"` strip at the top of the sheet
  with Retry / Discard"; "Error states", alert strips). Its text is
  `` `${request.event.title} couldn't sync.` `` (voice.md, "Sync failed
  (4xx)") followed by the op's `message`, and it holds two `type="button"`
  buttons named exactly "Retry" and "Discard" (never submit buttons: they
  sit inside the form). Styling - `--color-danger-subtle` background,
  `--color-danger` glyph and text, the existing `.alert` treatment - goes
  in `EventSheet.module.css`; jsdom cannot see it, so no test asserts it.
- **Retry (AC-2).** Calls `sync.retry(seq)`; when it resolves, calls
  `sync.failedOp(event.id)` again and shows what that returns: null → the
  strip is gone; non-null → the strip stays with the new message.
- **Discard (AC-3).** Calls `sync.discard(seq, event.id)`; when it resolves
  with a row, the sheet stays open and shows **that row**: every field
  reads the server copy, the strip is gone, the sheet is clean (closing it
  asks nothing), and a later Save patches against that row (its
  `updatedAt` is the token). The mechanism is GREEN's (e.g. the outer
  `EventSheet` remounting `OpenSheet` with the fresh row and a generation
  in its key - `keyOf` alone will not change, since a refused op never
  moved the cache row's `updatedAt`). Focus stays inside the sheet. A
  `null` row (an insert discarded: the event is gone) closes the sheet
  (`onClose()`).

**Block 3 - the page, `src/calendar/CalendarPage.tsx`.** `CalendarPage`
gains `sheetSync?: SheetSync` and passes it to `EventSheet` as `sync`
(`props.sheetSync ?? sheetSync`, beside `actions`). No other change: the
event the chip hands the sheet already carries `sync` from the cached
store.
