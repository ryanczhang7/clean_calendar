## Context

EPIC-07. Source: `docs/wiki/audits/EPIC-07-2026-11-24.md`, Decided 5 and
Evidence `### E-PO2`. CAL-086 left this open in its `## Out of scope`.

The send-reminders function runs unattended every minute, and its `deps.log`
lines (`console.error` in `index.ts`) are the only record of a write that
went wrong. After pushing a due reminder it PATCHes `sent_at`
(`supabase/functions/send-reminders/handler.ts:292-301`). A PATCH that
**throws** is logged (`:302-308`, pinned by CAL-086). A PATCH that
**answers** non-2xx is not: the response is never read. The reminder stays
unmarked, the next minute's run pushes it again, and nothing anywhere says
so. E-PO2 reproduced it: with the PATCH answering 500, one reminder was
pushed 6 times, 09:00 to 09:05, the run answered 200 with `sent: 1` each
time, and there were 0 log lines.

**The decision, made by the user on 2026-11-24: log it and keep retrying.**
Repeats inside the due window are accepted, because delivering a reminder at
least once is better than losing one. The run's HTTP status and response
body do not change. The fix is one log line, shaped like the failed-DELETE
line at `handler.ts:273-276`.

What is settled and what is not. The **decision** above is settled, and this
story implements it without re-opening it. The audit's **evidence** (six
pushes over seven runs) was measured by a scratch script that no longer
exists; no criterion here depends on that number. The criteria below are
about one run, which is all the handler sees.

Required gate that would fail if this broke: `deno-test` (required; it
covers `supabase/functions/**` and runs `handler_test.ts`). `deno-check`
(required) type-checks both files. No optional gate holds any of this
story's evidence, so `required_gates` stays empty.

## Acceptance criteria

- **AC-1** - Given two due reminders, one subscription that accepts every
  push, a PATCH of the **first** reminder's `sent_at` that answers 500 and a
  PATCH of the second that answers 204, when the run is invoked, then
  `deps.log` holds exactly one line,
  `send-reminders: marking reminder <first id> sent failed: 500`; the
  response is 200 with
  `{ due: 2, sent: 2, pruned: 0, failed: 0, materialised: 0 }`; and each
  reminder is pushed once and then PATCHed once, the first before the
  second. (Today the log is empty: this is the bug.)
- **AC-2** - Given one due reminder, one subscription that accepts the push,
  and a PATCH of its `sent_at` that answers 200 (a 2xx that is not 204),
  when the run is invoked, then the PATCH was made exactly once, the
  response is 200 with
  `{ due: 1, sent: 1, pruned: 0, failed: 0, materialised: 0 }`, and
  `deps.log` is empty.

## Out of scope

- **Failing the run** when a `sent_at` write is refused (a 5xx or 502 from
  the function, or a count in the body). Rejected by the user on
  2026-11-24: the status and the body stay as they are.
- **Writing `sent_at` before the push.** Rejected by the user on
  2026-11-24: it trades a repeat for a reminder that can be lost, and at
  least once is the rule (`docs/wiki/architecture.md`, Reminders).
- Stopping the repeats any other way: retrying the PATCH inside the run,
  remembering the reminder between runs, or changing the five-minute
  window. A reminder whose write keeps being refused is pushed once a
  minute while it is due, up to six times (audit E-PO2), and that is
  accepted.
- A count of refused writes in the response body. `counts.failed` stays the
  count of refused pushes.
- The thrown-PATCH line and both DELETE lines. CAL-086 pinned them; they do
  not change.
- Whether a phone re-alerts when a repeat replaces the notification with
  the same `tag`. The audit did not check it, and nothing here depends on
  it.
- Proving the repeat across runs in a test. The handler holds no state
  between runs; the repeat follows from the candidate read still returning
  the unmarked row, which is the database's side and is not faked here.
