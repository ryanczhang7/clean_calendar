## Context

EPIC-05, brief §3 step 4 and success criterion 2: a booking e-mail becomes a
correct, correctly coloured event in under 30 seconds including review. This
is the in-app path (a paste box and an image picker); the share-sheet path
(CAL-022) lands on the same screens. Screens: `components.md`, "Capture
screen" and "Confirm screen"; copy: `voice.md`. The confirm screen reuses
`EventForm` from CAL-012 and saves through `createEvent` with
`origin: 'capture'` and the job id. Nothing is saved before the owner
confirms.

Required gate that would fail if this broke: `unit` (the function call is
mocked at `supabase.functions.invoke`).

## Acceptance criteria

- **AC-1** - Given `/capture`, when it renders, then it shows the heading
  "Capture", a textarea labelled "Booking email or text", a "Choose a
  screenshot" control (`<input type="file" accept="image/*">`), and "Propose
  event", which has `aria-disabled="true"` until one input has content.
- **AC-2** - Given text pasted, when "Propose event" is pressed, then the
  function `capture` is invoked with `{text}`, the inputs become read-only,
  the status line "Asking the assistant… usually takes a few seconds." is
  shown, and on success `/capture/confirm` renders the proposal in the event
  form.
- **AC-3** - Given an image picked, when it is proposed, then it is downscaled
  so that its long edge is at most 2048 px and its encoded size at most 4 MB,
  sent as `{image, mime}`, and a 96px thumbnail with "Remove screenshot" was
  shown; with both text and an image present only the image is sent and a note
  says so.
- **AC-4** - Given `navigator.onLine` is false, when `/capture` renders, then
  "Propose event" is disabled and "Capture needs a connection. Your other
  changes are saved and will sync." is shown; given the function returns an
  error, an alert reads "Couldn't read that. Try pasting the text instead."
  with "Retry".
- **AC-5** - Given the confirm screen, when "Save event" is pressed, then
  `createEvent` is called with the edited values, `origin: 'capture'` and the
  `captureJobId`, the job is marked `confirmed`, the app navigates to that
  day in the last-used view with the new chip focused, and the toast "Added
  {title}" with "View" is shown.
- **AC-6** - Given the confirm screen, when "Discard" is pressed, then no event
  is created, the job is marked `discarded`, and `/capture` renders empty.
- **AC-7** - Given the proposal's `kindName`, when the confirm form fills, then
  the kind picker shows the live kind with that name, and every field stays
  editable; "Show what was captured" reveals the original text (or image) for
  comparison, which is not persisted.

### Block 1 - the function client (AC-2, AC-3, AC-4)

`src/capture/captureClient.ts`:

```ts
import { captureResponseSchema, type CaptureResponse } from "../../shared/captureSchema";
export type CaptureInput = { text: string } | { image: string; mime: string };
export type CaptureOutcome =
  | { status: "ok"; response: CaptureResponse }
  | { status: "offline" }                                   // navigator.onLine false, or the fetch threw
  | { status: "error"; code: "upstream" | "unreadable" | "bad_request" | "payload_too_large" | "unsupported_media_type" | "forbidden" | "unauthorized" | "unknown"; http?: number };
export async function proposeEvent(input: CaptureInput, client: SupabaseClient<Database> = supabase): Promise<CaptureOutcome>;
/** What /capture hands /capture/confirm in router state (PO decision 3). */
export type CaptureSource = { kind: "text"; text: string } | { kind: "image"; dataUrl: string; mime: string };
export type CaptureHandoff = { response: CaptureResponse; source: CaptureSource };
```

- Mechanism: `client.functions.invoke("capture", { body: input })`, which
  POSTs `{SUPABASE_URL}/functions/v1/capture` with the session's bearer. A
  reply with `error === null` and `data` that passes `captureResponseSchema`
  is `ok`; `data` failing the schema is `error "unreadable"`; a
  `FunctionsHttpError` is `error` with `code` read from the function's JSON
  `{error}` body when it parses and `http` set to the status; a
  `FunctionsFetchError` (network) is `offline`. **Checkable, not sacred**:
  the test drives the real supabase-js client at `TEST_ORIGIN` with MSW
  answering `POST http://supabase.test/functions/v1/capture`, exactly as the
  repository tests do for PostgREST; if supabase-js 2.117's functions client
  shapes the request or the errors differently, RED amends this block with
  what it measured.
- Nothing in `src/` names the Gemini host or key (CAL-018 AC-7 guard still
  runs).
- **RED amendment (2026-10-26, test-developer), measured not assumed.** Read
  `@supabase/functions-js` 2.117.3 (`dist/main/FunctionsClient.js`, `types.js`)
  and drove the real client through `src/test/supabase-mock.ts` + MSW. The
  mechanism above holds: `invoke("capture", { body })` sends
  `POST http://supabase.test/functions/v1/capture`, no query string,
  `content-type: application/json`, the JSON body, `apikey` and
  `authorization: Bearer <token>` (the anon key under the mock, which sets
  `accessToken: async () => null`); a non-2xx resolves
  `{ data: null, error: FunctionsHttpError }` with the `Response` as
  `error.context` (its JSON body still readable); a rejected fetch is a
  `FunctionsFetchError`; a 2xx is parsed by content type (JSON → object,
  anything else → text, which then fails the schema → `unreadable`). Three
  cases the block did not name, now pinned:
  - a reply with `x-relay-error: true` is a **`FunctionsRelayError`** (also
    with the Response as `context`): it is `error "upstream"` with `http` -
    the relay could not reach the function, which is the function's own
    meaning of `upstream`;
  - a non-2xx whose body is not JSON, or is JSON without a string `error`, or
    names a code outside the union (`method_not_allowed`, 405 - the function
    can send it) is `error "unknown"` with `http`;
  - `navigator.onLine === false` resolves `offline` **without sending a
    request** (the comment on `offline` above, read as a short-circuit).
  - `unreadable` from a schema failure on a 2xx carries **no** `http` key; only
    a `FunctionsHttpError`/`FunctionsRelayError` sets `http`.

### Block 2 - the downscaler (AC-3)

`src/capture/downscale.ts`:

```ts
export const MAX_LONG_EDGE = 2048;
export const MAX_IMAGE_BYTES = 4 * 1024 * 1024;              // the function's limit, CAL-019
export const QUALITY_STEPS = [0.92, 0.8, 0.65, 0.5] as const;
/** Pure: the target size. The long edge is capped at `maxEdge`, the aspect kept (rounded), never upscaled. */
export function planDownscale(width: number, height: number, maxEdge?: number): { width: number; height: number; scaled: boolean };
export type Downscaled = { mime: "image/png" | "image/jpeg" | "image/webp"; base64: string; bytes: number; width: number; height: number; dataUrl: string };
export type DownscaleDeps = {
  /** Decode a file: its pixel size and an opaque handle the encoder accepts. */
  decode(file: Blob): Promise<{ width: number; height: number; source: unknown }>;
  /** Draw `source` at width x height and encode it; `quality` applies to lossy types. */
  encode(source: unknown, width: number, height: number, mime: string, quality: number): Promise<Blob>;
};
export const browserDeps: DownscaleDeps;                       // createImageBitmap + canvas; untested in jsdom
export async function downscaleImage(file: Blob, deps?: DownscaleDeps): Promise<{ status: "ok"; image: Downscaled } | { status: "too_large" } | { status: "unsupported" }>;
```

- `planDownscale(4000, 3000)` is `{2048, 1536, scaled: true}`;
  `(3000, 4000)` is `{1536, 2048}`; `(1024, 768)` is unchanged with
  `scaled: false`; `(2048, 10)` is unchanged. Rounding is `Math.round`, with
  a floor of 1.
- Pipeline: `unsupported` unless `file.type` is one of the three accepted
  types; decode; plan; encode at the planned size with the file's own type at
  `QUALITY_STEPS[0]`; while the result is over `MAX_IMAGE_BYTES`: a PNG
  re-encodes as `image/jpeg` first (lossless PNG screenshots are the large
  case), then each type steps down `QUALITY_STEPS`; after the last step
  still over -> `too_large`. `bytes` is the encoded Blob's size; `base64` is
  the standard-alphabet encoding of its bytes (what CAL-019's function
  accepts); `dataUrl` is `data:<mime>;base64,<base64>` for the thumbnail and
  the "what was captured" view.
- Tests use a fake `deps` whose `encode` returns a Blob of a size the test
  chooses per (mime, quality) call, so the step-down order is observable
  without a canvas; jsdom has none.

- **"Show what was captured"** / "Hide what was captured": a
  `<button type="button" aria-expanded>` toggling a region (`hidden` when
  collapsed) holding `<pre>` with the text, or
  `<img alt="The screenshot you captured">` from the data URL. The source is
  read from router state only; the test asserts no `localStorage` key and no
  PostgREST body carries it.
- **RED amendment (2026-10-26, test-developer).**
  - **Date-only all-day starts are local calendar days.** Measured on this
    host (America/Chicago): `new Date("2026-11-03").getDate()` is **2**, and in
    America/Los_Angeles likewise - so `newEventValue(new Date("2026-11-03"), …,
    true, …)` would show **2 November**. The sentence above ("lands on the
    right calendar day in zones west of UTC only when allDay is true") is
    therefore not what `new Date` does. Amended rule: a `startsAt`/`endsAt`
    matching `^\d{4}-\d{2}-\d{2}$` is read as **local midnight of that date**
    (e.g. `new Date(y, m - 1, d)`), not UTC midnight. The test pins the
    all-day case in America/Los_Angeles (`inZone`, which switches
    `process.env.TZ` and restores the previous zone *name* - deleting TZ was
    measured to leave the last zone cached). Date-only + timed stays GREEN's
    choice, as the block already said.
  - **All-day ends**: with `allDay: true` the form value comes from
    `newEventValue`, which makes `endDate === startDate` whatever `endsAt`
    says. The tests pin only the `endsAt: null` all-day case; a multi-day
    all-day proposal is not constrained.
  - **"The live kind"**: a kind with `deletedAt` set is never matched, even if
    it appears in `kinds`.
  - **Kinds arrive after the first render.** The page test uses the real
    `createKindsStore`, which starts `loading` and becomes `ready` a tick
    later (as the app's cached store does). The kind lookup must therefore
    apply once the kinds are ready - an initial value computed only on the
    first render with `[]` leaves the picker empty and fails AC-7.
  - Toasts: the no-state status line is found with `getByRole("status")` in a
    render **without** `ToastHost` (whose live region is also
    `role="status"`); in the app shell both exist, so GREEN should not rely on
    being the only status region.
