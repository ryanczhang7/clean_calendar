## Context

EPIC-04, from `docs/wiki/audits/epic-04-2026-11-06.md` (Decided 3 and 9;
Evidence E-STRYKER `src/sync/syncState.ts`, E-HAND SST56, S1, S2,
S1-order).

The sync status (CAL-015 AC-7, Block 7) follows `navigator.onLine` through
the window's `online` and `offline` events. `createSyncStateStore(db, drain,
target?)` takes the window as an optional third argument and falls back to
the global `window` (`syncState.ts:56`). **Every test passes `window`
explicitly**, and the app's own store, `syncState`, is the one built without
it (`:102`). With `target ?? (…)` made `target && (…)`, the app's indicator
never hears the network change: it keeps the state it read at subscribe.
The whole unit project passes (3000/3000, E-HAND SST56). The indicator is
the owner's only cue that an edit is waiting (EPIC-04 done-when: "Airplane
mode: … an edit is accepted").

Two tests claim more than they pin (Decided 9):

- "re-reads the counts on every changed notice, and calls its listener"
  passes with the drain subscription doing nothing at all (S2: 535/535 over
  `src/sync`), because the outbox liveQuery added in CAL-015's Return 1 also
  sees the write. Measured order (S1-order): the re-read resolves first and
  the liveQuery's emission lands after it and wins.
- "after the last unsubscribe it leaves the drain and the window alone"
  passes with the window listeners never removed (Stryker `:74:32`,
  `:75:32`): after the last unsubscribe the store has no listener to call,
  so `setOnline(false)` notifies nobody either way.

Test-only: the shipped module is believed correct, so each new assertion
passes on arrival and is earned by the mutant its criterion names.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given a store built with **no** `target` (as the app's
  `syncState` is), subscribed, when the window fires `offline` with
  `navigator.onLine` false, then the snapshot's `online` is false; and on
  `online`, true again. A test fails when `syncState.ts:56` is `target &&
  (…)`, or when its `typeof window === "undefined"` is `true` or `!==`
  (audit SST56; Stryker `:56:17`, `:56:28` ×2).
- **AC-2** - Given a store subscribed and then fully unsubscribed, when the
  window later fires `online` or `offline`, then the store's handler is no
  longer attached: `removeEventListener` was called for each type with the
  function `addEventListener` received (a spy on the target is acceptable),
  and a fresh subscribe afterwards leaves exactly one handler per type
  attached. A test fails when either `removeEventListener` at `:74` or `:75`
  is given another type (Stryker `:74:32`, `:75:32`).

**Block 1 - the module under test, as it is.** `src/sync/syncState.ts`
exports, and this story changes none of them:

```ts
export type SyncState = { online: boolean; queued: number; failed: number };
export type SyncStateStore = {
  subscribe(listener: () => void): () => void; // returns the unsubscribe
  getSnapshot(): SyncState;                    // same object until a value changes
};
export function createSyncStateStore(
  db: CalendarDb,
  drain: Pick<Drain, "subscribe">,
  target?: Window,
): SyncStateStore;
export const syncState: SyncStateStore;        // createSyncStateStore(appDb, appDrain) - no target
export function useSyncState(store?: SyncStateStore): SyncState;
export function statusLabel(s: SyncState): string;
```

What the new cases lean on, read from the source at `3875f33`:

- Nothing is attached before the first `subscribe()`. The first subscribe
  runs `start()`, which resolves the window **once** (`:56`: `target`, else
  the global `window`, else nothing), makes **one new** `onNetwork` function
  (`:57`) and calls `addEventListener("online", onNetwork)` then
  `addEventListener("offline", onNetwork)` - the same function for both
  types, two arguments, no options (`:58-59`).
- `onNetwork` reads `navigator.onLine` at the time of the event and
  publishes synchronously (`:57`, `:23-24`); the event's own type is not
  read. So "the window fires `offline` with `navigator.onLine` false" needs
  both: the property set, then the event dispatched.
- The unsubscribe that empties the listener set calls
  `removeEventListener("online", onNetwork)` and
  `removeEventListener("offline", onNetwork)` with that same function
  (`:74-75`), then leaves the drain and the liveQuery. A later subscribe
  runs `start()` again: a **different** `onNetwork`, attached once per type.

No exported signature changes, so there are **no callers to list**.

**Block 2 - what the test file already gives (reuse, do not rebuild).** The
unit project runs under jsdom (`vitest.config.ts:12`), so the global
`window` and `navigator` exist and `createSyncStateStore(db, drain)` with no
third argument falls back to that `window`. `beforeEach` makes `db =
freshDb()`, empties `listeners`, zeroes `unsubscribed` and clears
`drain.subscribe`; `afterEach` runs `cleanups`, closes `db` and deletes the
own `navigator.onLine` property, so every case starts from jsdom's `true`.
Helpers: `drain` (a `vi.fn` fake that records its listeners and counts
unsubscribes), `emit(notice)`, `op(id, status)`, `cleanups`, and

```ts
const setOnline = (value: boolean) => {
  Object.defineProperty(navigator, "onLine", { configurable: true, value });
  window.dispatchEvent(new Event(value ? "online" : "offline"));
};
```

which is exactly "the window fires the event with `navigator.onLine` set",
on the **global** window. No fake timers (fake-indexeddb and liveQuery run
on real ones). No new dependency. `vitest.config.ts` sets no
`restoreMocks`, so **a spy the case installs is restored by the case**
(push its `mockRestore` onto `cleanups`); a spy left on `window` leaks into
every later case in the file.

Baseline, measured 2026-11-14 on `3875f33`: `pnpm exec vitest run --project
unit src/sync/syncState.test.ts` is **17 passed (17)**.

**Block 3 - AC-1, the store built with no target.** One case, in the
`createSyncStateStore (Block 7)` describe, beside the existing "follows the
window's offline and online events" case, which it mirrors with the one
difference that matters:

- `const store = createSyncStateStore(db, drain);` - **two arguments**. Not
  `window`, not `undefined` spelled out by a helper that then passes it on,
  and not the exported `syncState` (that one holds the app's `db` and
  `appDrain`; the criterion is about the fallback, which this reaches with
  the file's own fixtures).
- `cleanups.push(store.subscribe(() => {}))`.
- Control, asserted: `store.getSnapshot().online` is `true` before any
  event. Without it the `false` below could be the value read at subscribe.
- `setOnline(false)`, then expect `online` to be `false`; `setOnline(true)`,
  then expect `true`. `vi.waitFor` as the neighbouring case does, or a
  direct assertion (the publish is synchronous) - RED's choice.

Under every `:56` mutant in Block 6 the store resolves no window, attaches
nothing, and keeps the `true` it read at subscribe: the first expectation
is the red.

**Block 4 - AC-2, the handlers are removed, by type and by function.** One
case (RED may split it into "removed" and "re-subscribe" if that reads
better; the Deferred entries then name both). It passes **`window`
explicitly** as the target and spies on that same object:

```ts
const add = vi.spyOn(window, "addEventListener");
const remove = vi.spyOn(window, "removeEventListener");
cleanups.push(() => { add.mockRestore(); remove.mockRestore(); });
```

Passing `window` is deliberate: the case then does not depend on `:56`, so
an AC-1 mutant reds AC-1's case and nothing else, and the counts in
`## Deferred verifications` stay one-to-one. (A hand-made spied target
object is the criterion's other permitted form; the global window is
preferred because nothing has to be cast to `Window`.) `vi.spyOn` calls
through, so the real listeners are still attached and removed.

jsdom, React and Testing Library may add window listeners of their own, so
**every count filters `mock.calls` by `call[0] === "online"` or
`"offline"`**; never assert on the total number of calls.

1. `const stop = store.subscribe(() => {})`. The filtered `add` calls are
   exactly one for `"online"` and one for `"offline"`; take the function
   each received (`call[1]`). (They are the same function; the case need
   not assert that, the criterion does not ask it.)
2. `stop()`. The filtered `remove` calls are exactly one per type, and
   `remove` was called with `("online", <the function add got for
   "online">)` and with `("offline", <the function add got for
   "offline">)` - compared by identity (`toBe` / `toHaveBeenCalledWith` on
   the captured function), not by `expect.any(Function)`, which a mutant
   passing some other function would satisfy.
3. Fresh subscribe: `cleanups.push(store.subscribe(() => {}))`. "Exactly
   one handler per type attached" is read off the ledger the two spies
   keep: per type, the functions `add` received **minus** those `remove`
   received for that same type, compared by identity, has length 1. Under
   a `:74` or `:75` mutant one type's first handler was never removed and
   that type's ledger holds two.

The `drain.subscribe` wait the neighbouring cases use is not needed:
`start()` attaches synchronously inside `subscribe()`.

The existing case "after the last unsubscribe it leaves the drain and the
window alone" stays as it is. Renaming or rewriting it is not in the
criteria; the new case is what makes its title true.
