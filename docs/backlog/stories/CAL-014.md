## Context

EPIC-04, brief §6 ("the PWA must open and show the calendar without a
network") and success criterion 3. `architecture.md`, "Where state lives":
the UI renders **only** from a local Dexie (IndexedDB) copy of kinds, events,
overrides and reminders - one user, a few thousand rows, so a full copy. This
story creates that database with every table later stories need (including
the `outbox` CAL-015 fills), hydrates it from the server, and moves
`useKinds` (CAL-006) and `useEventsInRange` (CAL-009) onto it **behind their
existing signatures**, so no view changes. It adds `useOverrides` for
CAL-024.

Required gate that would fail if this broke: `unit` (IndexedDB is provided by
`fake-indexeddb` in tests).

## Acceptance criteria

- **AC-1** - Given an empty cache and the network up, when sync starts after
  sign-in, then every live and soft-deleted row of `kinds`, `events` and
  `event_overrides` is written to the cache and the high-water mark (the
  greatest `updated_at` seen) is stored.
- **AC-2** - Given a populated cache, when sync starts again, then only rows
  with `updated_at` greater than the stored mark are requested (`listSince`),
  and each is upserted - a soft-deleted row stays in the cache marked deleted
  and leaves the views.
- **AC-3** - Given a populated cache and the network down, when the calendar
  opens, then `useKinds` and `useEventsInRange` return the cached rows and the
  month renders them, with no request attempted before the first render.
- **AC-4** - Given a cached row changes (written by sync or by an action), when
  a component is mounted on `useEventsInRange`, then it re-renders with the new
  value without a reload (`useLiveQuery`).
- **AC-5** - Given `useEventsInRange(start, end)`, when the cache holds events
  inside, overlapping and outside the range, then it returns exactly those
  that overlap `[start, end)` and are not deleted.
- **AC-6** - Given IndexedDB cannot be opened, when the app starts, then the
  full-page error "Can't open the calendar" with the line "Reload to try
  again." and a "Reload" button renders instead of the calendar.

### Block 1 - `src/sync/db.ts`

import Dexie, { type DexieOptions, type Table } from "dexie";
import type { Event, EventOverride, Kind } from "../data/rows";
export type OutboxOp = { seq?: number; op: "insert" | "update" | "delete"; table: "kinds" | "events" | "event_overrides" | "reminders"; id: string; patch: unknown; expectedUpdatedAt: string | null; clientTs: string };

export type ReminderRow = { id: string; eventId: string; minutesBefore: number; sentAt: string | null; occurrenceDate: string | null; createdAt: string; updatedAt: string };

  reminders: Table<ReminderRow, string>;   // declared here, filled by CAL-026

### Block 2 - `src/sync/hydrate.ts`

```ts
import type { ListResult } from "../data/result";
export type SyncRepos = {
  kinds: { listSince(since: string): Promise<ListResult<Kind>> };
  events: { listSince(since: string): Promise<ListResult<Event>> };
  overrides: { listSince(since: string): Promise<ListResult<EventOverride>> };
};
export const EPOCH = "1970-01-01T00:00:00+00:00";
export type SyncResult = { status: "ok" } | { status: "unavailable" };
/** One pass: for kinds, then events, then overrides - read the table's mark
 *  (meta key "mark:kinds" / "mark:events" / "mark:overrides"; absent →
 *  EPOCH), call listSince(mark), bulkPut every returned row as is (a
 *  soft-deleted row is stored with its deletedAt), then store the new mark:
 *  the greatest `updatedAt` among the returned rows, unchanged when none.
 *  A non-ok list stops the pass there: that table and the ones after it are
 *  untouched, earlier tables keep what they wrote, and the result is
 *  "unavailable". Never throws; a cache error is "unavailable" too. */
export function hydrate(db: CalendarDb, repos: SyncRepos): Promise<SyncResult>;
export type Sync = { run(): Promise<SyncResult> };
/** Concurrent run() calls share one in-flight pass. */
export function createSync(db: CalendarDb, repos: SyncRepos): Sync;
```

**The mark is a string, compared as a string**, and sent back byte for byte
(the same reason `updatedAt` is a string in `rows.ts`). PostgREST returns
every `timestamptz` in one format and offset, so lexicographic order is time
order there; a `Date` would drop the microseconds and re-request the last row
forever. Rows sharing the mark's exact `updated_at` and committed after the
pass are missed by `gt`. That is a known limit, recorded under `## Notes`,
and not fixed here (CAL-033 owns `updated_at`). AC-1 is the empty-cache
pass: `listSince(EPOCH)` on all three tables. AC-2 is the second pass:
`listSince(<stored mark>)` and an upsert, so a row that is now soft-deleted
replaces its live copy.

### Block 4 - `src/sync/cachedStores.ts`

```ts
export function createCachedKindsStore(db: CalendarDb, seedRepo: SeedRepo, sync: Sync): KindsStore;
export function createCachedEventsStore(db: CalendarDb, sync: Sync): EventsStore;
export function createCachedOverridesStore(db: CalendarDb, sync: Sync): OverridesStore;
```
Common semantics:
- **Nothing at construction.** No Dexie open, no query and no sync until the
  first `subscribe()`. This is AC-3's "no request attempted before the first
  render", and module import must stay side-effect free, since every suite
  imports these.
- On the first `subscribe()`, a Dexie `liveQuery` over the whole table. Each
  emission publishes `"ready"` with the rows, **even when the cache is
  empty**. The last unsubscribe stops it.
- `refresh()` = `sync.run()`, then re-read the table and publish, and only
  then resolve. So CAL-012/013's "an ok write is not handed back until the
  store refreshed" still means the caller sees the new snapshot.
- **A failed sync never changes the status**: offline, the cached rows stay
  `"ready"` (AC-3). Only a cache that cannot be read publishes
  `"unavailable"`. Nothing throws or rejects.
- `getSnapshot()` stays referentially stable between changes.

Kinds: the snapshot is `snapshotOf` over the cache (live kinds sorted, and
`byId` over every row, soft-deleted included). `ensureSeeded()` is the
existing `ensureDefaultKinds(seedRepo)`, decided by the server as in CAL-006.
Unless it returns "unavailable", it then awaits `sync.run()` before
resolving, so the seeded kinds are in the cache when the walkthrough shows.

Events: the snapshot is `liveSorted` over the cache (deletedAt null,
sorted), and `hide(id)` keeps CAL-013's semantics exactly: a count per id,
each reveal acts once, and the event stays hidden across refreshes.
`useEventsInRange(start, end, store)` is unchanged and keeps filtering with
`eventsInRange` (AC-5).

### PO decisions at PLANNED → RED (2026-10-21, lead-po)

1. **Cached stores beside the in-memory ones, not instead of them.** The app
   singletons move onto Dexie behind their existing types and hooks;
   `createKindsStore(repo)` and `createEventsStore(repo)` stay, because every
   view suite builds its stores with them and none of those suites is about
   the cache. The rule "the UI renders only from Dexie" (`architecture.md`)
   holds for the running app, which only ever uses the singletons. `touches:`
   gains `src/sync/cachedStores.ts`, its suite, and `src/test/setup.ts`.
2. **Sync starts from the existing sign-in path.** `RequireOwner` already
   calls `kindsStore.ensureSeeded()` once the owner is signed in; the cached
   kinds store runs `startSync()` once seeding settles. No change to
   `RequireOwner`, and its suite already mocks `../sync/kindsStore`. The
   events and overrides stores also run a sync on their first refresh, and a
   pass already in flight is shared.
3. **`liveQuery`, not the `useLiveQuery` hook.** AC-4's parenthetical names
   Dexie's observation mechanism. The hook form (`dexie-react-hooks`) cannot
   sit behind the existing `useSyncExternalStore` signatures, and it starts
   every consumer at `undefined`. So the stores subscribe to Dexie's own
   `liveQuery` observable, which is the same mechanism underneath, and no new
   production dependency is needed. What AC-4 asserts is unchanged: a
   mounted consumer re-renders when a cached row changes. *Flagged to the
   user before GREEN; overrule it and the stores gain the dependency.*
4. **A mark per table**, in the `meta` table (`mark:kinds`, `mark:events`,
   `mark:overrides`). AC-1's "the high-water mark" is singular; per table is
   the same promise kept separately, so a failure on one table does not move
   another's mark.
5. **Offline with an empty cache shows an empty, ready calendar**, not the
   "unavailable" state: the cache answered, it just has nothing yet. The
   full-page error is only for a cache that cannot be opened (AC-6).
6. **Epic done-when checked.** CAL-014 is EPIC-04's first story. It delivers
   "the calendar renders" offline, but the page itself opening offline is
   CAL-017's (Out of scope), and editing offline is CAL-015's. No gap before
   this story.
7. **Required gate: `unit`** (`covers | unit | src/**`, required).
   IndexedDB comes from `fake-indexeddb` in jsdom. A real browser's IndexedDB
   is CAL-031's smoke.
8. **Known limit, not fixed here.** `listSince` is a strict `gt` on
   `updated_at`. A row that commits after a pass with exactly the mark's
   timestamp is never fetched. CAL-033 owns `updated_at` stamps.
