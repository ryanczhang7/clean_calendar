## Context

EPIC-03, from `docs/wiki/audits/epic-03-2026-10-21.md` (Decided 2;
Evidence E-DST, hand mutants H3, H4, H5).

The month grid, the week's days and the month's keyboard steps all build a
day with `new Date(y, m, d + n)`. That stays on local midnight across a DST
change, where "add 24 hours of milliseconds" does not. Their suites have
cases that catch the milliseconds version, such as "every day is a local
midnight across 24 Oct - 2 Nov" and "ArrowDown from 31 October lands on
7 November". **But only in a zone that changes clocks on 1 November 2026.**
Only `src/domain/moveEvent.test.ts` pins its zone
(`vi.stubEnv("TZ", "America/Chicago")`, with a first case that checks the
pin took effect). The other three suites run in whatever zone the machine
has.

Measured on `bdd31c5`, each mutant against the whole unit project: killed on
the America/Chicago host, and **1603/1603 green under `TZ=UTC`**, which is
what CI's `ubuntu-latest` runner uses:

- `src/domain/monthGrid.ts:21` → `new Date(first.getTime() + (i - lead) * 86400000)`
  (host: 13 failed | 104 passed in `monthGrid.test.ts` + `MonthView.test.tsx`);
- `src/domain/timeGrid.ts:135` (`daysFrom`) → `new Date(first.getTime() + i * 86400000)`
  (host: 2 failed);
- `src/calendar/period.ts:42` (`addDays`) → `new Date(d.getTime() + n * 86400000)`
  (host: 1 failed, "ArrowDown from 31 October lands on 7 November").

So the owner's calendar showing 1 November twice, or skipping a day in the
week of a clock change, would pass CI. A developer on a UTC or no-DST
machine would also see a green local gate run.

Test-only: the shipped functions are believed correct, so each strengthened
assertion passes on arrival and is earned by its mutant, run under
`TZ=UTC`.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given `monthGrid.test.ts` run in a shell with `TZ=UTC`, when
  `monthGrid.ts:21` builds each cell as `first + (i - lead) × 24 h` instead
  of with the date constructor, then a test fails.
- **AC-2** - Given `timeGrid.test.ts` run with `TZ=UTC`, when `daysFrom`
  (`timeGrid.ts:135`) adds `i × 24 h` of milliseconds instead of `i` days,
  then a test fails. The same holds when `weekStart` (`timeGrid.ts:126-127`)
  steps back in milliseconds.
- **AC-3** - Given `period.test.ts` run with `TZ=UTC`, when `addDays`
  (`period.ts:41-42`) adds `n × 24 h` of milliseconds, then a test fails.
- **AC-4** - Given each of the three suites, when it starts, then a case
  asserts the zone it pinned took effect (the UTC offsets on either side of
  that zone's DST change differ), so a pin that silently stops working fails
  the suite rather than making every DST case vacuous. This mirrors
  `moveEvent.test.ts`'s zone guard.
- **AC-5** - Given each of the three suites, when it is run unmutated with
  `TZ=UTC` and with the host's zone, then it passes in both.

## Contract

**Writes:** `src/domain/monthGrid.test.ts`, `src/domain/timeGrid.test.ts`, `src/calendar/period.test.ts`

- The pattern is `src/domain/moveEvent.test.ts:20-29`: `vi.stubEnv("TZ",
  "America/Chicago")` at module level, plus a zone-guard case. Node re-reads
  `TZ` on assignment. Use the same zone so the existing Oct/Nov 2026 cases
  become real contrasts everywhere.
- **Not** a project-wide `TZ` in `vitest.config.ts` or `src/test/setup.ts`
  without the PO's say. That is config, it changes every suite's dates at
  once, and it would make this story touch production configuration. If the
  Test Developer finds the per-file pin unworkable, stop and put it to the
  PO. `touches:` grows only by that decision.
- No production file changes. Each AC is earned in RED by its mutant
  through `scripts/mutate.sh`, run as
  `bash scripts/mutate.sh FILE 'EXPR' -- env TZ=UTC pnpm exec vitest run --project unit <that suite>`,
  with the output pasted into `## Handoff`. The audit's E-DST section has
  the three expressions verbatim.
- Spring-forward cases (March 2027) are welcome but not required. The
  fall-back cases already discriminate once the zone is pinned.
