## Context

EPIC-03, from `docs/wiki/audits/epic-03-2026-10-21.md` (Decided 2;
Evidence E-DST, hand mutants H3, H4, H5).

The month grid, the week's days and the month's keyboard steps all build a
day with `new Date(y, m, d + n)`. That stays on local midnight across a DST
change, where "add 24 hours of milliseconds" does not. Their suites have
cases that catch the milliseconds version, such as "every day is a local
midnight across 24 Oct - 2 Nov" and "ArrowDown from 31 October lands on
7 November". **But only in a zone that changes clocks on 1 November 2026.**
Only `src/domain/moveEvent.test.ts` pins its zone
(`vi.stubEnv("TZ", "America/Chicago")`, with a first case that checks the
pin took effect). The other three suites run in whatever zone the machine
has.

Measured on `bdd31c5`, each mutant against the whole unit project: killed on
the America/Chicago host, and **1603/1603 green under `TZ=UTC`**, which is
what CI's `ubuntu-latest` runner uses:

- `src/domain/monthGrid.ts:21` → `new Date(first.getTime() + (i - lead) * 86400000)`
  (host: 13 failed | 104 passed in `monthGrid.test.ts` + `MonthView.test.tsx`);
- `src/domain/timeGrid.ts:135` (`daysFrom`) → `new Date(first.getTime() + i * 86400000)`
  (host: 2 failed);
- `src/calendar/period.ts:42` (`addDays`) → `new Date(d.getTime() + n * 86400000)`
  (host: 1 failed, "ArrowDown from 31 October lands on 7 November").

So the owner's calendar showing 1 November twice, or skipping a day in the
week of a clock change, would pass CI. A developer on a UTC or no-DST
machine would also see a green local gate run.

Test-only: the shipped functions are believed correct, so each strengthened
assertion passes on arrival and is earned by its mutant, run under
`TZ=UTC`.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given `monthGrid.test.ts` run in a shell with `TZ=UTC`, when
  `monthGrid.ts:21` builds each cell as `first + (i - lead) × 24 h` instead
  of with the date constructor, then a test fails.
- **AC-2** - Given `timeGrid.test.ts` run with `TZ=UTC`, when `daysFrom`
  (`timeGrid.ts:135`) adds `i × 24 h` of milliseconds instead of `i` days,
  then a test fails. The same holds when `weekStart` (`timeGrid.ts:126-127`)
  steps back in milliseconds.
- **AC-3** - Given `period.test.ts` run with `TZ=UTC`, when `addDays`
  (`period.ts:41-42`) adds `n × 24 h` of milliseconds, then a test fails.
- **AC-4** - Given each of the three suites, when it starts, then a case
  asserts the zone it pinned took effect (the UTC offsets on either side of
  that zone's DST change differ), so a pin that silently stops working fails
  the suite rather than making every DST case vacuous. This mirrors
  `moveEvent.test.ts`'s zone guard.
- **AC-5** - Given each of the three suites, when it is run unmutated with
  `TZ=UTC` and with the host's zone, then it passes in both.

**Block 1 - the zone pin, in each of the three files.** The pattern is
`src/domain/moveEvent.test.ts:20-29` verbatim: at module level, after the
imports and before any `describe`,

    vi.stubEnv("TZ", "America/Chicago");
    afterAll(() => {
      vi.unstubAllEnvs();
    });

with `afterAll` and `vi` added to the `vitest` import. Same zone in all
three, so the Oct/Nov 2026 cases already in the files become real contrasts
everywhere. Node re-reads `TZ` on assignment, and that holds inside this
project's vitest pool: the orchestrator ran
`env TZ=UTC pnpm exec vitest run --project unit src/domain/moveEvent.test.ts`
at PLANNED and its zone guard passed (39/39). A named mechanism is
checkable, not sacred: if RED finds the pin not taking effect in one of
these files, stop and say so rather than widening to a project-wide `TZ`
(that is config, frozen in RED, and a PO decision).

**Block 2 - the zone guard, AC-4, one case per file.** The first `describe`
in each file, mirroring `moveEvent.test.ts:49-54`:

    describe("the zone these cases are written for", () => {
      it("is one where Sun 1 Nov 2026 ends daylight saving: 31 Oct is UTC-5, 2 Nov is UTC-6", () => {
        expect(new Date(2026, 9, 31, 12).getTimezoneOffset()).toBe(300);
        expect(new Date(2026, 10, 2, 12).getTimezoneOffset()).toBe(360);
      });
    });

Two literal offsets, not "they differ": a pin that resolved to any other
DST zone would pass a difference check with the wrong contrasts. Under
`TZ=UTC` with the pin removed both offsets are 0 (measured at PLANNED).

**Block 3 - the mutants each AC names, as `sed` expressions.** These are
the audit's E-DST expressions verbatim for AC-1 to AC-3; the `weekStart`
one is new. Each runs through `scripts/mutate.sh` against the one suite:

    bash scripts/mutate.sh FILE 'EXPR' -- env TZ=UTC pnpm exec vitest run --project unit SUITE

**Block 4 - what the existing cases already catch once pinned, and what
RED adds.** Measured at the audit on the America/Chicago host (so: what the
pin alone buys under `TZ=UTC`):

- AC-1: 13 cases in `monthGrid.test.ts` + `MonthView.test.tsx` go red
  (the suite alone: "starts on Monday 28 September…", "runs one day at a
  time…", and the per-month `it.each` rows for 2026-10 and 2026-11 among
  them). The pin is enough; RED adds nothing to the arithmetic.
- AC-2a: "runs across a month end: 30 Oct, 31 Oct, 1 Nov, 2 Nov" and
  "every day is a local midnight across 24 Oct - 2 Nov" go red. The pin is
  enough.
- AC-2b: **not a DST contrast, and that is a PLANNED finding, not a gap.**
  `weekStart` takes an arbitrary instant, so the millisecond version keeps
  the time of day and "Sunday 1 November 23:59 is in the week of Monday 26
  October" kills it in every zone (orchestrator, node: host → Tue 27 Oct
  00:59 CDT; `TZ=UTC` → 26 Oct 23:59Z; both ≠ Mon 26 Oct 00:00). The
  midnight-then-milliseconds variant is **equivalent** under a pin whose
  change falls on Sunday 02:00 (the US rule): a Monday-start week's step
  back never crosses its own Sunday's second hour, measured at PLANNED for
  Nov 1 23:59 in both zones. So AC-2b is satisfied as written by the
  existing case under `TZ=UTC`; RED runs the mutant to show it and need
  not invent a contrast that cannot exist. The pasted result says which
  case failed.
- AC-3: "ArrowDown from 31 October lands on 7 November" goes red. The pin
  is enough. (`shiftPeriod` also uses `addDays`; its week/day cases are
  mid-October and stay green under this mutant - RED may add a
  `shiftPeriod` case across 1 November if it wants a second catch, not
  required.)
- AC-5: the audit's baseline, all three suites unmutated under `TZ=UTC`,
  passed; RED re-runs each suite unmutated under both `TZ=UTC` and the
  host zone and pastes both counts.

**Oracle partition.** Everything is mechanical: dates read out of the
existing cases, two offsets read out of the zone (300, 360), and the
expected reds read out of the audit. Nothing is oracle-free; nothing is
calibrated.

**Callers of changed signatures.** None; no export changes.

**Test command.** `pnpm exec vitest run --project unit <suite>` per file;
