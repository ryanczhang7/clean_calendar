## Context

EPIC-02. Source: `docs/wiki/audits/EPIC-02-2026-11-26.md`, Decided 5, and
Evidence `### E-STRYKER` (group `editor`) and `### E-WHOLE` (N08, N09).
CAL-007 built the kind editor's duplicate-name refusal and its delete
confirmation (`src/kinds/KindEditor.tsx`, Contract Block 5). Both are correct
today. These are markup lines the previous audit did not mutate. Two mutants
survive all 3444 unit tests:

- **N08, `KindEditor.tsx:380`, the name field clearing its error.** With
  `setNameError(null);` replaced by `;`, "You already have a kind called
  Gym." and `aria-invalid="true"` stay on the name field while the owner
  types a different name, until the next Save. The refusal tests
  (`KindEditor.test.tsx:280`, `:295`) stop at the refusal. `:327` checks
  `aria-invalid` is absent on a save that was never refused.
- **N09, `KindEditor.tsx:414`, the confirmation's `onClose`.** With
  `onClose={() => setConfirming(false)}` replaced by `onClose={() => undefined}`,
  Escape on "Delete the kind Gym?" does nothing. `Dialog` prevents the
  browser's own close (`src/ui/Dialog.tsx:47-53`), so the question stays on
  screen until Cancel or Delete is pressed. The confirmation tests press
  Cancel (`:786`) and Delete, never Escape.

This is a test-only story: the production code is right, and the tests pin it.
Each new test passes on arrival, so it has to be earned by putting the
audit's mutant back (see `## Deferred verifications`).

Required gate that would fail if this broke: `unit` (required).

## Acceptance criteria

- **AC-1** - Given the Movies editor beside a live Gym, when the name is set
  to "gym" and Save pressed (so the field is refused), and a letter is then
  typed into the name, then the name field is no longer `aria-invalid` and
  has no accessible description.
- **AC-2** - Given the Gym editor with "Delete the kind Gym?" open, when
  Escape is pressed, then the question closes, nothing is deleted, and the
  "Edit Gym" editor is still open.
