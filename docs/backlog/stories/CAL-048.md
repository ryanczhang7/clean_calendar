## Context

EPIC-05. On the hosted project every capture, text and image alike, fails
with `capture_jobs.error = "upstream 404"` (the owner read it in the Supabase
Table Editor, 2026-10-31; CAL-047 `## Notes`, last entries). Gemini answers
404 for `gemini-2.5-flash`, the model `supabase/functions/capture/gemini.ts`
pins. The Gemini API changelog, entry 2026-09-18, limits the 2.5 models to
users who used them recently and points new projects at 3.5 Flash-Lite or
3.8 Flash; Google Cloud's model lifecycle page lists 2.5 Flash's retirement
as 2026-10-16/20. The owner decided (2026-10-31): "Yes, 3.8 Flash".

`stack.md` records the model as pinned by name rather than `-latest`, "so a
model retirement is a deliberate change here". This story is that deliberate
change, so it updates the decision in `stack.md` and `architecture.md` with
the retirement as the reason, besides the constant and its pins.

What was verified against Google's documentation on 2026-10-31, so RED and
GREEN read it out rather than re-derive it:

- `gemini-3.8-flash` is the stable model id, takes text and image input, and
  lists structured outputs as supported
  (https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash; released
  GA 2026-09-02 per the changelog).
- `POST v1beta/models/{model}:generateContent` is still documented at
  https://ai.google.dev/api/generate-content with no legacy or deprecation
  banner, and https://ai.google.dev/gemini-api/docs/migrate-to-interactions
  says "While `generateContent` remains fully supported, we recommend the
  Interactions API for all new development." The structured-output guide now
  documents only the Interactions API, which is why it is read as "the guide
  moved", not "the endpoint changed".
- The generateContent `Schema` object still carries `nullable`, `minimum`,
  `maximum`, `enum` and the uppercase `Type` enum (`OBJECT`, `STRING`, ...)
  that `geminiResponseSchema` uses (same reference page, `Schema` and `Type`).
- Thinking: 3.8 Flash supports `low`, `medium`, `high`; `minimal` "is not
  supported and returns an error"; the thinking guide lists 3.8 Flash's
  default as "On (medium)". The current request sends no `thinkingConfig`, so
  it never names a level and cannot hit that error. No thinking field is
  added.

So the request changes in two places: the model id, and `temperature` from
`0` to `1.0`. The second is the owner's decision (Notes, PO decision 1): the
Gemini 3 developer guide (https://ai.google.dev/gemini-api/docs/gemini-3)
"strongly recommend[s] keeping the temperature parameter at its default
value of `1.0`" for Gemini 3 models and says setting it below 1.0 "may lead
to unexpected behavior, such as looping".

Required gates that fail if this breaks: `deno-test` (the model, URL and job
row pins in `gemini_test.ts` and `handler_test.ts`) and `deno-check`.

## Acceptance criteria

Both reproduce the defect mechanically: against today's constant, both are red.

- **AC-1** — Given the capture function with any `GEMINI_API_BASE`, when it
  calls Gemini for a text or an image capture, then the one request it makes
  is `POST {base}/v1beta/models/gemini-3.8-flash:generateContent`, and no
  request names `gemini-2.5-flash`. Its `generationConfig.temperature` is
  `1` (Google's recommended default for Gemini 3), for text and image alike.
  Headers (`x-goog-api-key`, `content-type`) and the rest of
  `generationConfig` (`responseMimeType: application/json`,
  `responseSchema`) are unchanged from CAL-018 AC-1.
- **AC-2** — Given a capture that reaches the model, whether the reply is
  usable (`status: proposed`) or not (`status: discarded`, `error: upstream
  <n>` or `unreadable`), when the `capture_jobs` row is written, then its
  `model` column is `"gemini-3.8-flash"`.

  `thinkingConfig`: the request shape is unchanged beyond the model id.
- **No other generation setting.** Temperature moves to `1` (PO decision
  1); `topP`, `topK`, `maxOutputTokens` and `thinkingConfig` stay unset, at
  the model's defaults.
