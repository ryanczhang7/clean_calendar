## Context

EPIC-08, success criterion 1: the owner can only switch if the app is on their
phone from a stable origin, and both the share target and Web Push require a
fixed HTTPS origin. `architecture.md`, "Deployment shape": the static PWA on
Cloudflare Pages, built from `main` by a GitHub Action; the hosted Supabase
project receives migrations (`supabase db push`) and functions
(`supabase functions deploy`) from the same workflow; secrets live in the
dashboards and GitHub, never in the repository. A `chore` with no product
behaviour, but every file it writes classifies as `harness`, `config` or
`docs` and each behaviour has a test that can be written first, so it runs as
an ordinary RED → GREEN cycle rather than SCAFFOLD (PO decision 1).

Required gates that would fail if this broke: `unit` (the workflow's
structure, the hosting headers, the deployment guide and the secret scan are
all unit-tested) and `build` (it covers `public/**`, so `_headers` reaches
`dist/`). What no gate can run is the deploy itself: it needs the production
secrets, which GitHub hands only to jobs on `main`. The first run after merge
is checked by hand, as a DONE step in `## Notes`.

## Acceptance criteria

- **AC-1** - Given a push to `main` (or a manual run on `main`), when
  `.github/workflows/deploy.yml` runs, then its one job uses the GitHub
  environment `production`, installs with `pnpm install --frozen-lockfile`,
  runs `bash scripts/gates.sh --fast` and stops on failure, then runs
  `pnpm build` with `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` and
  `VITE_OWNER_EMAIL` taken from that environment's variables.
- **AC-2** - Given the same run, after the build, then in this order:
  `supabase db push` and `supabase functions deploy` (every function, no names)
  run against the project in the environment variable `SUPABASE_PROJECT_REF`
  with the `SUPABASE_ACCESS_TOKEN` and `SUPABASE_DB_PASSWORD` secrets; then
  `dist/` is deployed to the Cloudflare Pages project named in the environment
  variable `CLOUDFLARE_PAGES_PROJECT`, using the `CLOUDFLARE_API_TOKEN` and
  `CLOUDFLARE_ACCOUNT_ID` secrets. A pull request runs nothing from this
  workflow.
- **AC-3** - Given `pnpm build`, when `dist/` is inspected, then `dist/_headers`
  gives `/sw.js` and `/manifest.webmanifest` `Cache-Control: no-cache`, and
  `dist/` has no top-level `404.html` and no `_redirects`, so Cloudflare Pages
  serves `index.html` for every client route (its single-page-application
  default).
- **AC-4** - `docs/wiki/deployment.md` lists, in order, every one-time step:
  creating the Supabase project and its database password; creating the Pages
  project by direct upload; the Google OAuth client, its JavaScript origin and
  redirect URI, and Supabase's Google provider and URL configuration; the
  `GEMINI_API_KEY` function secret; the scoped Supabase access token and its
  permissions; the Cloudflare API token and account ID; the GitHub
  `production` environment, its branch rule, secrets and variables; after the
  first deploy, setting `app_config.owner_email`; and how to restore a paused
  free-tier project. The VAPID keys and the Vault entries are named as CAL-028's
  steps, not this story's.
- **AC-5** - No secret value appears in the repository: in every tracked text
  file, each of `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`,
  `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, `GEMINI_API_KEY`,
  `VAPID_PRIVATE_KEY` is never assigned a literal value - only a reference
  (`${{ secrets.NAME }}`, an environment read, an identifier) or a placeholder.

### Block 1 - the deploy workflow (AC-1, AC-2)

`.github/workflows/deploy.yml`, one job `deploy`:

```yaml
name: deploy
on:
  push:
    branches: [main]
  workflow_dispatch:
permissions:
  contents: read
concurrency:
  group: deploy-production
  cancel-in-progress: false
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:   # in exactly this order
      - uses: actions/checkout@v5
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4        # with: node-version-file: .nvmrc, cache: pnpm
      - uses: denoland/setup-deno@v2       # with: deno-version: v2.9.x
      - name: Install dependencies         # run: pnpm install --frozen-lockfile
      - name: Gates                        # run: bash scripts/gates.sh --fast
      - name: Build                        # run: pnpm build
                                           # env: VITE_SUPABASE_URL: ${{ vars.VITE_SUPABASE_URL }}, VITE_SUPABASE_ANON_KEY: ${{ vars.VITE_SUPABASE_ANON_KEY }}, VITE_OWNER_EMAIL: ${{ vars.VITE_OWNER_EMAIL }}
      - name: Link Supabase                # run: pnpm exec supabase link --project-ref "$SUPABASE_PROJECT_REF" --password "$SUPABASE_DB_PASSWORD"
      - name: Push migrations              # run: pnpm exec supabase db push --linked --password "$SUPABASE_DB_PASSWORD"
      - name: Deploy functions             # run: pnpm exec supabase functions deploy --project-ref "$SUPABASE_PROJECT_REF" --use-api
      - name: Deploy to Cloudflare Pages   # uses: cloudflare/wrangler-action@v3
                                           # with: apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}, accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }},
                                           #       command: pages deploy dist --project-name=${{ vars.CLOUDFLARE_PAGES_PROJECT }} --branch=main
```

- The three Supabase steps each get `env:` `SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}`, `SUPABASE_DB_PASSWORD: ${{ secrets.SUPABASE_DB_PASSWORD }}`, `SUPABASE_PROJECT_REF: ${{ vars.SUPABASE_PROJECT_REF }}` (only the ones the step uses; never at job level, so no other step sees them).
- **No `pull_request` trigger and no `schedule`**: the environment would refuse a PR the secrets anyway, but the workflow must not even start (AC-2).
- **Why `--fast`**, not the full `gates.sh` (PO decision 3): `db` needs Docker and `integration` a browser (Out of scope), and `build` runs for real in the next step with the production variables. `--fast` runs every required gate except `build`, and the `Build` step's own exit status stops the job.
- **Why this order** (PO decision 4): the schema and functions go first, so the new client never runs against a schema older than it expects; a failed migration stops the job before the client changes. A failed Pages deploy leaves the new schema with the old client, which is the direction migrations are written to tolerate.
- **Checked at PLANNED** against the installed Supabase CLI 2.120.0's own `--help`: `functions deploy` "Deploys all if omitted" (so CAL-028's `send-reminders` is deployed with no edit here); `--use-api` "Bundle functions server-side without using Docker"; `db push --linked --password`; `link --project-ref --password`. Not checked: that a scoped access token with the permissions in Block 3 is enough for `link` - the first run says.
- `--branch=main` makes the upload the Pages project's production deployment (a direct-upload project's production branch is `main` unless changed at creation). Checkable only by the first run.

### Block 2 - hosting files (AC-3)

`public/_headers` (Vite copies `public/` into `dist/` verbatim):

```
/sw.js
  Cache-Control: no-cache
/manifest.webmanifest
  Cache-Control: no-cache
```

- Cloudflare Pages `_headers` syntax: a path line at column 0, then indented `Name: value` lines.
- **No `_redirects`.** The original AC-3 asked for `/* /index.html 200`. Cloudflare Pages already serves `index.html` for unmatched paths when the output has no top-level `404.html`, and a catch-all rewrite onto `/index.html` collides with Pages' own `/index.html` → `/` normalisation, which Pages reports as an infinite loop and ignores (from memory of Cloudflare's behaviour, not measured here - checkable on the first deploy by requesting a client route; PO decision 2).
- The test reads `public/_headers` and asserts `public/` has neither `404.html` nor `_redirects`; `vite build` copying `public/` verbatim is the `build` gate's (settled Vite behaviour, and `e2e/pwa-build.spec.ts` already checks files land in `dist/`).

### PO decisions at PLANNED → RED (2026-10-29, lead-po)

The criteria were rewritten at PLANNED (allowed without `## Amendments`)
because the 2026-10-12 text no longer matched the tree or the owner's setup:

1. **RED → GREEN, not SCAFFOLD.** Every file written classifies as
   `harness` (`deploy.yml`), `config` (`public/_headers`), `docs` or `test`
   (`scripts/classify.sh`, 2026-10-29); none is `source`, so no
   `## Scaffold inventory` is owed, and each behaviour can be pinned by a
   unit test first.
2. **No `_redirects`** (AC-3 changed): Pages' single-page-application default
   already serves `index.html` for client routes, and the catch-all rewrite is
   reported by Pages as an infinite loop (Contract Block 2; unmeasured here,
   checked on the first deploy).
3. **`gates.sh --fast` in the deploy, then the real build** (AC-1 changed):
   the optional `db`/`integration` gates need Docker and a browser (already
   Out of scope), and the production build needs the `VITE_*` variables the
   `build` gate does not have.
4. **Schema and functions before the client** (AC-2 reordered).
5. **The owner's setup is the contract** (AC-1, AC-2 changed): the
   `production` environment limited to `main` holds the secrets, so the job
   declares `environment: production` and reads `vars.*` from it, not
   repository variables. `functions deploy` names no function (CAL-028's
   `send-reminders` does not exist yet; "Deploys all if omitted"). No local
   dry run is wired into `project.conf`: `db push --dry-run` exists but needs
   the production password, which stays out of this machine's tooling.
