## Context

EPIC-04, from `docs/wiki/audits/epic-04-2026-11-06.md` (Decided 1 and 5;
Evidence E-STRYKER `src/sync/cachedStores.ts`, E-HAND C91 and C155).

`cachedTable` (CAL-014 Block 4) starts one Dexie `liveQuery` on the first
subscribe and stops it on the last unsubscribe; `withSyncMarkers` (CAL-015
Block 6) marks an event `failed` if any of its ops failed, else `saving`.
Stryker killed 108 of the module's 128 mutants. Two defects that survive
**the whole unit project** (3000/3000 each, measured by hand) are the ones
that matter:

- **Any unsubscribe stops the stream** (`cachedStores.ts:91`). With the
  guard reduced to `if (live !== null)`, the first listener to leave stops
  the liveQuery while others still listen, so every remaining view stops
  following the cache. The kinds store is read through `useKinds` by several
  components at once (`CalendarPage.tsx:469`, `:543`, `WeekView`, `DayView`,
  `KindLegend`), so a view
  switch would leave the page blind to a Realtime row or a drained op until
  something subscribes afresh. No test holds two listeners and removes one.
- **A later queued op hides a failure** (`:155`). With `else if
  (!marks.has(op.id))` reduced to `else`, an event whose op failed and was
  then edited again is marked `saving`, so its chip loses the failed badge
  and the sheet's failed-sync strip (CAL-045, gated on `sync === "failed"`)
  never shows. Every marker test queues the ops in the other order or one op
  per event.

Two lower-impact holes in the same file: an `"existing"` seed outcome that
writes the server's kinds into the cache itself (`:125:11` → `true`, W125t:
3000/3000), past the pending-op filter the sync applies, so a kind rename
still queued would be overwritten at start-up (reasoned); and a `refresh()`
whose re-read throws (`:66-67`; the catch can be emptied, so "only a cache
that cannot be read publishes unavailable" holds for `subscribe` but is not
pinned for `refresh`; W67: 3000/3000). The `"seeded"` half of `:125` is
pinned: with the write turned off, five `AppShell.test.tsx` legend cases
fail (W125).

Test-only: the shipped module is believed correct, so each new assertion
passes on arrival and is earned by the mutant its criterion names.

Required gate that would fail if this broke: `unit`.

## Acceptance criteria

- **AC-1** - Given a cached events store (and, separately, a cached kinds
  store) with **two** subscribed listeners, when one unsubscribes and a row
  is then written to the cache, then the remaining listener is called and
  `getSnapshot()` shows the row. A test fails when `cachedStores.ts:91` is
  `if (live !== null)` and when its `listeners.size === 0` is `true` or
  `listeners.size !== 0` (audit C91; Stryker `:91:13` → `true` and `!==`).
- **AC-2** - Given an event with a **failed** op and, after it, a **queued**
  op (higher `seq`), when the store publishes, then the event carries `sync:
  "failed"`. A test fails when `:155`'s `!marks.has(op.id)` is `true`
  (audit C155).
- **AC-3** - Given `ensureSeeded()` whose seed answers `"existing"` with
  rows, and an outbox holding a queued update of one of those kinds, when it
  resolves, then the cached kind still shows the queued value: the kinds
  store wrote nothing to `db.kinds` itself, and the sync after it held the
  row. A test fails when `:125`'s condition is `true` (audit W125t).
- **AC-4** - Given a subscribed store whose `read()` rejects during
  `refresh()`, when `refresh()` resolves, then the snapshot's status is
  `"unavailable"`. A test fails when the catch at `:66` is emptied or the
  `unavailable()` call at `:67` is removed.

The members the new cases use (types from `./kindsStore`, `./eventsStore`,
`../kinds/seedKinds`, `./hydrate`, all already imported by the test file):

```ts
// both stores
subscribe(listener: () => void): () => void;   // returns the unsubscribe
getSnapshot(): KindsSnapshot | EventsSnapshot; // { status, kinds, byId } | { status, events }
refresh(): Promise<void>;                      // never rejects
// kinds store only

// status: "loading" | "ready" | "unavailable"; a marked event carries sync: "saving" | "failed"

type SeedRepo = Pick<KindsRepo, "listAll" | "insertMany">;
```

No exported signature changes, so there are **no callers to list**.

**Block 2 - what the test file already gives (reuse, do not rebuild).**
`beforeEach` makes `db = freshDb()` (a real `CalendarDb` over its own
fake-indexeddb factory), `sync` (a `vi.fn` fake resolving `{ status: "ok" }`)
and `seed` (`listAll` / `insertMany` as bare `vi.fn`s); `afterEach` runs
`cleanups` and closes every db in `dbs`. Helpers: `keep(store, listener?)`
(subscribe until the test ends), `settle()` (30 ms for fake-indexeddb and
liveQuery), `titles()`, `offlineRepos()`, `asSyncRepos()`, the kinds `A`, `B`,
`C`, and from `../test/cache-fixtures` `kind(n, extra)`, `ev(n, startsAt,
endsAt, extra)`, `at(month, date, hour)`, `STAMP`, `T1`, `T2`. The `op(id,
status, table = "events")` builder is local to the `sync markers from the
outbox` describe; AC-2's case goes inside that describe, and AC-3's builds its
kind op there too or with a literal of the same shape. No fake timers:
fake-indexeddb schedules on real ones. No new dependency.

State is written straight into the cache: rows with `db.events.put` /
`db.kinds.put` / `bulkPut`; ops with `db.outbox.add` / `bulkAdd`. The outbox
key is `++seq` (`db.ts:48`), so **`seq` is the order of insertion** and
`db.outbox.toArray()` (what the events store's reader calls, `:176`) returns
ops in that order. An op's `status` is the literal `"queued"` or `"failed"`
on the stored record. The seed outcome is injected through `seed.listAll`:
`{ status: "ok", rows: [...] }` with at least one row makes
`ensureDefaultKinds` answer `"existing"` with those rows and never call
`insertMany` (`seedKinds.ts:20`).

**Block 3 - AC-1, two listeners, one leaves (two cases: events, kinds).**
Per store: `const first = vi.fn(), second = vi.fn()`; subscribe both, keeping
both unsubscribes (push the staying one's onto `cleanups`); wait for `status
=== "ready"`; call one listener's unsubscribe; `mockClear()` both; write one
new row (`db.events.put(ev(...))`, respectively `db.kinds.put(A)`); then
`await vi.waitFor(...)` that the listener that stayed has been called **and**
`getSnapshot()` shows the row (events: `titles(...)` or `toStrictEqual([row])`;
kinds: `kinds` `toStrictEqual([A])`). Also assert the listener that left was
not called after it left. Which of the two leaves is RED's choice; the case
needs one that leaves while one stays. With the guard broken the liveQuery is
stopped at that first unsubscribe, the write publishes nothing, and
`vi.waitFor` times out: that timeout is the red.

**Block 4 - AC-2, failed first, then queued.** Inside the markers describe:
one event `put`, then `db.outbox.bulkAdd([op(e.id, "failed"), op(e.id,
"queued")])` in **that** order (failed gets the lower `seq`; the existing
"failed when both" case adds them queued-first, which is why it does not pin
`:155`). Subscribe (or `refresh()` with no subscriber - either reaches
`withSyncMarkers`) and expect `events` `toStrictEqual([{ ...e, sync: "failed"
}])`. Under the mutant the later queued op overwrites the mark with
`"saving"`.

**Block 5 - AC-3, an "existing" seed writes nothing itself.** The criterion's
last clause ("the sync after it held the row") is read as: the store's sync is
a **real** `createSync(db, asSyncRepos(repos))`, not the `vi.fn` fake - with
the fake, the outbox in the Given would be decoration. Setup, with `server =
kind(1, { name: "Gym" })` and `local = { ...server, name: "Yoga" }` (the
optimistic rename):

- `await db.kinds.put(local)`; `await db.outbox.add(` a queued `update` op,
  `table: "kinds"`, `id: server.id`, `patch: { name: "Yoga" }` `)`;
- `seed.listAll.mockResolvedValue({ status: "ok", rows: [server] })`;
- `repos`: `kinds.listSince` resolves `{ status: "ok", rows: [server] }`, the
  other three resolve `{ status: "ok", rows: [] }`;
- `store = createCachedKindsStore(db, seed, createSync(db, asSyncRepos(repos)))`.

Then `await expect(store.ensureSeeded()).resolves.toBe("existing")` and
`expect(await db.kinds.get(server.id)).toStrictEqual(local)`. Two controls
that keep it from being vacuous, both asserted: `repos.kinds.listSince` was
called once (the sync ran and was offered the server's row, so "held" is
`hydrate.ts:65`'s pending filter at work), and `seed.insertMany` was not
called. Under the mutant the store's own `bulkPut([server])` runs before the
sync and the cached name is `"Gym"`. A snapshot assertion through a
subscriber is optional; `db.kinds.get` is the oracle, because the criterion is
about what was written to `db.kinds`.

**Block 6 - AC-4, the read rejects during `refresh()`.** The store must be
subscribed and **`ready` first** - on a `brokenDb()` it is already
`"unavailable"` from subscribe (`:83`, `:86`), which is exactly why the
existing "a cache that cannot be read" case does not pin `:66-67`. So: a
working `db`, `keep(store)`, wait for `"ready"`, then make the **next** read
reject and nothing else: `vi.spyOn(db.events, "toArray")
.mockRejectedValueOnce(new Error("read failed"))` (kinds store:
`db.kinds.toArray`), `await expect(store.refresh()).resolves.toBeUndefined()`,
then `expect(store.getSnapshot().status).toBe("unavailable")`. One store is
enough (events is suggested); restore the spy. The fake `sync` writes
nothing, so the liveQuery does not re-query and consume the one rejection.
This mechanism is reasoned, not run: if the spy cannot intercept the reader's
call on this Dexie (4.x), the fallback is `db.close()` before `refresh()` (a
closed Dexie rejects queries and does not auto-reopen); RED amends this block
with which it used and why. Either way the status just before `refresh()` is
asserted `"ready"`, so the `"unavailable"` after it can only have come from
`reread`'s catch. "The catch emptied" and "the `unavailable()` call removed"
are one edit: line 67 is the catch's only statement.

**Block 7 - oracle partition.** All four criteria are **mechanical: pin

invent. The only waiting is `vi.waitFor` on a liveQuery emission, as the file
