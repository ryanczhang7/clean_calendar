## Context

EPIC-05. The capture edge function (`supabase/functions/capture`, CAL-018,
CAL-019) is called from the browser by `src/capture/captureClient.ts` through
supabase-js, from the deployed app's origin `https://clean-calendar.pages.dev`
and from `pnpm dev` (`http://localhost:5173`, or the LAN `--host` origin for
phone testing). That is a cross-origin request with custom headers, so the
browser sends a CORS preflight first. Found on the owner's first use on the
Pixel (CAL-030 `## Notes`, "Owner's first use on the Pixel (2026-10-30)") and
measured by the orchestrator with curl against the hosted project:

    OPTIONS /functions/v1/capture
      Origin: https://clean-calendar.pages.dev
      Access-Control-Request-Method: POST
      Access-Control-Request-Headers: authorization,apikey,content-type,x-client-info
    HTTP/1.1 405 Method Not Allowed        (no Access-Control-Allow-Origin)

The 405 is the function's own first check (`handleCapture`, step 1: anything
but POST is 405), so the gateway passes OPTIONS through to the function even
with `verify_jwt = true`, and the function has no OPTIONS or CORS handling
(grep: no `Access-Control` or `OPTIONS` under `supabase/functions/`). The
browser refuses the POST, supabase-js raises `FunctionsFetchError`, and
`captureClient.ts` maps that to `{ status: "offline" }`: the owner, online,
sees "Capture needs a connection". A POST sent without auth gets 401 from
Supabase's gateway, which adds `Access-Control-Allow-Origin: *` itself, so
only responses the function produces lack the header, which is every response
that matters.

Two defects, one cause: the preflight is refused, and even once it passes, a
reply without `Access-Control-Allow-Origin` is opaque to the browser, so a 403
or a 502 would also read as "offline" instead of the error the client already
knows how to show. `architecture.md` ("Capture", "Deployment shape") bounds
the solution: one production origin plus local dev; auth is the session's
bearer JWT, never a cookie; the owner check in `_shared/owner.ts` stays the
authorization boundary.

Required gates that would fail if this broke: `deno-test` (the handler and
owner suites, `fetch` stubbed) and `deno-check`. Both required already, so
`required_gates` stays empty.

## Acceptance criteria

All three are mechanical: exact headers on exact responses, no metric, no
threshold. Header names are compared case-insensitively (`Headers.get`).

- **AC-1** — Given an `OPTIONS` request to the function carrying
  `Origin: https://clean-calendar.pages.dev`,
  `Access-Control-Request-Method: POST` and
  `Access-Control-Request-Headers: authorization,apikey,content-type,x-client-info`,
  and **no** `Authorization` header and no body, when `handleCapture` handles
  it, then the status is 204, `Access-Control-Allow-Origin` is `*`,
  `Access-Control-Allow-Headers` names (case-insensitively, as a
  comma-separated list) every header in the Contract's `ALLOWED_HEADERS`,
  which includes the four the browser asked for, `Access-Control-Allow-Methods`
  names `POST`, and `deps.fetch` is never called. This reproduces the bug:
  today the same request is 405 with none of those headers.
- **AC-2** — Given any request `handleCapture` answers itself, when it
  replies, then the reply carries `Access-Control-Allow-Origin: *`. "Any"
  means every status the handler can produce, each with its own test: 405
  (GET), 401 (no bearer), 400 (bad body), 415, 413, 403 (owner false, and the
  rpc failing), 502 `upstream` (kinds fetch failing, Gemini network failure,
  Gemini HTTP failure, no job id), 502 `unreadable`, and 200. The
  `content-type: application/json` on the error and success replies is
  unchanged.
- **AC-3** — Given `requireOwner` in `supabase/functions/_shared/owner.ts`
  refuses a caller, when it returns its 401 or its 403, then that response
  carries `Access-Control-Allow-Origin: *`, so a function that returns it
  unchanged (as `handleCapture` does) is covered without touching it.

### Block 1 - `supabase/functions/_shared/cors.ts` (new)

```ts
/** The one origin value. See Notes, "Origin decision": `*`, never an echo. */
export const ALLOWED_ORIGIN = "*";

/**
 * Every request header supabase-js 2.117.3 can send to a function, as listed
 * by the SDK's own `@supabase/supabase-js/cors` module (SUPABASE_HEADERS in
 * node_modules/.pnpm/@supabase+supabase-js@2.117.3/.../dist/cors.mjs), which
 * the SDK keeps in sync with what it sends. Four of them are in the measured
 * preflight; the other four are sent only on retries or with tracing on, and
 * refusing them would be this bug again the day one appears.
 */
export const ALLOWED_HEADERS = [
  "authorization",
  "x-client-info",
  "apikey",
  "content-type",
  "x-retry-count",
  "traceparent",
  "tracestate",
  "baggage",
] as const;

/** The function accepts POST; OPTIONS is the preflight itself. */
export const ALLOWED_METHODS = ["POST", "OPTIONS"] as const;

/** Lowercase keys; spread into every response the function builds. */
export const CORS_HEADERS: Readonly<Record<string, string>> = {
  "access-control-allow-origin": ALLOWED_ORIGIN,
  "access-control-allow-headers": ALLOWED_HEADERS.join(", "),
  "access-control-allow-methods": ALLOWED_METHODS.join(", "),
  "access-control-max-age": "86400",
};

/**
 * The preflight reply when `req.method === "OPTIONS"`: status 204, empty
 * body, exactly CORS_HEADERS. Null for every other method. Reads nothing
 * from the request: no Origin check (the origin is `*`), no body, no auth.
 */
export function preflight(req: Request): Response | null;
```

Semantics of the numbers: **204** because a preflight has no body and
supabase-js never sees it (the browser consumes it); any 2xx satisfies the
browser, 204 says so. **86400** seconds is "cache the preflight for a day";
Chromium caps it at 7200 and Firefox at 86400, so the practical effect is one
preflight per tab per one to two hours rather than one per capture. A wrong
value here cannot break anything, only cost a preflight.

`ALLOWED_METHODS` does not list GET: the handler answers GET with 405 and a
CORS header on it (AC-2) is what lets the browser *read* that 405.

Why a hand-written list rather than `import { corsHeaders } from
"npm:@supabase/supabase-js/cors"`: the Deno function would add an npm
dependency to `supabase/functions/deno.json` and `deno.lock` for three
strings, the list is pinned here against the installed SDK version, and
`cors_test.ts` pins it (Block 4). When supabase-js is upgraded, re-read the
SDK's list.

### Block 2 - `supabase/functions/_shared/owner.ts`

## Notes

### Origin decision (PLANNED, 2026-10-30): `Access-Control-Allow-Origin: *`

- Authentication is the session's bearer JWT in the `Authorization` header,
  never a cookie, so the request is not credentialed and `*` grants nothing
  that a request from any origin could not already send with curl. The owner
  check (`_shared/owner.ts`, `is_owner()` with the caller's JWT) is the
  authorization boundary and is unchanged.
- The function is called from more than one origin: the Pages origin, the
  Vite dev server (`http://localhost:5173`, `config.toml`'s `site_url`), the
  preview build (`:4173`) and the LAN `--host` origin `architecture.md` names
  for device testing. An allow-list would need an env var the deploy does not
  have (nothing in `.github/workflows/deploy.yml`, `config.toml` or the
  `VITE_*` names declares the app origin) and a second value per environment.
- It is what Supabase's own gateway already sends on the 401 it produces
  before the function runs, and what the SDK's `@supabase/supabase-js/cors`
  helper ships as its default.
- A cookie, a credentialed request or a second tenant would reopen this;
  none exists in the brief.

### Proof on the hosted project

The gates prove the handler in-process. The bug was observed on the hosted
function, so the fix is only proven there by: the merge, the deploy workflow
on `main` (`supabase functions deploy`), the orchestrator repeating the curl

### Why `jsonResponse` and not the gateway

The gateway adds CORS only to responses it produces itself (its own 401). The
function's responses pass through untouched, which is why the handler's 405
reached the browser bare.
