## Context

EPIC-06. Source: `docs/wiki/audits/EPIC-06-2026-11-21.md` (Decided 8,
Evidence E-STRYKER `page`, E-RECHECK R5 to R8).

`useEventEdits` in `src/calendar/CalendarPage.tsx` (CAL-025 Block 6) turns
the edit-scope dialog's answer into a write. Four mutants of it survive the
whole unit project (3380 tests), each re-run in the real tree:

- **R5, `:278`**: `seriesOf`'s `find((e) => e.id === event.id)` ->
  `find((e) => true)`. "All events in the series" then acts on **whatever
  event is first in the events store**: a Delete calls
  `removeEvent(<that event>)`, and a move computes the series' new span from
  that event's times and sends its `updatedAt` as the token. Every CAL-025,
  CAL-075 and CAL-077 page case seeds the store with the series alone
  (`useMoves([spin])`), so the first event *is* the series.
- **R6, `:345`**: the prior-override lookup for the Undo of a "This event
  only" move, `(o) => o.eventId === event.id && o.occurrenceDate === date`
  -> `(o) => true`. The Undo then writes back the times of whatever override
  is first in the store. The two Undo cases (`CalendarPage.test.tsx:3034` and
  `:3059`) hold zero overrides and one override, the matching one.
- **R7, `:392`**: `setPending(null)` removed from `onConfirm`. The dialog
  stays open after Save or Delete has written. No case asserts the
  alertdialog is gone after a confirm (the five `queryByRole("alertdialog")`
  `toBeNull` checks are for writes that never open it, and for Cancel).
- **R8, `:317`**: `failed()` removed from the "series row no longer in the
  cache" branch. "All events" then does nothing, silently. No case removes
  the series between opening the dialog and confirming it.

Test-only: the shipped page is believed correct, so each case passes on
arrival and is earned by its mutant. Required gate that would fail: `unit`
(and `coverage`). The suite is the 150 s `CalendarPage.test.tsx`; the cases
belong beside CAL-025's describes for AC-2, AC-4 and AC-5.

## Acceptance criteria

- **AC-1** - Given the events store holding a one-off event that sorts
  before the weekly Spin series (first in the store's array) and the Spin
  series, when the owner presses Delete on the 18 November Spin chip and
  confirms "All events in the series", then `removeEvent` is called once,
  with the Spin series row, and the one-off's chip stays. A test fails under
  `278s/(e) => e.id === event.id/(e) => true/` on
  `src/calendar/CalendarPage.tsx`.
- **AC-2** - Given the same two rows, when the owner moves the 18 November
  Spin occurrence two days later and confirms "All events in the series",
  then `updateEvent` is called once with the Spin series' id, the span
  `seriesSpan` gives from the **Spin** row (4 November moved to 6 November,
  10:00-11:00), and the Spin row's `updatedAt`. The same mutant fails it.
- **AC-3** - Given the overrides store holding one override for another
  occurrence (Spin, 11 November, 12:00-13:00) and none for 18 November, when
  the owner moves the 18 November occurrence, confirms "This event only",
  and presses Undo, then the second `setOverride` call is
  `(spin.id, "2026-11-18", { startsAt: null, endsAt: null })`. A test fails
  under `345s/(o) => o.eventId === event.id \&\& o.occurrenceDate === date/(o) => true/`.
- **AC-4** - After Save in a change dialog, and after Delete in a delete
  dialog, for either answer, the alertdialog is no longer in the document.
  A test fails under `392s/^    setPending(null);$/    \/\/ setPending(null);/`.
- **AC-5** - Given the delete dialog open for a Spin occurrence, when the
  Spin series row leaves the events store before the owner confirms "All
  events in the series", then the alert "Couldn't save. Try again." is shown
  and neither `removeEvent` nor `cancelOccurrence` is called. A test fails
  under `317s/^      failed();$/      \/\/ failed();/`.

What the code does, read from it, that the fixtures lean on:

- The events store sorts: `liveSorted` (`src/sync/snapshots.ts:24`) orders
  by `startsAt` ascending, then `createdAt`. "First in the store's array" is
  therefore decided by the start time, not by the order of the array given
  to `useMoves`.
- `seriesOf` (`:277-278`) finds the row by `event.id` in
  `stores.events.getSnapshot().events`.
- A series move calls `actions.updateEvent(event.id, next, series.updatedAt)`
  (`:373`) with `next = seriesSpan(series, event, span)` (`:361`). The id is
  the **occurrence's** `event.id` either way, so under R5 the id argument
  does not change; the span and the token do (Block 5).

  `setOverride`, and the Undo closure writes `before` back.
- `onConfirm` (`:390-401`) clears `pending` synchronously in the click;
  `EditScopeDialog` renders nothing when `open` is false
  (`src/events/EditScopeDialog.tsx:35`), so the alertdialog is out of the
  document as soon as the confirm click has been handled, before the write
  resolves.

- Nothing but `onConfirm` and `onCancel` clears `pending` (`:392`, `:448`),
  and `Dialog` only closes through `onClose`; the dialog is expected to stay
  open when the chip that opened it leaves the grid (Block 8).
