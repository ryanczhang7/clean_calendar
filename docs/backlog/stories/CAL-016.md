## Context

EPIC-04, brief §4.4 and success criterion 3: a change on the phone appears on
the laptop within seconds. `architecture.md`, "How the pieces talk": Realtime
`postgres_changes` on `events`, `event_overrides`, `kinds` and `reminders`,
each change applied to the Dexie cache, which the views already observe
(CAL-014). A row with a pending local op keeps its optimistic local value; the
outbox's conditional update (CAL-015) settles it. Realtime does not deliver to
a closed app, so every (re)connect also runs the incremental catch-up.

Required gates that would fail if this broke: `unit` (the channel is mocked)
and `db` (the publication migration), so `db` is in `required_gates`.

## Acceptance criteria

- **AC-1** - Given `supabase db reset`, when the `supabase_realtime`
  publication is inspected, then it includes `events`, `event_overrides`,
  `kinds` and `reminders` and no other table of ours.
- **AC-2** - Given the owner signed in and online, when sync starts, then one
  channel subscribes to `postgres_changes` (all events) on those four tables.
- **AC-3** - Given an INSERT or UPDATE payload whose `updated_at` is newer than
  the cached row's (or no cached row), when it arrives, then the row is
  upserted in the cache and a mounted month view shows it without a reload;
  an older or equal `updated_at` is ignored.
- **AC-4** - Given a payload for a row that has a pending op in the outbox, when
  it arrives, then the cache keeps the local value and the op stays queued.
- **AC-5** - Given the channel reports `SUBSCRIBED` after a disconnect, or the
  app returns to the foreground, when that happens, then the incremental
  catch-up of CAL-014 runs once.

### Block 3 - `src/sync/realtime.ts`

```ts
import type { RealtimePostgresChangesPayload, RealtimeChannel, REALTIME_SUBSCRIBE_STATES } from "@supabase/supabase-js";
/** The two members of SupabaseClient the module uses; tests hand a fake. */
export type RealtimeClient = {
  channel(name: string): RealtimeChannel;
  removeChannel(channel: RealtimeChannel): Promise<unknown>;
};
export const CHANNEL_NAME = "cache";
export const TABLES = ["events", "event_overrides", "kinds", "reminders"] as const;
export type RealtimeTable = (typeof TABLES)[number];
export type Realtime = {
  /** Subscribes the one channel; idempotent while started. */
  start(): void;
  /** Removes the channel and the visibility listener; idempotent. */
  stop(): void;
  /** Apply one payload to the cache (exported for the tests; start() wires it to the channel). */
  apply(table: RealtimeTable, payload: RealtimePostgresChangesPayload<Record<string, unknown>>): Promise<void>;
};
export function createRealtime(client: RealtimeClient, db: CalendarDb, sync: Pick<Sync, "run">, doc?: Document): Realtime;   // doc default: document
/** The reminders row mapper (rows.ts has none yet; CAL-026 may move it). */
export function toReminderRow(row: { id: string; event_id: string; minutes_before: number; sent_at: string | null; occurrence_date: string | null; created_at: string; updated_at: string }): ReminderRow;
```

`start()`: `client.channel(CHANNEL_NAME)`, then for each of the four tables
`.on("postgres_changes", { event: "*", schema: "public", table }, (payload)
=> void apply(table, payload))`, then `.subscribe(onStatus)` - one channel,
four bindings, in `TABLES` order (AC-2). Also `doc.addEventListener(
"visibilitychange", onVisible)`.

`apply(table, payload)` (AC-3, AC-4), nothing throws:
- `eventType` `DELETE` → ignored (hard deletes never happen, story Notes).
- `INSERT` / `UPDATE` → `row = payload.new` mapped by `toEvent` /
  `toEventOverride` / `toKind` / `toReminderRow` into the matching Dexie
  table (`events`, `overrides`, `kinds`, `reminders`).
- In one `db.transaction("rw", table, db.outbox)`: if the outbox holds any
  op (`queued` or `failed`) for `(table's outbox name, row.id)` → **no
  write** (AC-4; the drain settles it, CAL-015). Else if the cached row
  exists and `cached.updatedAt >= row.updatedAt` (string compare, the same
  rule as the sync mark) → no write. Else `put(row)`.
- A mapper that throws on a malformed payload → the payload is ignored.

*RED, 2026-10-22: "nothing throws" is pinned as "`apply` never rejects".
Two malformed shapes are tested per table: `new: null` (the rows.ts mappers
throw on it) and `new: {}` (the mappers do NOT throw - they return an
object whose `id` is `undefined` - and Dexie then rejects the key). Both
must resolve with the cache unchanged, so the guard is a `try` around the
whole of `apply`, not around the mapper alone. An UPDATE for a row the
cache does not hold is inserted, as an INSERT is.*

`onStatus(status)` (AC-5): the **first** `SUBSCRIBED` after `start()` runs
nothing (`startSync` has just pulled); every later `SUBSCRIBED` (a rejoin
after a disconnect) → one `sync.run()`. `TIMED_OUT`, `CLOSED`,
`CHANNEL_ERROR` → nothing (the client reconnects itself). `onVisible`: when
`doc.visibilityState === "visible"` → one `sync.run()`; `"hidden"` → nothing.
`stop()`: `client.removeChannel(channel)`, remove the listener, forget the
channel so a later `start()` subscribes anew and its first `SUBSCRIBED` is
again silent.

*RED, 2026-10-22: a status reported by a channel that `stop()` already
removed runs nothing (tested: after `stop()`, a late `SUBSCRIBED` from
the old channel adds no `sync.run()`). A `start()` while started is a
no-op for the page listener too: one `visibilitychange` → one run.*
